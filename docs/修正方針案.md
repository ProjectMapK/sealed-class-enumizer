## 1. runtime-api の自動追加スコープ（`implementation` → `api`・アプリ側修正済み）

- **状態**: gradle-plugin の修正（自動追加を `api` へ）は適用済み。テスト側の暫定宣言（下記「残作業」）が残り
  他資料も本項を参照するため、その除去まで本項を残す（除去をもって欠番化する）。
- **仕様（期待）**: 概要 §7「生成 API（`SI.Enumish` とそのメンバー）は通常の宣言としてメタデータ / klib に載るため、
  **プラグインを適用していない利用側モジュールからも普通に参照できる**（プラグインが必要なのは生成する側だけである）」。
- **修正前の NG**: `consumer-pure-jvm`（プラグイン未適用・`implementation(project(":producer-jvm"))` のみ）から
  `SI.Enumish.entries` / `si.asEnumish()` / `si.label` を参照するとコンパイルエラーになっていた。

  ```
  Cannot access 'org.wrongwrong.sealedClassEnumizer.Enumish' which is a supertype of
  'org.wrongwrong.fixtures.SI.Enumish'. Check your module classpath for missing or conflicting dependencies.
  ```

  原因は `SealedClassEnumizerGradlePlugin.addRuntimeDependencyIfEnabled` が runtime-api を
  `implementation` で追加していたことである。`implementation` は利用側のコンパイルクラスパスへ伝播しないため、
  生成 API の supertype（`Enumish` / `Enumized`）と拡張プロパティ `label` が利用側から見えない。
  生成 API は supertype として runtime-api の型を公開している（ABI の一部）ので、これは
  Gradle の api/implementation 区分でいう **api 依存**である。
- **適用した修正**: `SealedClassEnumizerGradlePlugin` の自動追加を `implementation` → `api`
  （`defaultSourceSet.dependencies { api(...) }`）へ変更した。Kotlin JVM / MPP プラグインはソースセットに
  `api` スコープを常設しているため置き換えのみで足りる。テスト系コンパイレーション（`test` 等）は公開面を
  持たないが、区別の実益が無いため全コンパイレーション `api`（害は無い）とした。
  概要 §7 のモジュール表（gradle-plugin の行）へ「`runtime-api` を **api スコープで**自動追加」を反映済み。
- **暫定宣言の除去（実施済み）**: producer / lib をプロジェクト参照する消費側（`consumer-pure-jvm` /
  `downstream-subtype-jvm` / `java-consumer` / `mpp-consumer` と TestKit フィクスチャ abi-propagation /
  sweep-xm-negative / diag-cross-*）は `api` 化で runtime-api を推移取得できるため、暫定の明示宣言を除去した。
- **欠番化の保留**: 別要因（推移メタデータを持たない依存形態など）で明示宣言を要する消費側や、
  他資料が本項を参照する間は、方針どおり欠番化せず記述を保持する。

## 2. MPP の共通ソース由来の生成 companion が、生成コンパイレーションの外から参照できない

- **仕様（期待）**: 概要 §7「生成 API は通常の宣言としてメタデータ / klib に載るため、プラグインを適用していない
  利用側モジュールからも普通に参照できる」・概要 §1/§6 の kind 単位 when の枝 `SI.Foo.Companion ->`。
- **実測（NG）**: commonMain の `@Enumize sealed interface SI { data class Foo(val v: Int) : SI }`
  （companion 自動生成）に対して:
  - 全ターゲット共通: 別コンパイレーション（**同一モジュールの commonTest を含む**）からの
    `SI.Foo.Companion` の名指しが `Unresolved reference 'Companion'`。一方で網羅性検査は
    「Add the 'Companion' branch or an 'else' branch」を報告する = sealed inheritors の直列化は成立しており、
    **companion の連結（ネストクラスとしての可視化）だけが欠落**している。
  - klib 系（js / wasmJs / wasmWasi）: 加えて末端型レシーバでの `asEnumish()` 呼び出し（返り値型 = 生成
    companion。enum 末端の `Command.Builtin.HELP.asEnumish()` を含む）が
    `Cannot access class '...Companion'` でコンパイル不能。
  - JVM はクラスファイル・bridge・static な Companion フィールドまで完全に生成され、呼び出し自体は可能。
  - **手動宣言した companion・object 末端・生成 Enumish とその Companion・platform ソースセット
    （jvmMain 等）に置いた階層は全経路で正常**。JVM 単一プラットフォームモジュール（producer-jvm）でも
    再現しない。共通ソースセット由来の「自動生成 companion」に固有の欠落である。
- **根拠となる観測**: JVM `@Metadata` の protobuf 比較で、jvmMain 由来の末端には nested_class_name
  （"Companion"）が載るのに対し、common 由来の末端には **companion_object_name はあるが
  nested_class_name が無い**。
- **推定原因（実装コードと突き合わせ済み）**: 末端の自動 companion は設計01 §6 の正規経路
  （`getNestedClassifiersNames` / `generateNestedClassLikeDeclaration`）で生成されており、生成経路の
  逸脱ではない。一方、`replaceCompanionObjectSymbol` + `ownerGenerator` リフレクション刻印による
  自前連結（実装ノート §2 の 1）の対象である**生成 Enumish の Companion は全ターゲットで正常**である。
  この対比から、欠落は「**ソース宣言（common フラグメント帰属）の外側クラスを直列化する際の、
  provider 生成ネスト分類子の列挙**」に固有と考えられる — companion_object_name は
  `FirCompanionGenerationProcessor` が FirRegularClass へ連結した結果として残り、nested_class_name の
  索引だけが生成拡張への問い合わせを経ずに直列化されている形である。これは設計00 §7・§10 V5 が
  未確定としていた「`FirDeclarationsForMetadataProviderExtension` の要否」が（少なくとも共通ソースの
  ネスト索引について）「要」である徴候の可能性が高い。
- **修正方針案**: (1) `FirDeclarationsForMetadataProviderExtension` を実装し、共通ソースセットの
  直列化へ生成宣言（少なくとも末端の自動 companion）を供給してネスト索引に載せる（V5 の残項目の
  決着を兼ねる）。(2) 併せて、K2 + MPP で companion 自動生成の実績がある kotlinx.serialization の
  登録・生成形（同じ provider 経路）との差分比較で、フラグメントセッション × 直列化の欠落点を特定する。
  自前連結側（生成 Enumish の Companion）は正常のため変更しない。
  修正後は、テスト側で書き換えた「基底型レシーバ経由」の検証を companion 名指し形へ戻し、
  無効化した else 無し kind-when（companion 枝）を有効化して確認する。
- **テスト側の暫定対応**: kind の同一性検証は基底型レシーバの `asEnumish()` / `valueOf` 経由に書き換えて
  意味論を全ターゲットで検証済み（mpp-producer / mpp-consumer）。companion 名指しを要する
  else 無し kind-when は本来形をコメントに残して `@Ignore` で無効化。object 末端のみの階層では
  跨モジュール else 無し kind-when が全 klib ターゲットで成立することを別途 green で確認している
  （V1-a の inheritors 直列化そのものは成立）。

## 4. エッジ §1.1 #2「基底より広い末端」の interface 末端への一般化が過剰

- **仕様（記述）**: エッジケースへの対応方針 §1.1 #2（sealed interface 階層では基底より広い可視性の末端が
  言語上成立する）。テストケース管理.md はこれを interface 末端へ展開したケース（TC-GAP-014 =
  internal 基底 + public **interface** 末端）を持つ。
- **実測**: `public interface Wide : InternalBase` は
  `'public' sub-interface exposes its 'internal' supertype 'InternalBase'` で**コンパイル不能**
  （Kotlin 2.4.20-Beta1）。エッジ §1.1 の実測表 #2 自体は「internal / private な interface を
  public **class** が実装」の測定であり正しい。過剰なのはその帰結文「sealed interface 階層では
  基底より広い末端が言語上成立する」の無限定な一般化（および §1.2 の表・テストケース側の
  interface 末端への展開）で、実際に露出検査を免れるのは implements 形（class 系末端 —
  object / enum / value class を含む）に限られ、**interface が interface を継承（extends 形）する
  場合は露出検査が働く**。
- **修正方針案**: アプリ側の修正は不要。エッジケースへの対応方針 §1.1 の実測表へ
  「public interface が internal interface を継承 → エラー（extends 形には露出検査が働く）」の行を
  追加し、帰結文と §1.2 の「基底より広い末端」行に「成立するのは class 系末端に限る
  （interface / fun interface 末端は言語の露出検査によりコンパイル不能）」の限定を付す。
  拡張点（非 final 末端）× E-2 の組み合わせに言及する箇所は open / abstract class 末端に限定する。
- **テスト側の対応**: E-2 の外部観測（consumer 側）は class 末端（`widerleaf.PublicLeaf`）ベースで実装する。
  interface 末端版（TC-GAP-014 の元定義）は「言語上成立しない」ことの確認へ読み替え済み。

## 6. ENUMIZE_LABEL_CLASH の報告位置が別ファイル末端で壊れる

- **仕様（期待）**: 設計01 §7.1 — label 衝突は衝突する両末端（それぞれの宣言位置）に報告する。
- **実測（NG）**: 衝突する末端が基底と**別ファイル**にある場合、診断が**基底側ファイルの無関係な座標**
  （例: import 行の内部オフセット）に付く。文言と両当事者の FQN 自体は正しい。
- **推定原因**: チェッカーが基底宣言の検査中に `leaf.source`（別ファイル由来のオフセット）で reportOn
  しており、診断の座標系が「検査中のファイル」に紐づくため、別ファイルのオフセットが検査中ファイルの
  座標として解釈される。
- **修正方針案**: 衝突検査の報告を「基底の検査中に全末端へ report」から「**各末端の検査時に自分の宣言へ
  report**」する形へ移す（末端側チェッカーで自分の label が階層内で衝突しているかを判定する）。
  末端側で検査すれば source は常に検査中ファイル内であり座標系の不整合が起きない。
- **テスト側の暫定対応**: 文言・FQN の assert は有効のまま、位置 assert のみ仕様どおり書いて
  `@Disabled` で保持（gradle-integration の diag-label-clash 系）。

## 7. IC で label 衝突を導入するとバックエンドの codegen クラッシュになる

- **仕様（期待)**: 設計00 §5.3 #8 — 再ビルドで label 衝突を導入したら ENUMIZE_LABEL_CLASH の
  コンパイルエラー（フロントエンド診断）になる。
- **実測（NG）**: 初回ビルド後に衝突する末端ファイルを追加して再ビルドすると、診断が出ないまま
  バックエンドが `RuntimeException: Exception while generating code for asEnumish` でクラッシュする
  （KT-86121 と同系の見え方）。
- **推定原因**: IC ラウンドで基底が共連れ再コンパイルされる際、チェッカーの衝突検査が
  （前ラウンドのメタデータ由来の宣言と新規ソース宣言の混在ビューで）素通りし、フロントエンドを
  通過した不整合な階層に対して IR 生成が失敗している。
- **修正方針案**: まず #6 の「末端側で検査」への移行で、新規追加された末端自身のコンパイル時に
  衝突が検出される形にする（追加ファイルは必ず当該ラウンドのソースにあるため、メタデータ混在ビューでも
  自分自身の検査は成立する）。その上で、IR 側にも「entries 構築時に label 重複を検出したら
  ICE でなく診断相当のエラー報告へ落とす」ガードを敷く（フロントエンド素通り時の安全網）。
- **テスト側の暫定対応**: TestKit の該当ケースはクラッシュ実測を記録し `@Disabled`（仕様アサートのまま）。

## 8. import エイリアス経由の supertype で階層判定が全欠落する

- **仕様（期待）**: 設計01 §6.2 — raw-ref が追えない構成（typealias 等）でも解決後の検査で
  ENUMIZE_COMPANION_REQUIRED を報告し、明示 companion を促す（「明示的な companion は常に完全な
  ワークアラウンド」）。typealias 経由は実測どおり発火する（TC-DIAG-057 green）。
- **実測（NG）**: **import エイリアス**（`import pkg.SI as Base` して `class Foo : Base`）経由だと、
  プラグインの診断が一切出ず、supertype 注入・asEnumish 生成も行われず、言語の
  「abstract member 未実装」エラーへ合流する（companion を明示しても解消しない = ワークアラウンド不成立）。
- **推定原因**: raw 段階（COMPANION_GENERATION フェーズ）の非所属判定の結果が basesCache に残り、
  解決後フェーズ（SUPER_TYPES 以降）の判定がその汚染されたキャッシュを参照している
  （resolver 冒頭コメントが警告している構成そのもの）。import エイリアスは raw-ref では別名にしか
  見えないため raw 判定は「非所属」になるが、その結果を解決後にも使い回してはならない。
- **修正方針案**: basesCache をフェーズ別に分離する（raw 段階の否定結果を解決後の判定に使わない。
  解決後は fullyExpandedType ベースで再判定してキャッシュを上書きする）。修正後は import エイリアス
  構成が typealias と同じ扱い（companion 自動生成の候補判定は働かず ENUMIZE_COMPANION_REQUIRED、
  明示 companion で完全動作）になることをテストで確認する。
- **テスト側の暫定対応**: 単離フィクスチャで実挙動を記録し `@Disabled`（仕様アサートのまま）。

## 9. ENUMIZE_CROSS_SOURCE_SET（言語エラーへの補足）が発火しない

- **仕様（期待）**: 概要 §8・設計01 §7.2 — 階層の継承者が別ソースセットにある場合、コンパイラ本体の
  言語エラーに加えて補足説明の ENUMIZE_CROSS_SOURCE_SET を出す。
- **実測（NG）**: 言語エラー「Extending sealed classes or interfaces from a different module is
  prohibited.」のみが出て、補足診断が出ない。
- **推定原因**: 別ソースセットの継承者はコンパイラが基底の inheritors 一覧に載せないため、
  プラグインの検査（inheritors 走査ベース）からは当該継承者が見えず、検査対象が空になる。
- **修正方針案**: 2 案あり、(a) 継承者側のチェッカー（supertype に @Enumize 基底を持つ宣言の検査）として
  実装し直し、宣言側セッションの moduleData 比較で別ソースセットを検出する。
  (b) 言語エラーが十分に説明的である（メッセージが sealed の同一モジュール制約を明示する）ことを
  受けて、補足診断を諦めて設計01 §7.2 から削除し、概要 §8 の該当行を「コンパイラ本体の診断に委ねる」へ
  改める。継承者は inheritors に載らない = プラグインの動作自体は正しく保たれるため実害は薄く、
  **(b) の文書側整理を推奨**する（(a) は KMP のソースセット構成の網羅が必要で費用対効果が悪い）。
- **テスト側の暫定対応**: 言語エラーの発火（= 階層が壊れないこと）は green で確認済み。補足診断の
  assert のみ `@Disabled`。

## 10. KIND_NOT_ACCESSIBLE と KIND_TYPE_NOT_DENOTABLE の優先関係が成立していない

- **仕様（期待）**: テストケース管理.md の優先規則（NOT_ACCESSIBLE > DENOTABLE。両方の条件が
  重なる構成では NOT_ACCESSIBLE のみを報告する）。なおこの優先規則は設計01 §7.2 の診断カタログには
  明文化されておらず、ケース表側だけが規定している（仕様の出典が弱い）。
- **実測（NG）**: 両条件が重なる構成（基底より広い末端 + private companion 等）で**両方が併発**する。
- **修正方針案**: 参照可能性検査（NOT_ACCESSIBLE）が成立した末端については返り値型の表記可能性検査
  （DENOTABLE）をスキップする早期 return を入れ、同時に**優先規則を設計01 §7.2 へ明文化**する
  （現状はケース表にしか根拠が無いため、仕様側の追記が修正の一部である）。報告が 2 重になるだけで
  挙動への実害は無いため優先度は低いが、NOT_ACCESSIBLE の修正（companion を可視化）が DENOTABLE も
  同時に解消する従属関係にある以上、先勝ちの方が利用者の導線として正しい。併発許容へ仕様側を
  倒す選択肢は、この従属関係を利用者に二重に見せるだけで利点が無い。
- **テスト側の暫定対応**: 併発の実測を記録し、単独発火の assert を `@Disabled`。

## 11. 発火範囲が仕様の含意と異なる 2 件（分岐判定待ち）

いずれも「仕様の文言がどちらとも読める」ため、修正でなく判断の材料として記録する。

- **拡張シャドーイング警告（ENUMIZE_EXTENSION_SHADOWED）が継承メンバーを見ない**: 階層メンバーが
  supertype から `label` プロパティを**継承**している場合（自クラスに宣言が無い場合）、警告が出ない。
  これは概要 §8 の字義（「階層メンバーが label という可視メンバーを**宣言している**場合」）には
  一致しており、仕様違反ではない。一方でシャドーイングの実害（`x.label` がユーザープロパティを返す）は
  継承由来でも同じに起きるため、**検査を可視メンバー全体へ広げて概要 §8 の文言も「宣言または継承」へ
  改める**か、字義どおり宣言のみに留めるかの仕様判断である。実害の同質性から前者を推奨するが、
  継承由来は supertype 側の都合で発生し末端の作者に修正手段が乏しい（改名できない）ため、
  広げる場合も警告レベル維持と「asEnumish() 経由の取得」を案内する文言が前提になる。
- **ENUMIZE_MULTIPLE_FAMILIES が非 sealed 末端 interface 経由の二重所属を検出しない**: 家族探索が
  sealed 連鎖のみを辿るため、非 sealed 末端 interface を経由して 2 階層に属する型は言語エラー
  （sealed 外継承の禁止等）にしか掛からない。テストケース管理.md 自体が「ID 未確定の残ギャップ」と
  していた領域。言語エラーで実害が塞がっているため、**検出範囲の拡張はせず、設計01 §7.2 に
  「非 sealed 経由の二重所属は言語エラーに委ねる」と明記する案を推奨**する。

## 12. 基底不在の IC ラウンドで生成 asEnumish の IR ボディが充填されずバックエンド ICE になる

- **仕様（期待）**: 設計00 §1・§5 — 階層不変条件（末端側ファイルだけが編集されても基底ファイルが
  共連れ再コンパイルされ、生成が常に階層 1 単位で行われる）を IC 安全の一級要件とする。
  §5.3 #2（末端追加）は「利用側の網羅性エラーとして正しく現れる」が期待。
- **実測（NG）**: 次の 2 形で決定的に
  `e: java.lang.RuntimeException: Exception while generating code for ... asEnumish ...`
  `Caused by: IllegalStateException: Function has no body: FUN GENERATED[...EnumizeKey] asEnumish`
  のバックエンド ICE になる（再試行でも持続・**clean ビルドで回復**）:
  1. 末端を**新規ファイル**として追加（`data object Baz : SI` の新 .kt 追加 → 初回 IC ラウンドが
     新規ファイル単独で走る）— TC-IC-011（§5.3 #2）
  2. **中間 sealed のファイル単独の ABI 非変更編集**（2 段・3 段チェーンとも、中間ファイルのコメント
     編集で末端側が基底不在ラウンドで再コンパイルされる）— TC-IC-025/060
  - 既存ファイルへの末端追記・末端削除・基底ファイル同時編集（同一ラウンド入り）では**発生しない**。
    設計00 §5.4 が想定していた「連続編集ラウンド」のクラッシュはむしろ再現しない（コメント・private
    追加・基底編集の連続ラウンドはすべて green・entries 非 stale・バイト一致）。
- **推定原因**: KT-86121（多ファイル sealed × プラグイン生成 × IC。2.5.0-Beta1 修正予定）の再現形。
  設計00 §1 の階層不変条件は「同一**ビルド**での再コンパイル」を述べており、その粒度では成立している
  可能性があるが、コンパイラのマルチラウンド IC は**ラウンド粒度では階層の部分集合ビューを許す**
  （設計01 §7.1 がチェッカーに単調性を要求しているのはこのため）。プラグイン構造としては、
  実装ノート §2 の 4（IC ラウンド外基底のアノテーション直接照合フォールバック）により
  **FIR 側の宣言生成は基底不在ラウンドでも成立する**一方、**IR 側のボディ充填が「基底（と生成
  Enumish）が同一ラウンドの IR にあること」を前提**にしており、部分集合ビューへの耐性がチェッカーに
  しか設計されていなかった非対称が破綻点である — 宣言だけが codegen へ渡って
  "Function has no body" に落ちる。
- **修正方針案**:
  1. **短期（プラグイン側緩和）**: IR 生成時、ラウンド内の各生成宣言（asEnumish 等）についてボディ
     未充填を検出したら、基底・生成 Enumish・companion のシンボルを（ラウンド外でも）シンボルテーブル /
     参照経由で解決してボディを構築する。生成対象の末端クラス IR 自体はラウンド内に必ずあるため、
     参照解決さえできればボディは組める。少なくとも ICE を「明示的な診断（再ビルド or clean を促す）」へ
     落とすガードは必須（沈黙のクラッシュは IC 安全の一級要件に対する最悪の形）。
  2. **恒久**: Kotlin 2.5 系の KT-86121 修正で基底共連れがコンパイラ側で保証されるなら、
     マイナーバージョン毎のアーティファクト分割（概要 §7）の下で 2.5 対応版から本問題を解消済みとし、
     2.4 版は 1. のガード + 既知の制限として文書化する。
  3. **文書**: 設計00 §1/§5 の「階層不変条件（実測確認済み）」に本 2 形の除外を追記し、
     §5.3 #2 の期待を「新規ファイル追加の初回ラウンドは既知の ICE（KT-86121）」へ改める。
     回避策（新規末端の追加は基底ファイルと同時編集で保存する・clean で回復する）を known-issue として
     概要 §7 か README 相当に記載する。
- **関連**: #7（IC での label 衝突導入がクラッシュ）は再現形が「新規ファイル追加」であり、本項の 1. の
  形と同根の可能性が高い。#12 の緩和後に #7 が診断（LABEL_CLASH）へ到達できるようになるかを再測すること。
  ただし報告位置の問題（#6）は独立に残る。
- **テスト側の暫定対応**: 仕様どおりのアサートを持つ 2 メソッドを `@Disabled` 化し、`Kt86121Test` が
  両形を「クラッシュすることが expected」の回帰ゲートとして保持する（Kotlin 更新等で解消したら
  テストが fail して検出できる）。

## 13. private 外側クラスにネストした別ファイル末端で KIND_NOT_ACCESSIBLE が発火しない

- **仕様（期待）**: 概要 §8・設計01 §7.2 — kind が基底の本体スコープから名前参照できない構成
  （entries 構築コードは基底の内側に生成されるため各 kind を名前で参照できる必要がある）は
  `ENUMIZE_KIND_NOT_ACCESSIBLE` でエラーにする。列挙されている具体例は (a) 別ファイルの private な
  **トップレベル**の末端、(b) 末端 class の private / protected な既存 companion。
- **実測（NG）**: `private class HiddenHost { object Leaf : Root }`（外側クラスが private・末端 Leaf 自身は
  public・**別ファイル**）は、doc の想定に反して診断が発火せず、`Leaf` が entries に載り
  `valueOf("Leaf")` / `label` が実行時に正常動作する（producer-jvm `sweepprivateouter` の
  `SweepPrivateOuterTest` が green で固定）。一方 (a) の「末端自身が private トップレベル」
  （TC-LEAF-089 / TC-VIS-031）は仕様どおり発火する。
- **推定原因**: (1) チェッカーの参照可能性判定が「末端シンボル自身の実効可視性」を見ており、
  **外側クラス連鎖の可視性**（private 外側クラス経由で名前解決経路が断たれること）を辿っていない。
  (2) entries 構築コードは IR-only 生成（EntriesHolder.createEntries）であり、JVM では private
  トップレベルクラスが package-private にコンパイルされるため、同一パッケージの生成コードから
  `HiddenHost.Leaf`（の INSTANCE フィールド）へアクセスできてしまい、FIR チェッカーがすり抜けた後の
  IR / バイトコードでもエラーにならない。**この「JVM で通る」性質はプラットフォーム依存**であり、
  他バックエンド（klib）では参照不能または実行時エラーになりうるため、MPP 一級要件の観点から
  黙認すべきでない。
- **修正方針案**: チェッカーの KIND_NOT_ACCESSIBLE 判定を、末端自身の可視性だけでなく
  **「基底本体スコープから末端の ClassId を名前解決できるか」= 外側クラス連鎖を含む名前到達可能性**へ
  一般化する（外側のいずれかが基底スコープから不可視なら発火）。併せて概要 §8・設計01 §7.2 の
  列挙 (a) を「別ファイルの private トップレベル末端**、または private / internal な外側クラスに
  ネストされ基底スコープから名前参照できない末端**」へ拡張する。
- **テスト側の暫定対応**: `SweepPrivateOuterTest` が現状の実挙動（非発火・entries 掲載）を固定している。
  修正後は同テストを「KIND_NOT_ACCESSIBLE 発火」を要求する TestKit 負値へ移し替える
  （コンパイルエラーになるため通常モジュールには置けない）。
