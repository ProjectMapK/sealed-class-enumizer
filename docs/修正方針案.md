## 17. 生成型への typealias を基底の supertype の頭に使うとバックエンド ICE になる（配置依存）

- **仕様（期待）**: 設計01 §4・§6.2 — 型引数まで一致する `Enumized<SI.Enumish>` の手動宣言は注入をスキップし、supertype
  の表記で扱いを変えない。  
  [保留](test/保留.md) GATE-01。
- **実測（NG）**: `typealias A = Enumized<SI.Enumish>` を介した `@Enumize sealed interface SI : A` が、
  エイリアスが階層より先に解決されない配置（**階層と同一ファイル**・**ソース処理順で後になる別ファイル**）で
  `Backend Internal error: Exception during IR fake override builder`（`IllegalArgumentException`。
  フロントエンド診断は一切出ない）になる。  
  エイリアスが先に処理される別ファイル配置（ケース04 DIA-52 の先解決配置）は成立する。
- **原因（実測で切り分け済み）**: typealias の展開先が**プラグイン生成型**（`SI.Enumish`）である場合、
  エイリアスが階層より先に解決されない配置では、解決済み supertype がエイリアスのまま据え置かれ `fullyExpandedType`
  でも展開できない。  
  プラグイン側の注入抑止は raw 追跡（エイリアス自身のスコープでの名前解決）へ落として配置に依らず成立しており、
  二重注入は起きない。  
  残るのは未展開のまま IR へ渡る言語側の経路である。  
  生成型を介さない同型（`typealias A = Box<S.Nested>` + `sealed interface S : A`）はプラグイン非適用なら同一ファイルでも
  正常にコンパイルされるため、生成型との組み合わせに固有である。
- **修正方針案**: プラグイン側で塞ぐ手段は無い。  
  この配置を検出して報告する専用診断は設けない（言語側の制約に対して診断カタログを増やす価値が低い）。  
  回避策（**基底の supertype の頭にはエイリアスを使わない** —
  型引数としての使用と末端側での使用は配置に依らず成立する）は概要 §7 に既知の制限として記載がある。  
  本項は言語側の解消をもって欠番化する。
- **テスト側の暫定対応**: 仕様どおりのアサートは `@Disabled` で保持し、
  実挙動（ICE）を固定する回帰ゲートを併置する（SweepTypealiasSupertypeTest。解消したらゲートが fail して検出できる）。
