## 12. 基底不在の IC ラウンドでプラグインの IR 生成が走らずバックエンド ICE になる

- **仕様（期待）**: 設計00 §1・§5 — 階層不変条件に相乗りし、継承者の集合に依存する生成物を基底ファイル帰属に
  置くことで IC 安全を得る（P1）。§5.3 #2（末端追加）は「利用側の網羅性エラーとして正しく現れる」、
  設計01 §7.1 は部分集合ビューでも診断が単調であることが期待。
- **原因（確定）**: `EnumizeIrGenerationExtension` は `@Enumize` 基底を**ラウンド内のファイルからのみ**収集し、
  見つからなければ早期リターンする。基底不在ラウンドではプラグインの IR 生成（EntriesHolder 生成・ボディ充填・
  kind の toString 生成）が丸ごと走らず、FIR が生成した宣言がボディ無しで codegen へ渡って
  `IllegalStateException: Function has no body: FUN GENERATED[...EnumizeKey] asEnumish` になる。
  Kotlin 本体のプラグインはこの形を取らず、**module fragment 上で `origin` が自分の `GeneratedByPlugin` である
  宣言を見つけて埋める**（`plugins/plugin-sandbox` の `AbstractTransformerForGenerator`・Parcelize の
  `ParcelizeIrTransformer`。後者はラウンド内で未生成の参照を `defer` へ退避する）。本プラグインでも末端側の
  ボディ（`asEnumish` / `label` / `enumizedClass` / kind の `toString`）は末端と companion だけで組めるため、
  基底の同席は本来不要である。同種症状の upstream 事例 KT-59112（`@Parcelize` × ネスト sealed の
  "Function has no body"）も Subsystem = Tools. Parcelize としてプラグイン側で修正されている。
- **KT-86121 とは別事象**: KT-86121 は「serializable な sealed 継承チェーンが複数ファイルに分かれた場合の IC 失敗」
  であり、`SyntheticAccessorLowering` の委譲コンストラクタ処理で `IndexOutOfBoundsException` になる
  （kotlinx.serialization / Affected 2.4.0-Beta2・2.3.21 / Planned 2.5.0-Beta1）。落ちる層もクラッシュ種も違い、
  共通点は「多ファイル sealed × プラグイン × IC」という表層だけであるため、2.5 での解消は期待できない。
- **基底がラウンドに入る条件（実測）**: IR 拡張へ一時計測を入れ、各ラウンドの `moduleFragment.files` と収集できた
  基底を観測した（Kotlin 2.4.20-Beta1 / Gradle 9.5.0）。

  | 編集 | ラウンドのファイル | 基底 | 結果 |
  |---|---|---|---|
  | 既存 kind を宣言するファイルのコメント編集 | 末端 3 + Si + Use | あり | 成功 |
  | 同じファイルへの末端追記 | 末端 3 + Si + Use | あり | 成功・entries 更新 |
  | **新規ファイルでの末端追加** | 新規末端 + Use | **なし** | ICE |
  | **中間 sealed ファイルの単独編集**（3 段チェーン） | Mid2 + Leaf | **なし** | ICE |
  | チェーンの kind のファイルの編集 | Csi + Leaf + Mid1 + Mid2 | あり | 成功 |
  | 新規ファイル + 既存 kind ファイルの同時編集 | 末端 3 + 新規末端 + Si + Use | あり | 成功・entries 更新 |

  共連れが成立するのは**編集したファイルが既存 kind を宣言している場合に限る**。これは言語側の保証ではなく、
  基底ファイルの生成物（`$EntriesHolder.createEntries`）が各 kind を参照することで生じた依存辺の効果であり、
  プラグイン非適用の同形では末端ファイルのコメント編集は当該ファイル単独の 1 ラウンドで終わる。新規末端は前ビルドの
  参照グラフに無く、中間 sealed は生成物から参照されないため、いずれも基底を dirty にしない。
  Gradle 側のビルドレポートの `Compile iteration` は理由が付いた dirty ファイルのみを列挙し、実コンパイル対象とは
  一致しない（上表 1・2 行目はレポート上は 2 ファイルだが、実ラウンドは基底を含む 5 ファイル）。
- **実測（NG。基底不在ラウンドで同時に起きること）**:
  1. ボディ未充填のバックエンド ICE（再試行でも持続・**clean ビルドで回復**）。
  2. entries は基底ファイル帰属の `$EntriesHolder` へ `listOf(...)` として焼かれるため、このラウンドでは
     再生成されない（更新は「基底がラウンドに入ること」が必要十分）。
  3. kind-when の網羅性が前ラウンドのメタデータ由来の継承者一覧で判定され、新規末端の枝が無くても通る
     （同一ソースの clean は `'when' expression must be exhaustive. Add the 'Baz' branch` を報告する）。
  4. 同一ラウンドで追加した同名末端どうしの ENUMIZE_LABEL_CLASH が発火しない（clean は両末端へ報告する）。
     label 索引を同じ継承者一覧から張るためであり、既存末端との衝突は相手が索引に載っているため従来どおり発火する。
  - 失敗ラウンドは出力を一切書かない（全生成物が編集前とバイト一致・新規末端の .class も未生成）ため、
    2〜4 が成果物へ出ることは現状では無い。ICE が 2〜4 を巻き取っている。
- **修正方針案**:
  1. **プラグイン側（本項の解決手段）**: IR 側のエントリポイントを origin 駆動へ改める。module fragment を走査し、
     `GeneratedByPlugin(EnumizeKey)` の宣言のうち末端側のものは基底不在ラウンドでも充填する。EntriesHolder と
     生成 companion の委譲は基底が同席するラウンドでのみ生成し（P1 は保つ）、新規末端の entries への反映は
     後続ラウンドでの基底再コンパイルに委ねる。**合否条件は「ICE が出ないこと」ではなく「最終成果物の
     entries・valueOf・kind-when 診断・LABEL_CLASH が clean ビルドと一致すること」**とする（上記 2〜4 が残ると
     ICE は沈黙の不正ビルドへ変わる）。後続ラウンドで基底が dirty になること自体はプラグイン非適用の同形で
     実測しているが、適用時は初回ラウンドで ICE になるため未確認であり、修正と同時に実測する。
  2. **文書**: 設計00 §1・§5（階層不変条件と P1 の前提）は本項の実測へ改めた。設計01 §8・設計02 §2・§5 の
     「同一ラウンドで再生成される」記述も限定付きへ改めた。概要 §7 の回避策は「基底ファイルと同時に保存する」
     だけでなく「同じ階層の**既存 kind を宣言するファイル**を一緒に保存する」でも足りる。
     `Kt86121Test` とテストケース管理の「KT-86121 型」という名称は別事象を指すため、修正と同時に改名する。
- **関連**: 新規ファイルで追加した末端が**既存の**末端と label 衝突する場合は、フロントエンドの
  ENUMIZE_LABEL_CLASH（末端側チェッカー）が先にコンパイルを止めるため本 ICE には到達しない（実測）。
  本項の再現形は、追加した末端が既存の階層と衝突しない場合に限られる。
- **テスト側の暫定対応**: 仕様どおりのアサートを持つ 2 メソッド（TC-IC-011・TC-IC-060/025）を `@Disabled` 化し、
  `Kt86121Test` が両形の ICE を expected として固定する（修正で通らなくなったときにテストが fail して検出できる）。
  stale ビュー由来の 3・4 を固定するゲートは未整備。

## 17. 生成型への typealias を基底の supertype の頭に使うとバックエンド ICE になる（配置依存）

- **仕様（期待）**: 設計01 §4・§6.2 — 型引数まで一致する `Enumized<SI.Enumish>` の手動宣言は注入を
  スキップし、supertype の表記で扱いを変えない。テストケース管理.md TC-MAN-085。
- **実測（NG）**: `typealias A = Enumized<SI.Enumish>` を介した `@Enumize sealed interface SI : A` が、
  エイリアスが階層より先に解決されない配置（**階層と同一ファイル**・**ソース処理順で後になる別ファイル**）で
  `Backend Internal error: Exception during IR fake override builder`
  （`IllegalArgumentException`。フロントエンド診断は一切出ない）になる。
  エイリアスが先に処理される別ファイル配置（TC-MAN-081）は成立する。
- **原因（実測で切り分け済み）**: typealias の展開先が**プラグイン生成型**（`SI.Enumish`）である場合、
  エイリアスが階層より先に解決されない配置では、解決済み supertype がエイリアスのまま据え置かれ
  `fullyExpandedType` でも展開できない。プラグイン側の注入抑止は raw 追跡（エイリアス自身のスコープでの
  名前解決）へ落として配置に依らず成立しており、二重注入は起きない。残るのは未展開のまま IR へ渡る
  言語側の経路である。生成型を介さない同型（`typealias A = Box<S.Nested>` + `sealed interface S : A`）は
  プラグイン非適用なら同一ファイルでも正常にコンパイルされるため、生成型との組み合わせに固有である。
- **修正方針案**: プラグイン側で塞ぐ手段は無い（注入は既に抑止済みで、未展開の supertype を
  IR へ渡すのは言語側）。専用診断（この配置を検出して報告する）を設ける案はあるが、言語側の制約に対して
  診断カタログを増やす価値は低い。回避策（**基底の supertype の頭にはエイリアスを使わない** —
  型引数としての使用と末端側での使用は配置に依らず成立する）は概要 §7 に既知の制限として記載済みであり、
  本項は言語側の解消をもって欠番化する。
- **テスト側の暫定対応**: 仕様どおりのアサートは `@Disabled` で保持し、実挙動（ICE）を固定する
  回帰ゲートを併置する（SweepTypealiasSupertypeTest。解消したらゲートが fail して検出できる）。
