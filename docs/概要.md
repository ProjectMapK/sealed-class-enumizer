# sealed-class-enumizer 概要

`sealed class` / `sealed interface` に対して、`enum class` と同等の操作系 API（`entries` / `valueOf` / `label`
など）をコンパイル時に生成する Kotlin (K2) コンパイラプラグインである。

設計原則:

- 位置づけは「enum の代替」ではなく「**sealed 階層に enum の操作系 API を後付けする**」ものである
- ランタイムでの reflection は一切使用しない（`kotlin-reflect` 不要・`Class.forName` 等も不使用）
- Kotlin Multiplatform 対応（JVM / JS / Native / Wasm）。**プラットフォームで挙動が割れる API は表に出さない**（§3）
- インクリメンタルコンパイル（IC）において、基底と継承者のファイルが分かれていて片方だけが編集された場合でも壊れないこと
  を、設計の一級要件とする。継承者の集合に依存する生成物を基底ファイルへ帰属させ、
  それ以外は宣言自身だけで組めるようにすることで満たしている。
  方針と実測の詳細は [設計00 の IC 設計](コンパイラプラグイン設計00.md) を参照
- enum 的意味論（entries の完全性・label の一意性・kind の一意対応）はチェッカーで守り、
  表示（`toString`）のカスタマイズは常に利用側に開く（§4・§8）
- 継承者の列挙・順序はコンパイラが提供するものをそのまま用い、プラグイン独自の解釈や並べ替えを挟まない（§5）

言語側にも「reflection なしで sealed のサブクラスを列挙したい」という要望（KT-25871、Open）が長年存在する。  
`KClass.sealedSubclasses` は JVM 専用であり、kotlin-reflect を必須とし R8 で壊れるため、MPP や Android
では実用にならない。  
本プラグインはこの空白をコンパイル時の生成で埋める。

## 1. 使用イメージ

```kotlin
package io.github.projectmapk

import io.github.projectmapk.sealedClassEnumizer.Enumize

@Enumize
sealed interface SI {
    data class Foo(val v: Int) : SI
    data object Bar : SI
}
```

`@Enumize` を付けるだけで、以下の API が使えるようになる。

```kotlin
// enum の entries / valueOf 相当（kind = 「末端 1 種類につき 1 つのシングルトン」）
val kinds: List<SI.Enumish> = SI.Enumish.entries        // [Bar, Foo]（コンパイラが提供する継承者順。§5）
val foo: SI.Enumish = SI.Enumish.valueOf("Foo")         // 不一致は IllegalArgumentException
val orNull: SI.Enumish? = SI.Enumish.valueOfOrNull("X") // null 返却版（enum に無い追加）

// 値から kind へ
val si: SI = SI.Foo(42)
val kind: SI.Enumish = si.asEnumish()   // Foo の kind（= Foo.Companion）
si.label    // "Foo"（拡張プロパティ。enum の name 相当）
kind.enumizedClass    // SI.Foo::class（kind に対応する末端の KClass。§2）

// kind 単位の網羅 when（生成 Enumish は sealed であり else 不要。§3 参照）
when (si.asEnumish()) {
    SI.Foo -> println("Foo という種類") // 末端 class の kind は companion（短縮形で名指しする。明示形は SI.Foo.Companion ->。§6）
    SI.Bar -> println("Bar という種類")
}
```

> **`ordinal` 相当と `Comparable` は提供しない**。  
> 序数は宣言順ではなくコンパイラが提供する継承者順に従い、改名で変動する。  
> 永続化に使えない値を API 表面に置く弊害が利得を上回るためである（詳細は §4・§5）。

### 生成物の概念形

プラグインが生成するコードを Kotlin ソース相当で書き下すと以下になる（実際は FIR/IR 上の生成であり、
このソースが出力されるわけではない）。

```kotlin
sealed interface SI : Enumized<SI.Enumish> {
    // enum 定数の型に相当する sealed interface。操作系 API（entries / valueOf）を基底の companion に
    // 継承で載せる形は、利用側 companion の可視性（private 等）が生成 API を制限するため採らず、
    // 専用のネスト宣言として個別に生成する
    sealed interface Enumish : io.github.projectmapk.sealedClassEnumizer.Enumish {

        // 基底の宣言（EnumishCompanion<Enumish>）を具体型へ共変 override する
        override val enumishCompanion: Companion get() = Companion

        // 基底の宣言（KClass<out Enumized<*>>）を階層の型へ共変 override する（実装は各 kind が持つ）
        override val enumizedClass: KClass<out SI>

        companion object : io.github.projectmapk.sealedClassEnumizer.EnumishCompanion<Enumish> {
            // entries の保持と探索は EntriesHolder（= EnumishEntriesHolder の実装。§2）に委譲する
            override val entries: List<Enumish> get() = EntriesHolder.entries
            override fun valueOf(value: String): Enumish = EntriesHolder.getByLabel(value)
            override fun valueOfOrNull(value: String): Enumish? = EntriesHolder.getByLabelOrNull(value)
        }

        // 実体は IR のみで生成されるオブジェクト（メタデータに載らないため Kotlin ソースからは不可視・ABI 保証外）
        // object EntriesHolder : EnumishEntriesHolder<Enumish>() {
        //     override val enumizedRootClass: KClass<SI> get() = SI::class
        //     override fun createEntries(): List<Enumish> = listOf(Bar, Foo.Companion)  // コンパイラ提供順（§5）
        // }
    }

    data class Foo(val v: Int) : SI {
        override fun asEnumish(): Companion = Companion

        companion object : Enumish {
            override val label: String get() = "Foo"
            override val enumizedClass: KClass<Foo> get() = Foo::class
            override fun toString(): String = label
        }
    }

    data object Bar : SI, Enumish {
        override fun asEnumish(): Bar = this
        override val label: String get() = "Bar"
        override val enumizedClass: KClass<Bar> get() = Bar::class
        // data object の toString は言語による合成実装が既に在るため生成しない（§4 原則 1）
    }
}
```

### enum が sealed interface を継承しているケース

enum class は sealed interface の継承者になれる。本プラグインはこれを一級ケースとして扱う。

```kotlin
@Enumize
sealed interface Command {
    data class Custom(val raw: String) : Command
    enum class Builtin : Command { HELP, VERSION }   // enum が sealed interface を継承
}

Command.Enumish.entries          // enum 全体で 1 kind（定数毎には展開しない）。順序はコンパイラ提供順（§5）
Command.Enumish.entries.map { it.label }  // ["Builtin", "Custom"]
Command.Builtin.HELP.name        // "HELP"    ← enum 本来の name（final メンバー）
Command.Builtin.HELP.label       // "Builtin" ← kind の label（Enumized 拡張プロパティ）
```

kind の粒度は「`when (command)` の網羅性の枝」（= sealed の直和の枝を末端まで展開したもの）に一致させており、enum
は全体で 1 kind になる。  
enum 定数 1 つずつを kind 化する展開は提供しない（設計判断） — 展開すると kind と when
の枝が 1 対 1 でなくなり、粒度の一致という前提が崩れるためである。

基底 API が `label` という名前を使うのは、この構成で enum 定数の final メンバー `Enum.name` に横取り・
シャドーイングされないためである（§4）。  
末端 enum への生成内容は普通の末端 class と同一である — `asEnumish()`（末端本体）と、companion（= kind）への `label` /
`enumizedClass` / `toString`（`toString` の生成の有無は §4 の 2 原則に従う）。

## 2. runtime-api

生成コードが依存する基盤 API は `runtime-api` モジュールとして配布する（reflection 非依存・MPP 対応）。  
宣言の実体と宣言毎の制約コメントは `runtime-api` のソースを正とし、ここでは役割と設計判断のみを示す。

| 宣言 | 役割 |
|---|---|
| `@Enumize(labelCase = PROJECT_DEFAULT)` | 生成対象の指定。`labelCase` は階層の label ケース指定（§4） |
| `@EnumishLabel(value)` | 末端の label の明示指定（§4）。ケース変換は適用されない |
| `LabelCase` | label のケース指定の enum（§4）。`PROJECT_DEFAULT` はプロジェクト既定（未設定時は `AS_DECLARED`）の読み込み |
| `Enumish` | kind の基底 interface。`label`（enum の `name` 相当）/ `enumishCompanion` / `enumizedClass` を宣言する |
| `EnumishCompanion<out T : Enumish>` | 操作系 API（`entries` / `valueOf` / `valueOfOrNull`）。生成 Enumish の companion が実装する |
| `Enumized<out T : Enumish>` | 値側の基底 interface。`asEnumish()` を宣言する |
| `Enumized<T>.label`（拡張プロパティ） | `asEnumish().label` の短縮（コード生成不要）。enum の `name` と併存できる命名（§4） |
| `EnumishEntriesHolder<T : Enumish>` | 各階層の EntriesHolder（プラグイン生成）の基底 abstract class。entries の遅延構築と `getByLabel` / `getByLabelOrNull` を提供し、生成側は supertype の型引数・`enumizedRootClass` の実装・`createEntries()` の実装の 3 つだけを担う |

設計メモ:

- `Retention` は `BINARY`。「ランタイム reflection に依存しない」ことの明示であり（`RUNTIME` にしない）、`SOURCE`
  にしないのはビルドツールや将来の keep ルールとの連携のためである。
- `Enumish` / `Enumized` が abstract class でなく interface であるのは sealed 階層に継承させるためである
  （sealed 階層に属さない `EnumishEntriesHolder` はこの制約の対象外）。
- `enumishCompanion` は「値から階層全体（entries）へ辿る」ための唯一の reflection レスな手段である（機能としては Java
  Enum の `getDeclaringClass` に対応）。  
  基底では `EnumishCompanion<Enumish>` と宣言し、生成 Enumish 側が具体型（`SI.Enumish.Companion`）へ**共変 override**
  するため、静的型が `SI.Enumish` なら `enumishCompanion.entries` は `List<SI.Enumish>` として型付く。  
  宣言側共変（`out T`）により、複数階層の Companion を `List<EnumishCompanion<Enumish>>` として射影なしで束ねられる。  
  `declaringCompanion` を名乗らないのは、本設計の kind が Companion に宣言されない（宣言されるのは各末端である）うえ、
  companion にとって「宣言元」は慣習的に外側クラスを指し誤読を誘うためで、
  名前は「この kind の（生成）Enumish の companion object」そのものを返すことによる。
- `enumizedClass` は kind に対応する末端の class リテラル（`Foo::class`）を返す。  
  kind を reflection 系ライブラリ（kotlin-reflect・serialization・DI 等）と接続する用途のためで、runtime-api 自身は
  class リテラルを保持するだけであり reflection を使わない。  
  命名は Enumized（値側）↔ Enumish（kind 側）の双対に基づく（内部用語「末端」は公開 API 名に出さない）。  
  基底の `KClass<out Enumized<*>>` を生成 Enumish が `KClass<out SI>` へ、各 kind が `KClass<Foo>` へと共変 override
  するため、`entries.map { it.enumizedClass }` は `List<KClass<out SI>>` として型付く。  
  非 final な末端（§3）では分類の代表である末端自身を返す — 値の実行時クラスとは一致しない場合がある
- `EnumishCompanion` を `Enumish` にネストしないのは、ネストして単純名を `Companion` にすると生成 `SI.Enumish`
  のスコープでその companion object 自身と曖昧化するためである。  
  名前は、これを実装する生成側の companion object に由来する。
- `Enumish` は `toString` を宣言しない。  
  interface での抽象再宣言は `Any` の実装では充足されず（実測）、§4 原則 2 の保証の下では充足の成立条件を増やすだけで
  利点が無い。  
  kind の `toString` が label を返すのは、interface の要求ではなく生成側の実装による（§4）
- `EnumishEntriesHolder` はコンストラクタ引数を持たず、基底の識別は `enumizedRootClass`（生成側が基底の class
  リテラルを返す）で行う — 生成側の super 呼び出しが no-arg で済む。  
  名前は Enumized 階層の根（= `@Enumize` の基底）を指し、`enumizedClass`（末端側）とは Root の有無で区別する。  
  class リテラルと `KClass.simpleName` は stdlib の機能であり kotlin-reflect を要しない（`qualifiedName` は JS
  等のプラットフォームで利用できないため使わない）
- `getByLabel` の失敗メッセージは `No enumish entry with label 'X' in SI` 形式である。  
  enum の `No enum constant FQN.NAME` は定数が enum クラスの内側に宣言されている前提の表記だが、sealed
  の末端は基底の内側に宣言されるとは限らないため、宣言位置を示唆しない事実の記述にする

> `EnumishEntriesHolder` の挙動: `entries` は初回アクセス時に一度だけ構築され、以降は同じインスタンスを返す。  
> `getByLabel` / `getByLabelOrNull` は `entries` の線形走査で label が完全一致する最初の要素を返す
> （一意性はチェッカー `ENUMIZE_LABEL_CLASH` = §8 が保証する）。

> 注意（シャドーイング）: Kotlin ではメンバーが拡張より常に優先されるため、
> 階層のメンバーが `label` という同名プロパティを持つ場合（例: `data class Tagged(val label: String) : SI`。supertype
> から継承したものも同じ）、拡張プロパティは黙って隠され、`x.label` はユーザープロパティを返す。  
> **確実に kind の値を得るには `asEnumish().label` を使う**こと。  
> この構成にはチェッカーが警告（`ENUMIZE_EXTENSION_SHADOWED`）を出す。

## 3. enum 機能との対応カタログ

◎ = 同等以上 / ○ = 生成で同等相当 / △ = 制限付き / ×（設計）= 実現手段はあるが設計判断で提供しない /
×（不可）= 言語・実行環境の制約により原理的に実現できない（`A/B` は「対象・構成により A または B」。
本節が「enum と同じにできない部分」の文書化を兼ねる）

| enum の機能 | 可否 | 本プラグインでの姿 |
|---|---|---|
| `entries` | ○ | `SI.Enumish.entries`（`List<T>`。毎回同じインスタンスを返す。`kotlin.enums.EnumEntries` は `E : Enum<E>` という境界を持つため型として使えず、`List<T>` で公開する） |
| `values()` | ○ | `entries` に一本化（enum 側も KT-48872 で entries へ移行済みである） |
| `valueOf(name)` | ○ | `SI.Enumish.valueOf(label)`。加えて `valueOfOrNull`（enum に無い追加） |
| `name` | ○ | `label`（命名理由は §4） |
| `ordinal` | ×（設計） | **提供しない**（設計判断。§4）。序数が必要な場合は `entries.indexOf(kind)` で得られるが、その値は改名で変動し永続化に使えない（§5） |
| `compareTo`（ordinal 順） | ×（設計） | **提供しない**（`ordinal` 相当を持たないため。§4）。並べ替えが必要な場合は `sortedBy { it.label }` 等、意味の明確な基準を利用側で選ぶ（`entries` の並びは公式な保証の無いコンパイラ提供順であり、改名や階層の入れ子の変更で変動する。§5） |
| `getDeclaringClass` | ○ | `enumishCompanion`（値から階層の Companion へ。「declaring」を名乗らない理由は §2） |
| reified `enumValueOf<T>()` / `enumEntries<T>()` | ×（設計） | **提供しない**（設計判断。理由は下記）。代替は `SI.Enumish.entries` / `SI.Enumish.valueOf(...)` の直接記述である |
| `toString() = name` | ○/△ | 明示的な `toString` 実装（手動宣言・継承・data object の合成）があればそれを尊重し、無ければ `toString() = label` を必ず生成する（末端 enum の kind = companion も同様）。**kind が明示実装なしに `Any` の既定表示へ落ちる構成は許容しない**（§4） |
| 網羅的 `when` | ◎/△ | 値単位の when は sealed の地力で型による網羅性検査とスマートキャストが効く（enum を超える）。kind 単位の when（`when (x.asEnumish())`）は生成 Enumish が sealed のため else 不要（全 kind が呼び出し側から可視の場合に限る。Enumish の手動実装（§8 の許容 = 階層内）がある場合はその枝も必要） |
| `hashCode` / `equals` / 同一性 | ○ | kind は object / companion のシングルトンなので参照同一性が成立する（Java の直列化を経ると壊れる。下記） |
| Java シリアライズ（`java.io.Serializable`） | ×（不可） | enum は直列化プロトコルがシングルトン性を保証するが、kind は `Serializable` でなく、手動で対応しても `readResolve` なしでは復元後の同一性（when の等値枝の前提）が壊れる |
| Java からの利用 | △ | `@JvmStatic` を付与しないため、Java からは interface 上に公開される static フィールド `Companion` を経由して `SI.Enumish.Companion.getEntries()` / `.valueOf(...)` / `.valueOfOrNull(...)` を呼ぶ（`entries` はプロパティなので Java では `getEntries()` になる）。`@JvmStatic` による `SI.Enumish.getEntries()` 形の static アクセスは**提供できない** — 生成メンバーは `EnumishCompanion` の override であり、Kotlin は override への `@JvmStatic` を禁止しているためである（設計00 §4.1）。古典的な enum の `switch` は使えない |
| Java 側の網羅 `switch` | ○ | jvmTarget 17+ では sealed に `PermittedSubclasses` 属性が出力され、Java 21 のパターンマッチング switch で網羅性が効く |
| リフレクション連携 | ○ | `KClass.sealedSubclasses` 等の言語標準の機構はそのまま使える（JVM + kotlin-reflect 限定・プラグイン関与なし）。ただし `entries` は中間 sealed を末端まで展開するため、**中間 sealed がある階層では `sealedSubclasses` と要素の集合も並びも一致しない**（§5）。kind からは `enumizedClass` で末端の `KClass` を得られ、reflection 系ライブラリとの接続点になる（§2） |
| kotlinx.serialization | △ | 自動では効かない。label ベースの `KSerializer` を利用側で書く（`@Serializable sealed` の既定であるポリモーフィック形式とはワイヤ形状が異なる点に注意） |
| Jackson / Gson / Moshi 等 | △ | 各フレームワークは `java.lang.Enum` を特別扱いするため自動では効かない。label ベースのカスタムシリアライザを利用側で書く |
| ORM（Exposed / JPA） | △ | `Enum<T>` 境界の API（`enumerationByName` 等）は使えない。label ベースのカスタムマッピングのレシピを文書で提供する |
| Compose 安定性 | ○ | kind はシングルトンの object であり、stable 推論と相性が良い |

### reified ヘルパを提供しない理由

`enumishEntries<T>()` / `enumishValueOf<T>()` のような reified ヘルパは提供しない。  
reflection を使わない実現手段では、**MPP のプラットフォーム間で挙動を揃えられない**ためである。

reflection なしの実現手段は、コンパイラが呼び出し点を Companion への直接参照に書き換える intrinsic 方式しかない。  
この書き換えを全経路で保証できるのは JVM（公開拡張点 `JvmIrIntrinsicExtension`）だけである。  
klib（JS / Native / Wasm）では公式実装（`kotlin.enums.enumEntries`）が**すべてのインライン展開の後**の lowering
で置換しているのに対し、プラグインが立てられる `IrGenerationExtension` はあらゆる展開より**前**にしか位置せず、
コンパイラ本体も intrinsic のサポートを JVM のみと明記している — 工夫で埋められない**構造的な制約**である。  
帰結として、ヘルパを自前の `inline` 関数で包む自然な使い方が「JVM では動くが klib
では実行時例外」というプラットフォームで挙動が割れる API になり、ランタイム reflection を禁じる本プロジェクトには
kotlinx.serialization のようなランタイム解決へのフォールバックも無い。

一方で、ヘルパが無くて困る場面はほとんど無い —
`enumishEntries<T>()` と書ける状況では `T` が静的に判っており、`SI.Enumish.entries` と直接書けば済む。  
このため設計は reified ヘルパに関わる構成要素（runtime-api のヘルパ・IR の intrinsic 書き換え・専用の診断）を持たない。

### 末端は非 final でもよい（拡張点を開いたまま使える）

sealed でない継承者はすべて末端として扱う。  
**final なクラスや object だけでなく、open class / abstract class / interface / fun interface も末端になり、通常どおり生成の対象となる**。  
末端 fun interface では生成される `asEnumish` が default 実装になるため SAM の抽象メソッドは 1 つに保たれ、
ラムダによる SAM 変換もそのまま使える。

```kotlin
@Enumize
sealed interface Shape {
    data class Circle(val r: Double) : Shape          // 末端（final）
    abstract class Polygon : Shape                    // 末端（abstract）— 拡張点として開いておく
    interface Custom : Shape                          // 末端（interface）— 第三者が実装できる
}

Shape.Enumish.entries   // [Circle, Custom, Polygon] — 末端の数だけ。サブタイプでは増えない
```

**階層外にサブタイプをいくつ作っても entries は変わらない**のが要点である。  
`class Triangle : Shape.Polygon()` を別モジュールで定義しても、`Triangle` は新しい kind を作らず、`asEnumish()` の実装を
`Polygon` から継承して **`Polygon` の kind に吸収される**。

```kotlin
val t: Shape = Triangle()
t.asEnumish()   // Shape.Polygon.Companion
t.label         // "Polygon"
```

値単位の `when` の網羅性も、`is Polygon ->` の枝がサブタイプをすべて覆うため成立する。  
つまり「分類の粒度は固定したまま、各分類の実装は開いておく」という設計が素直に書ける。

制約は 1 つだけで、**ある型が 2 つ以上の末端のサブタイプになってはならない**（どの kind
に対応するか決まらないため。§8）。  
なお階層外で複数の末端 interface を実装した場合は、`asEnumish()`
の戻り値型が両立しないため言語側でもコンパイルが通らない。

### enum に対する優位点

- エントリーがデータを持てる（`data class` 継承者 = パラメタライズドなバリアント）
- 値単位の網羅 when + スマートキャスト
- 多段の分類が可能（中間 sealed によるグルーピング）
- **末端を非 final にでき、分類を固定したまま実装を開けておける**（上記。enum には無い自由度）
- Java 21 のパターンマッチングとの親和性
- companion 単位の拡張性（kind に対して拡張関数を生やせる）

## 4. label という命名の理由と、ordinal 相当を提供しない理由

### label（name にしない理由）

enum class が階層の末端になるケース（§1 の `Builtin`）では、enum 定数は `Enum.name`
を**final メンバー**として持っている。  
基底 API が `name` を名乗ると:

1. メンバーによる暗黙の充足 — 階層側に抽象プロパティ `name` を宣言してもコンパイルエラーにはならず、enum 末端では final
   メンバー `Enum.name` がその実装として**黙って採用される**（実測）。  
   kind の label であるべきところに定数名（`"HELP"`）が返り、final のため override で正すこともできない
2. 拡張シャドーイング — 拡張プロパティ `name` を用意しても、enum 定数上ではメンバー `Enum.name`
   が優先され、**静的型によって返る値が変わる**静かな罠になる

`label` はこの罠を構造的に回避する命名であり、ケース変換等、表示用のカスタマイズを受ける名前としても適する。  
ただし `label` もドメインモデルで頻出の名前であり、ユーザー側のメンバーによる拡張シャドーイング（§2
の注意）のリスクは残る。  
これはチェッカー警告と「確実な取得は `asEnumish()` 経由」という規約で対処する。

### ordinal 相当と Comparable を提供しない理由

enum の `ordinal` に相当するプロパティと、それに基づく `Comparable` は**提供しない**。  
アプリケーション上の意義が薄く、弊害の方が大きいためである。

- sealed 階層の序数は enum のように「宣言順」で定まらない。  
  コンパイラが提供する継承者順（§5）に従うほかなく、**末端や外側クラスの改名で値が変動する**
- したがって永続化にも通信にも使えず、「使ってはならない値」を API 表面に置くことになる
- `Comparable` は序数の存在が前提である（enum の `compareTo` は ordinal 比較）。  
  序数を持たない以上「何順で比較するのか」の自然な答えが無いため、併せて提供しない。  
  並べ替えが必要な場合は `sortedBy { it.label }` のように**意味の明確な基準を利用側が選ぶ**方が健全である

### toString について

kind の `toString` は次の 2 原則で扱う。

1. **表示のカスタマイズは常に利用側が勝つ**: 明示的な `toString` 実装を持つ kind に、プラグインは何もしない。  
   `toString` は表示専用であり、変えても `entries` / `valueOf` / `asEnumish` の整合性には影響しないため、
   手動定義をチェッカーの禁止対象にもしていない（§8。`Any` のメンバーである以上どのクラスでも override でき、
   言語仕様上これを禁じる手段も無い）
2. **`Any` の既定表示を許容しない**: 明示的な実装を持たない kind には、
   プラグインが `label` を返す `toString` を **必ず override 生成する**（kind が companion object の場合も末端 object
   の場合も同様）。  
   kind の表示が明示実装なしに `クラス名@ハッシュ` 形式（`Any` の既定実装）へ落ちる構成は存在させない

「明示的な `toString` 実装がある」と見なし、原則 1 により生成しないのは次の 3 ケースである。

- **kind 自身の手動宣言**: ユーザー定義をそのまま採用する
- **継承経路上の `Any` 以外の具象 `toString`**: 生成すると override してしまい、利用側が意図した表示を潰す
- **末端 data object**: 言語が単純名を返す `toString` を自動合成しており、この合成実装の存在が理由である。  
  label のケース変換・明示指定（下記）で label と単純名が一致しない場合も生成せず、言語合成の単純名のままとする

**末端 enum class の kind（= その companion）も特別扱いせず**上記の 2 原則で判定する（通常は `toString() = label`
が生成される）。  
enum 定数側の表示（`Enum.toString()`）と kind 側の表示は管轄の異なる別物として併存する（例: 定数は
`"HELP"`、kind は `"Builtin"`）。  
原則 2 の保証は網羅的である — どの kind にも手動宣言・継承実装・data object の合成・生成の label
のいずれかが必ず具象実装として存在する。

kind の supertype が `toString` を**抽象として再宣言**している場合（interface での抽象再宣言は `Any` の実装では
充足されない。§2）、生成はこの要求の充足には使えず、kind 側に手動実装が必要である（無ければ言語の
「抽象メンバー未実装」エラーになる）。

確実に label を得たい場合は、いずれのケースでも `toString` ではなく `label` を参照すること。

### label のカスタマイズ

label は次の優先順位で決まる（詳細は [エッジケースへの対応方針](エッジケースへの対応方針.md) §3）。

1. **明示指定** — 末端宣言への `@EnumishLabel("...")`。ケース変換は適用されず、この値がそのまま最終 label になる。  
   衝突の解消と、末端の改名時に旧名を与えて永続化済み label との互換を保つ用途に使う
2. **階層個別のケース変換** — `@Enumize(labelCase = LabelCase.UPPER_SNAKE_CASE)` のような具体指定
3. **プロジェクト既定** — compiler-plugin のオプション `labelCase`。  
   gradle-plugin は DSL の `sealedClassEnumizer { labelCase = ... }` を常に具体値でこのオプションへ伝達する。  
   `@Enumize` の `labelCase` の既定値 `PROJECT_DEFAULT` はこの設定を読む指定である
4. **組み込み既定** — オプション欠落時（gradle-plugin を経ないビルド）は `AS_DECLARED`（無変換）

`LabelCase` の具体ケースは `AS_DECLARED`（無変換）/ `UPPER_SNAKE_CASE`（`FooBar` → `FOO_BAR`）/
`SNAKE_CASE`（`foo_bar`）/ `KEBAB_CASE`（`foo-bar`）。  
変換の単語分割は kotlinx.serialization の `JsonNamingStrategy` と同一で、大文字の連続は 1 語として保ち、
直後に小文字が続く場合のみ末尾 1 文字を次語の頭とする（`HTTPServer` → `HTTP_SERVER`）。  
判定はロケールに依存せず、**label は永続化対象のためリリース後に変換結果を変えない**。  
変換は全末端へ一律に適用される（enum 末端の kind・companion 自身が末端の場合の宣言名も同様）。  
衝突判定（`ENUMIZE_LABEL_CLASH`）は最終 label で行われ、変換で初めて衝突する単純名の組も検出される。  
kind の `toString` は label getter 経由のため自動で追随するが、data object の `toString` は言語合成（単純名）
のままであり（上記原則 1）、カスタマイズで label と表示が乖離しうる。確実な取得は label を参照すること。

### 将来拡張（v1 では非対応）

次は将来拡張であり、**v1 では非対応**である。

- 生成 Enumish への追加基底 interface の注入（プロパティ / 関数の追加用。生成メンバーの具体 override は許容しない。
  手動実装は v1 でも禁止されないため = §8、新たに加わるのは注入の自動化と全 kind への一括適用である）
- 手動 `Enumized<K>` 継承による基底指定の許容（[エッジケースへの対応方針](エッジケースへの対応方針.md) §2）

## 5. entries の順序

`entries` の順序は、**Kotlin コンパイラが sealed 継承者一覧として提供する順序**に合わせる。  
コンパイラは継承者一覧を **FQN（ClassId）文字列の序数昇順（大文字小文字を区別・ロケール非依存）に正規化**してメタデータ
へ直列化しており、`KClass.sealedSubclasses`（kotlin-reflect）や KSP が返す順序もこれである（実測エビデンスは
[設計00](コンパイラプラグイン設計00.md) §6.1）。

**プラグインは並べ替えに一切介入しない。** コンパイラが渡す継承者リストをそのまま使い、
中間 sealed に到達したらその継承者リストへ再帰的に降りる。  
この走査で現れた順序がそのまま `entries` になる。

- **中間 sealed が無い階層**では、`entries` はコンパイラが提供する順序そのもの、すなわち上記の FQN 序数順である。  
  末端がすべて基底にネストしている、またはすべてトップレベルにある構成なら、単純名（= 既定の label）の昇順と一致する
- **中間 sealed がある階層**では、中間の位置にその継承者が入れ子に展開されるた
  め、**全体としては FQN 序数順にならない場合がある**。  
  中間 sealed の継承者が中間の内側にネストしていない構成がこれにあたる:

  ```kotlin
  sealed interface SI
  sealed interface Mid : SI     // pkg/Mid
  object Aaa : Mid              // pkg/Aaa  ← Mid の内側ではなくトップレベル
  object Bbb : SI               // pkg/Bbb

  // SI の継承者は [Bbb, Mid] → Mid を展開して entries = [Bbb, Aaa]
  ```

  末端が中間 sealed の内側にネストしている通常の構成では、ネストした末端の FQN が中間の FQN を接頭辞に持つため、
  結果的に FQN 序数順と一致する

- **末端が複数の中間 sealed を同時に実装している場合**（`class C : Mid1, Mid2`）は、
  `entries` には**最初に到達した位置に 1 回だけ**現れる（kind は末端 1 種類につき 1 つである）

**性質（enum の宣言順との違い）**:

- **宣言順ではない**。宣言を並べ替えても `entries` の並びは変わらない
- 順序が変わるのは**末端（またはその外側クラス）の改名・追加・削除**、および階層の入れ子構造の変更のときである
- 中間 sealed を持つ階層では `sealedSubclasses` が直接の継承者（中間 sealed を含む）を返すのに対し `entries`
  は末端までフラット化するため、**要素の集合も並びも `sealedSubclasses` とは一致しない**（一致するのは中間 sealed
  が無い場合に限られる）

この正規化順はコンパイラの実装詳細であり**公式な保証は無い**（宣言順を提供してほしいという要望は、KSP 側で not-planned
としてクローズ済みである）。  
ただしこの正規化は継承者一覧を**属性へ格納する時点**で行われるため（設計00 §6.1）、`entries`
の並びも**ソースの配置（ファイル名・ファイル順・宣言位置）には依存しない**。  
本プラグインは (a) Kotlin のマイナーバージョン毎のアーティファクト分割（§7）、(b)
順序の回帰を検出する決定性テスト（設計00 §9）によってこれを受容する。  
**`entries` 上の位置（`indexOf` の値）を永続化に使ってはならない** — 改名で変動するためである。  
永続化には label または独自プロパティを使うこと。

## 6. 利用感の違い（enum からの読み替え）

| enum での操作 | 本プラグインでの操作 |
|---|---|
| `MyEnum.entries` | `SI.Enumish.entries`（`.Enumish` が 1 段挟まる） |
| `MyEnum.valueOf("A")` | `SI.Enumish.valueOf("A")` |
| `e.name` | `kind.label`（値からは `si.label` 拡張、または `si.asEnumish().label`） |
| `e.ordinal` | 対応物なし（§4）。必要なら `SI.Enumish.entries.indexOf(kind)`（永続化不可） |
| `e1 < e2` | 対応物なし（§4）。`sortedBy { it.label }` 等、意味の明確な基準を選ぶ |
| `when (e) { MyEnum.A -> }` | 値単位: `when (si) { is SI.Foo -> }` / kind 単位: `when (si.asEnumish()) { SI.Foo -> }`（companion 短縮形） |
| `Enum<*>`（任意の enum） | `Enumish`（任意の kind。複数階層の Companion は `EnumishCompanion<Enumish>` で束ねられる。§2） |

その他の体感差:

- **entries の並びは宣言順ではない**: 基本は名前（FQN）順で、
  中間 sealed がある階層では入れ子展開による例外がある（§5）。  
  enum の「上から順」の感覚は成立しないが、代わりにソースの配置（ファイル・宣言位置）に依存しない
- **エントリーの実体が 2 種類ある**: 末端 object は「値 = kind」だが、
  末端 class は「値（インスタンス多数）と kind（companion）が別物」。  
  `SI.Foo(42) != SI.Foo(43)` だが `SI.Foo(42).asEnumish() === SI.Foo(43).asEnumish()`
- **kind 単位の when における枝の書き方**: 末端 class の kind は companion 短縮形 `SI.Foo ->` で名指しする。  
  短縮形も網羅性の判定に算入され、明示形 `SI.Foo.Companion ->` と等価である。  
  名前つき companion（`companion object Factory`）では明示形が `SI.Foo.Factory ->` への追従を要するのに対し、
  短縮形は companion の宣言名に依存せず改名の影響を受けないため、短縮形を正典とする
- **kind 単位の when では値の型は絞り込まれない**: `when (si.asEnumish())` の分岐内でも `si` の静的型は元のままである。  
  Kotlin の contract は「特定のオブジェクトを返したらレシーバはこの型」という関係を表現できず（`returns()`
  に指定できるのは `true` / `false` / `null` のみ）、`asEnumish()` は override メンバーなのでそもそも contract
  を書けない（いずれも実測で確認）。  
  **値の型が必要な場合は値単位の `when (si)` を使う** — そちらは sealed の地力でスマートキャストが効く
- **初期化タイミング**: enum はクラスの静的初期化時に全定数が一括で初期化されるが、entries
  は初回アクセス時の遅延初期化である。  
  初回アクセスまで実行時異常が顕在化しない点が異なる
- **初期化再入の禁止**: kind（companion / 末端 object）の初期化子・init ブロックから階層の `entries` / `valueOf`
  を参照してはならない（遅延初期化の再入により、プラットフォームによって初期化子の二重実行・デッドロック・
  実行時異常などの未定義動作になりうる。JVM 実測では初期化子が二重実行される。enum のコンストラクタから `values()`
  に触れないのと同種の制約）
- **型パラメータ付き sealed も対象にできる**（enum は型パラメータを持てない）: `sealed class S<T>` に `@Enumize`
  を付与できる。  
  生成される `S.Enumish` は型パラメータを持たず、kind は `S<*>` の分類子である — 型引数は kind
  の同一性に影響しない（同じ末端のインスタンスであれば `Foo<Int>` でも `Foo<String>` でも同じ kind に分類される）
- **IDE**: IntelliJ の K2 モードはサードパーティ FIR プラグインをデフォルトでロードしない（KTIJ-29248）。  
  当面は「**CLI / Gradle ビルドは正しく通るが、エディタ上では生成 API が未解決表示になる**」という状態が既定の体験になる

  対応外の Kotlin への適用は gradle-plugin / maven-plugin が警告する（エラーにはしない。適用先の Kotlin
  版は、Gradle では KGP の版・Maven では kotlin-maven-plugin の版として読む）
- 階層（sealed 基底から末端までの範囲）は言語仕様上、同一パッケージ・同一モジュール・
  （MPP では）同一ソースセットに閉じる。  
  末端が非 final な場合、そのサブタイプは階層の外側にあってよい（別モジュールでもよい。§3）。  
  `@Enumize` を expect / actual 宣言に付与することは、v1 ではエラーとする（expect は actual
  毎に階層が変わりうるため。actual は生成物の注入 — supertype `Enumized<T>` やネスト宣言 `SI.Enumish` — が
  expect-actual マッチングと両立するか未検証のため）
- **対象はソースに書かれた宣言に限る**。  
  基底も継承者も、当該モジュールのソース上の宣言であることを前提とする。  
  **他のコンパイラプラグインが生成した宣言と組み合わせた場合の動作は v1 では未定義**である（本プラグインの判定・
  診断はフロントエンドで動くため、そこに存在しない宣言は観測できない。設計00 §1）
- 既知の制限: 生成 API（`SI.Enumish`）を参照する `typealias` を
  **`@Enumize` 基底の supertype の頭**（`sealed interface SI : A`）には使わない。  
  エイリアスが階層より先に解決されない配置（階層と同一ファイル・ソース処理順で後になる別ファイル）では、
  コンパイラがエイリアスを展開しないまま IR へ渡してバックエンドのエラーになる。  
  これは言語側の制約であり、プラグイン側で塞ぐ手段は無い。  
  型引数としての使用（`Enumized<A>`）と末端側の supertype での使用は配置に依らず成立する

### モジュールを跨いだ利用

- 生成 API（`SI.Enumish` とそのメンバー）は通常の宣言としてメタデータ / klib
  に載るため、**プラグインを適用していない利用側モジュールからも普通に参照できる**（プラグインが必要なのは生成する側だけ
  である）
- モジュールを跨いだ kind 単位の網羅 when（else 省略）は、生成 Enumish
  の継承者一覧のメタデータへの直列化により成立する（JVM のメタデータ・klib のいずれも確認済み）
- 末端の追加はライブラリの ABI 変更（sealed サブクラス一覧はメタデータの一部）として利用側の再コンパイルを正しく誘発し、
  未編集の利用側モジュールでも else 無しの kind 単位の網羅 when が網羅性エラーとして再検査される
- 旧バイナリと実行時にだけ組み合わさる場合も、entries は実行時に解決されるので「実行時に存在する版の集合」が返る（このた
  め entries アクセサは inline にしない）

## 8. 制限事項（チェッカーがエラーにする構成）

enum 的意味論（entries の完全性・label の一意性・kind の一意対応）を守るため、以下はコンパイルエラーとする。  
診断 ID と検査の詳細は [設計01](コンパイラプラグイン設計01.md) を参照。

| 構成 | 理由 |
|---|---|
| `@Enumize` を sealed class / sealed interface 以外（fun interface を含む）に付与 | 階層が定義できない |
| `@Enumize` を typealias / import 別名の表記で付与 | プラグインはエイリアス展開前に基底を認識する必要があり、この表記では生成が走らない（静かな非生成を許さずエラーにする。直接名または FQN で付与する） |
| `@Enumize` を expect / actual 宣言に付与 | expect: actual 毎に階層が変わりうる。actual: 生成物の注入（supertype・ネスト宣言）が expect-actual マッチングと両立するか未検証（いずれも v1 制限） |
| 1 つのクラスが 2 つ以上の `@Enumize` 階層に属する（入れ子・兄弟とも） | `Enumized<A>` / `Enumized<B>` を異なる型引数で二重に継承することになり、言語仕様違反になる |
| 階層内のある型が 2 つ以上の末端のサブタイプになる（例: `abstract class A : SI` と `class B : A(), SI`） | どちらの kind に対応するか一意に定まらない。階層外で複数の末端 interface を実装した場合も同様だが、そちらは言語側でもコンパイル不能になる |
| 末端が inner class | inner class は companion を持てない（言語制約） |
| 末端の可視性が基底より広く（sealed interface 階層で言語上成立する構成）、かつ companion の実効可視性が末端未満 | `asEnumish` の返り値型（companion の型・生成 Enumish へのフォールバックのいずれも）が露出エラー無しに書けない（[エッジケースへの対応方針](エッジケースへの対応方針.md) §1.3） |
| 階層の末端 class の companion が（別階層を含む）いずれかの `@Enumize` 階層の末端でもある | 同一オブジェクトに kind が二重対応してしまう |
| label（明示指定 > ケース変換 > 既定 = 末端宣言の単純名。**companion 自身が末端である場合に限り**その宣言名。§4）の重複。判定は最終 label で行われ、ケース変換で初めて衝突する組も含む | `valueOf` の解決が一意に定まらない。sealed の末端は同一パッケージ内の任意のクラスの中にネストできるため、enum と違って単純名の衝突が起こりうる。明示指定（`@EnumishLabel`）でも解消できる |
| `@EnumishLabel` の不正（空白のみの値・末端宣言以外 — 基底・中間 sealed・階層外・kind の companion — への付与） | label の由来は末端宣言に限る（§4） |
| 生成対象メンバーを**その生成先クラス**が手動宣言・継承している（kind = 末端 object / 末端の companion での `label` / `enumizedClass`、生成 Enumish での `enumishCompanion` / `enumizedClass`、その Companion での `entries` / `valueOf` / `valueOfOrNull`、末端での `asEnumish`） | 生成と衝突（`is Enumish` と言える supertype 宣言の重複だけなら許容）。※ `toString` は対象外（明示実装があれば生成せず利用側定義を採用する。§4）。※ 末端 class **自身**が `label` を持つ構成（宣言・継承のいずれでも）は、このエラーではなく下記の警告になる（生成先は companion のため） |
| 階層外のクラスが生成 Enumish を直接実装する | sealed の継承者一覧へ反映する経路が無く、一覧に無い実装は実行時拒否になる（kind 単位の網羅 when の健全性も壊れる）。階層内の手動実装は許容される（下記） |
| 型引数の異なる手動継承（`: Enumized<別の型>` 等） | 言語仕様違反（同一の総称インターフェースを異なる型引数で二重に継承すること）への合流を先回りして検出する |
| 基底に既存のネスト宣言 `Enumish` がある | 生成名と衝突 |

警告: 階層メンバーが `label` という可視メンバーを宣言または継承している場合（拡張シャドーイング。§2）。  
実害（`x.label` がユーザーのメンバーを返す）は継承由来でも同じに起きるため、継承のみの場合も警告し、
メッセージが宣言元を示す。  
kind（末端 object・companion）の `label` は生成物であり、継承した同名メンバーを override して kind
の値を返すため対象外である。  
改名できない継承由来の構成では `asEnumish().label` を使う。

なお、階層の継承者が別ソースセットに存在する構成もコンパイルエラーになるが、
これは**コンパイラ本体の診断に委ねる**（プラグインは補足診断を持たない）。  
別ソースセットの継承者は基底の sealed 継承者一覧に載らずプラグインからは観測できないうえ、
本体の言語エラーが sealed の同一モジュール制約を明示するためである。

許容: 基底 Enumish（runtime-api の `Enumish`）の手動実装は無制約である。  
生成 Enumish の手動実装は **階層内のもの（末端 class 自身による実装など）に限り許容**し、
階層外からの直接実装は継承者一覧へ反映する経路が無いため上表のとおりエラーにする。  
許容される手動実装で作られる値は kind ではないため entries に含まれず `valueOf` でも解決されない — enum 的 API
が保証する対象は kind に閉じており、手動実装はこの保証を壊さない。  
生成 Enumish は sealed で出荷されるため、手動実装は言語の sealed 制約（同一モジュール・
同一パッケージ）に従い、kind 単位の網羅 when にはその実装の枝も必要になる。  
手動実装の可視性は kind と同じ原則（下記「可視性は entries の掲載を妨げない」）に従う —
可視性の低い手動実装（internal 等）も許容され継承者一覧に載り、減衰するのは静的表現力のみである
（実装枝を名指しできない位置では kind 単位の when に else が要る）。

### 可視性は entries の掲載を妨げない

**基底自身の可視性も、個々の kind の可視性も、entries の掲載を妨げない。** `private` / `internal` な sealed 基底に
`@Enumize` を付けてよく、生成 API はその基底が見える範囲で通常どおりすべて使える。  
基底本体スコープから名前参照できない kind（private / protected な既存 companion・
別ファイルの private トップレベル末端・private 外側クラスにネストした末端）も、
プラグインが生成する **IR-only アクセサ**（メタデータ非搭載＝ABI 非追加。
外部ソースからは呼べず entries 構築コードからのみ呼ばれる。[設計02](コンパイラプラグイン設計02.md) §4.3）経由で entries
/ valueOf / label に載る。  
可視性で減衰するのは静的表現力（kind の名指し・網羅 when・IDE 補完）だけである。  
成立の理由・可視性が混在する階層（internal / private の末端・companion を含む構成）の帰結は
[エッジケースへの対応方針](エッジケースへの対応方針.md) §1 を参照。

## 9. 未検証範囲

生成方式（生成 API の形・kind の解決・entries / valueOf・toString・非 final 末端・enum 末端）は JVM で確定している。  
klib（JS / Native / Wasm）への直列化 — IR-only 生成物（EntriesHolder・kind の `toString`）と生成 Enumish の継承者一覧、
およびそれに基づく跨モジュールの網羅 when — も全 klib ターゲットで確定している。  
以下はまだ検証していない環境面であり、詳細と検証計画は [設計00](コンパイラプラグイン設計00.md) §10
と結合テスト（[テスト戦略](test/テスト戦略.md)・[保留](test/保留.md)）が扱う。

| 範囲 | 内容 |
|---|---|
| IC の環境マトリクス | 階層不変条件（sealed 階層の一括再コンパイル）が JVM + Gradle 以外（JPS / Maven）でも成り立つこと（MPP は Kotlin 側が既定で非 incremental のため、この条件を要さないことを実測済み）。Maven はプラグインの適用・オプション伝達・診断を実測済みであり、未検証なのは IC 面のみである。未検証の環境はサポート対象外と明記する |

（§6 の既定体験を既知の制限として受容する）。
