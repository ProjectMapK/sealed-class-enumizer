# sealed-class-enumizer 概要

`sealed class` / `sealed interface` に対して、`enum class` と同等の操作系 API（`entries` / `valueOf` /
`label` など）をコンパイル時に生成する Kotlin (K2) コンパイラプラグインである。

設計原則:

- 位置づけは「enum の代替」ではなく「**sealed 階層に enum の操作系 API を後付けする**」ものである
- ランタイムでの reflection は一切使用しない（`kotlin-reflect` 不要・`Class.forName` 等も不使用）
- Kotlin Multiplatform 対応（JVM / JS / Native / Wasm）。**プラットフォームで挙動が割れる API は表に出さない**（§3）
- インクリメンタルコンパイル（IC）において、基底と継承者のファイルが分かれていて片方だけが編集された場合でも壊れないことを、設計の一級要件とする。Kotlin コンパイラが sealed 階層を常に 1 単位で再コンパイルする性質に相乗りする形で設計しており、方針と実測の詳細は [設計00 の IC 設計](コンパイラプラグイン設計00.md) を参照
- enum 的意味論（entries の完全性・label の一意性・kind の一意対応）はチェッカーで守り、表示（`toString`）のカスタマイズは常に利用側に開く（§4・§8）
- 継承者の列挙・順序はコンパイラが提供するものをそのまま用い、プラグイン独自の解釈や並べ替えを挟まない（§5）

言語側にも「reflection なしで sealed のサブクラスを列挙したい」という要望（KT-25871、Open）が長年存在する。
`KClass.sealedSubclasses` は JVM 専用であり、kotlin-reflect を必須とし R8 で壊れるため、
MPP や Android では実用にならない。本プラグインはこの空白をコンパイル時の生成で埋める。

## 1. 使用イメージ

```kotlin
package org.wrongwrong

import io.github.projectmapk.sealedClassEnumizer.Enumize

@Enumize
sealed interface SI {
    data class Foo(val v: Int) : SI
    data object Bar : SI
}
```

`@Enumize` を付けるだけで、以下の API が使えるようになる。

```kotlin
// enum の entries / valueOf 相当（kind = 「末端 1 種類につき 1 つのシングルトン」）
val kinds: List<SI.Enumish> = SI.Enumish.entries        // [Bar, Foo]（コンパイラが提供する継承者順。§5）
val foo: SI.Enumish = SI.Enumish.valueOf("Foo")         // 不一致は IllegalArgumentException
val orNull: SI.Enumish? = SI.Enumish.valueOfOrNull("X") // null 返却版（enum に無い追加）

// 値から kind へ
val si: SI = SI.Foo(42)
val kind: SI.Enumish = si.asEnumish()   // Foo の kind（= Foo.Companion）
si.label    // "Foo"（拡張プロパティ。enum の name 相当）
kind.enumizedClass    // SI.Foo::class（kind に対応する末端の KClass。§2）

// kind 単位の網羅 when（生成 Enumish の sealed 化は未検証項目 V1。縮退時は else が必要。§3・§9 参照）
when (si.asEnumish()) {
    SI.Foo.Companion -> println("Foo という種類") // 短縮形 `SI.Foo ->` が使えるかは V1（§9）
    SI.Bar -> println("Bar という種類")
}
```

> **`ordinal` 相当と `Comparable` は提供しない**。sealed 階層では序数の意味づけが弱く
> （宣言順ではなくコンパイラが提供する継承者順に従い、改名で変動する）、アプリケーション上の利得よりも
> 「永続化してはならない値」を API 表面に置く弊害の方が大きいためである。詳細は §4・§5。

### 生成物の概念形

プラグインが生成するコードを Kotlin ソース相当で書き下すと以下になる（実際は FIR/IR 上の生成であり、
このソースが出力されるわけではない）。

```kotlin
sealed interface SI : Enumized<SI.Enumish> {
    // enum 定数の型に相当する sealed interface。操作系 API（entries / valueOf）を基底の companion に
    // 継承で載せる形は、利用側 companion の可視性（private 等）が生成 API を制限するため採らず、
    // 専用のネスト宣言として個別に生成する
    sealed interface Enumish : io.github.projectmapk.sealedClassEnumizer.Enumish {

        // 基底の宣言（Companion<Enumish>）を具体型へ共変 override する
        override val enumishCompanion: Companion get() = Companion

        // 基底の宣言（KClass<out Enumized<*>>）を階層の型へ共変 override する（実装は各 kind が持つ）
        override val enumizedClass: KClass<out SI>

        companion object : io.github.projectmapk.sealedClassEnumizer.Enumish.Companion<Enumish> {
            // entries の保持と探索は EntriesHolder（= EnumishEntriesHolder の実装。§2）に委譲する
            override val entries: List<Enumish> get() = EntriesHolder.entries
            override fun valueOf(value: String): Enumish = EntriesHolder.getByLabel(value)
            override fun valueOfOrNull(value: String): Enumish? = EntriesHolder.getByLabelOrNull(value)
        }

        // 実体は IR のみで生成されるオブジェクト（メタデータに載らないため Kotlin ソースからは不可視・ABI 保証外）
        // object EntriesHolder : EnumishEntriesHolder<Enumish>() {
        //     override val enumizedRootClass: KClass<SI> get() = SI::class
        //     override fun createEntries(): List<Enumish> = listOf(Bar, Foo.Companion)  // コンパイラ提供順（§5）
        // }
    }

    data class Foo(val v: Int) : SI {
        override fun asEnumish(): Companion = Companion

        companion object : Enumish {
            override val label: String get() = "Foo"
            override val enumizedClass: KClass<Foo> get() = Foo::class
            override fun toString(): String = label
        }
    }

    data object Bar : SI, Enumish {
        override fun asEnumish(): Bar = this
        override val label: String get() = "Bar"
        override val enumizedClass: KClass<Bar> get() = Bar::class
        // data object の toString は言語による合成実装が既に在るため生成しない（§4 原則 1）
    }
}
```

### enum が sealed interface を継承しているケース

enum class は sealed interface の継承者になれる。本プラグインはこれを一級ケースとして扱う。

```kotlin
@Enumize
sealed interface Command {
    data class Custom(val raw: String) : Command
    enum class Builtin : Command { HELP, VERSION }   // enum が sealed interface を継承
}

Command.Enumish.entries          // enum 全体で 1 kind（定数毎には展開しない）。順序はコンパイラ提供順（§5）
Command.Enumish.entries.map { it.label }  // ["Builtin", "Custom"]
Command.Builtin.HELP.name        // "HELP"    ← enum 本来の name（final メンバー）
Command.Builtin.HELP.label       // "Builtin" ← kind の label（Enumized 拡張プロパティ）
```

kind の粒度は「`when (command)` の網羅性の枝」（= sealed の直和の枝を末端まで展開したもの）に一致させており、
enum は全体で 1 kind になる。enum 定数 1 つずつを kind 化する展開は将来拡張である。

基底 API が `label` という名前を使うのは、この構成で enum 定数の final メンバー `Enum.name` に
横取り・シャドーイングされないためである（§4）。末端 enum への生成内容は普通の末端 class と同一である —
`asEnumish()`（末端本体）と、companion（= kind）への `label` / `enumizedClass` / `toString`（`toString` の生成の有無は §4 の 2 原則に従う）。

> enum class への `asEnumish()` メンバーの生成は未検証項目（設計00 の V4）であり、成立しない場合は末端 enum class を
> コンパイルエラーにする形へ縮退する。

## 2. runtime-api

生成コードが依存する基盤 API は `runtime-api` モジュールとして配布する（reflection 非依存・MPP 対応）。

```kotlin
package io.github.projectmapk.sealedClassEnumizer

import kotlin.reflect.KClass

@Target(AnnotationTarget.CLASS)
@Retention(AnnotationRetention.BINARY)
annotation class Enumize

interface Enumish {
    val label: String                              // enum の name 相当
    val enumishCompanion: Companion<Enumish>       // enum の declaringClass 相当（値から階層全体へ辿る手段）
    val enumizedClass: KClass<out Enumized<*>>     // kind に対応する末端の class リテラル（設計メモ参照）

    interface Companion<out T : Enumish> {
        val entries: List<T>
        fun valueOf(value: String): T
        fun valueOfOrNull(value: String): T?
    }
}

interface Enumized<out T : Enumish> {
    fun asEnumish(): T
}

// 値から kind の label を引く短縮（拡張プロパティ）
val <T : Enumish> Enumized<T>.label: String get() = asEnumish().label

// entries の保持・遅延初期化・label 探索を集約する基底クラス。
// 各階層の EntriesHolder（プラグインが生成）がこれを継承する。
// なお `Enumish` / `Enumized` が abstract class でなく interface であるのは sealed 階層に継承させるためであり、
// sealed 階層に属さない `EnumishEntriesHolder` はこの制約の対象外である
abstract class EnumishEntriesHolder<T : Enumish> {
    protected abstract val enumizedRootClass: KClass<out Enumized<T>>

    protected abstract fun createEntries(): List<T>

    val entries: List<T> by lazy { createEntries() }

    fun getByLabelOrNull(label: String): T? = entries.firstOrNull { it.label == label }

    fun getByLabel(label: String): T =
        getByLabelOrNull(label)
            ?: throw IllegalArgumentException("No enumish entry with label '$label' in ${enumizedRootClass.simpleName}")
}
```

設計メモ:

- `Retention` が `BINARY` なのは「ランタイム reflection に依存しない」ことの明示である（`RUNTIME` にしない）。
  `SOURCE` にしないのは、ビルドツールや将来の keep ルールとの連携のためである。
- `enumishCompanion` は「値から階層全体（entries）へ辿る」ための唯一の reflection レスな手段である
  （機能としては Java Enum の `getDeclaringClass` に対応）。基底では `Companion<Enumish>` と宣言し、
  生成 Enumish 側が具体型（`SI.Enumish.Companion`）へ**共変 override** するため、
  静的型が `SI.Enumish` なら `enumishCompanion.entries` は `List<SI.Enumish>` として型付く。
  また `Companion<out T>` の宣言側共変により、複数階層の Companion を `List<Enumish.Companion<Enumish>>` として
  射影なしで束ねられる。
  **`declaringCompanion` という名前は採らない**: Java の「declaring」は「定数が enum クラスの宣言内で
  宣言されている」という包含関係に基づく命名だが、本設計の kind は Companion に宣言されない（Companion は entries を
  持つ集約点であり、kind が宣言されるのは各末端である）。さらに末端 class の kind は companion object 自身であり、companion に
  とって「宣言元」は慣習的に外側クラス（`Foo`）を指すため、`Foo.Companion` 上でその名前は誤読を誘う。
  `enumishCompanion` は、返すものが「この kind の（生成）Enumish の companion object」そのものであることによる命名である。
- `enumizedClass` は kind に対応する末端の class リテラル（`Foo::class`）を返す。命名は Enumized（値側）↔
  Enumish（kind 側）の双対に基づく — `asEnumish()` が値→kind の対応であるのに対し、こちらは kind→対応する
  Enumized 実装クラスというクラスレベルの逆対応である（内部用語「末端」は公開 API 名に出さない）。
  kind を reflection 系ライブラリ
  （kotlin-reflect・serialization・DI 等）と接続する用途のためで、runtime-api 自身は class リテラルを保持するだけ
  であり reflection を使わない。基底では `KClass<out Enumized<*>>` と宣言し、生成 Enumish が `KClass<out SI>` へ、
  各 kind が `KClass<Foo>` へと共変 override するため、`entries.map { it.enumizedClass }` は `List<KClass<out SI>>`
  として型付く。非 final な末端（§3）では分類の代表である末端自身を返す — 値の実行時クラス（`Triangle()::class`）
  とは一致しない場合がある
- ネスト interface 名が `Companion` なのは、生成側の `SI.Enumish.Companion`（本物の companion object）と概念が揃うためである。
  代償として `Enumish` 自体には既定名の companion object を今後追加できないが、概念の一致を優先する。
- `Enumish` は `toString` を宣言しない。interface での `toString` の抽象再宣言は `Any` の実装では充足されない（実測）。
  §4 原則 2 の保証により全 kind は具象 `toString`（生成・手動宣言・継承実装・data object の合成）を持つため宣言も成立しうるが、
  充足の成立条件を増やすだけで利点が無い。kind の `toString` が label を返すのは、interface の要求ではなく生成側の実装による（§4）
- `EnumishEntriesHolder` はコンストラクタ引数を持たず、基底の識別は `protected abstract val enumizedRootClass`
  （生成側が基底の class リテラルを返す）で行う。これにより生成側の super 呼び出しは no-arg で済む。
  名前は Enumized 階層の根（= `@Enumize` の基底）を指し、`Enumish.enumizedClass`（末端側）とは Root の有無で
  区別する。class リテラルと `KClass.simpleName` は stdlib の機能であり kotlin-reflect を要しない（no-reflection 原則の
  範囲内。`qualifiedName` は JS 等のプラットフォームで利用できないため使わない）
- `getByLabel` の失敗メッセージは `No enumish entry with label 'X' in SI` 形式である。enum の
  `No enum constant FQN.NAME` は定数が enum クラスの内側に宣言されていることを前提にした表記だが、
  sealed の末端は基底の内側に宣言されるとは限らないため、宣言位置を示唆する `FQN.label` の連結は採らず、
  「基底の階層の entries に該当する label が無い」という事実を述べる

### runtime-api が提供するその他の API

| API | 内容 |
|---|---|
| `val <T : Enumish> Enumized<T>.label: String` | `asEnumish().label` の短縮（コード生成不要）。enum の `name` と併存できる命名（§4） |
| `abstract class EnumishEntriesHolder<T : Enumish>` | 各階層の `EntriesHolder` の基底（上記）。entries の遅延構築と `getByLabel` / `getByLabelOrNull` を提供する。生成側は supertype の指定（型引数）・`enumizedRootClass` の実装（基底の class リテラルを返す）・`createEntries()` の実装の 3 つだけを担う |

> `EnumishEntriesHolder` の挙動: `entries` は初回アクセス時に一度だけ構築され、以降は同じインスタンスを返す。
> `getByLabel` / `getByLabelOrNull` はその `entries` を先頭から線形に走査し、label が完全一致する最初の
> 要素を返す。label の一意性はチェッカー（`ENUMIZE_LABEL_CLASH`。§8）が保証するため、最初の一致を返す
> 実装でも結果は一意に定まる。

> 注意（シャドーイング）: Kotlin ではメンバーが拡張より常に優先されるため、階層のメンバーが `label` という
> 同名プロパティを持つ場合（例: `data class Tagged(val label: String) : SI`）、拡張プロパティは黙って隠され、
> `x.label` はユーザープロパティを返す。**確実に kind の値を得るには `asEnumish().label` を使う**こと。
> この構成にはチェッカーが警告（`ENUMIZE_EXTENSION_SHADOWED`）を出す。

## 3. enum 機能との対応カタログ

◎ = 同等以上 / ○ = 生成で同等相当 / △ = 制限付き / × = 提供しない・原理的に不可
（`A → B` は「v1 では A、将来のアドオン等で B になる余地」、`A/B` は「対象・構成により A または B」。
本節が「enum と同じにできない部分」の文書化を兼ねる）

| enum の機能 | 可否 | 本プラグインでの姿 |
|---|---|---|
| `entries` | ○ | `SI.Enumish.entries`（`List<T>`。毎回同じインスタンスを返す。`kotlin.enums.EnumEntries` は `E : Enum<E>` という境界を持つため型として使えず、`List<T>` で公開する） |
| `valueOf(name)` | ○ | `SI.Enumish.valueOf(label)`。加えて `valueOfOrNull`（enum に無い追加） |
| `values()` | △ | 提供しない（`entries` に一本化。enum 側も KT-48872 で entries へ移行済みである） |
| `name` | ○ | `label`（命名理由は §4） |
| `ordinal` | × | **提供しない**（設計判断。§4）。序数が必要な場合は `entries.indexOf(kind)` で得られるが、その値は改名で変動し永続化に使えない（§5） |
| `getDeclaringClass` | ○ | `enumishCompanion`（値から階層の Companion へ。「declaring」を名乗らない理由は §2） |
| reified `enumValueOf<T>()` / `enumEntries<T>()` | × | **提供しない**（設計判断。理由は下記）。型引数から Companion を引く用途は、型が静的に判っている以上 `SI.Enumish.entries` / `SI.Enumish.valueOf(...)` を直接書けば足りる |
| `compareTo`（ordinal 順） | × | **提供しない**（`ordinal` 相当を持たないため。§4）。並べ替えが必要な場合は `sortedBy { it.label }` 等、意味の明確な基準を利用側で選ぶ。`entries` の並びはコンパイラが渡す継承者順に従う（改名や階層の入れ子の変更で変動し、公式な保証も無い。§5） |
| `toString() = name` | ○/△ | 明示的な `toString` 実装（手動宣言・継承・data object の合成）があればそれを尊重し、無ければ `toString() = label` を必ず生成する（末端 enum の kind = companion も同様）。**kind が明示実装なしに `Any` の既定表示へ落ちる構成は許容しない**（§4） |
| 網羅的 `when` | ◎/△ | 値単位の when は sealed の地力で型による網羅性検査とスマートキャストが効く（enum を超える）。kind 単位の when（`when (x.asEnumish())`）は、生成 Enumish の sealed 化が成立すれば else が不要になる（未検証項目 V1。かつ全 kind が呼び出し側から可視の場合に限る。Enumish の手動実装（§8 の許容）がある場合はその枝も必要）。縮退時は else が必要 |
| `hashCode` / `equals` / 同一性 | ○ | kind は object / companion のシングルトンなので参照同一性が成立する（Java の直列化を経ると壊れる。下記） |
| Java シリアライズ（`java.io.Serializable`） | × | enum は直列化プロトコルがシングルトン性を保証するが、kind は `Serializable` でなく、手動で対応しても `readResolve` なしでは復元後の同一性（when の等値枝の前提）が壊れる |
| アノテーション引数 | × | 言語仕様の制約（アノテーション引数は const / enum / KClass 等のみで、object 参照は渡せない）。**enum 代替として最大の非互換点** |
| `EnumSet` / `EnumMap` | × → △ | Java の本物は `E extends Enum<E>` という境界を持つため使えない。将来 `EnumishSet` / `EnumishMap`（entries 上の位置を内部で利用する実装）を runtime-api で提供する余地はある |
| Java からの利用 | △ | v1 では `@JvmStatic` を付与しないため、Java からは interface 上に公開される static フィールド `Companion` を経由して `SI.Enumish.Companion.getEntries()` / `.valueOf(...)` / `.valueOfOrNull(...)` を呼ぶ（`entries` はプロパティなので Java では `getEntries()` になる）。`@JvmStatic` による `SI.Enumish.getEntries()` 形の static アクセスは**将来拡張**とする（override として生成されるメンバーに付与できるかが未確認であり、その不確実性を v1 に持ち込まないため。設計00 §4.1）。古典的な enum の `switch` は使えない |
| Java 側の網羅 `switch` | ○ | jvmTarget 17+ では sealed に `PermittedSubclasses` 属性が出力され、Java 21 のパターンマッチング switch で網羅性が効く |
| リフレクション連携 | ○ | `KClass.sealedSubclasses` 等の言語標準の機構はそのまま使える（JVM + kotlin-reflect 限定・プラグイン関与なし）。ただし `entries` は中間 sealed を末端まで展開するため、**中間 sealed がある階層では `sealedSubclasses` と要素の集合も並びも一致しない**（§5）。kind からは `enumizedClass` で末端の `KClass` を得られ、reflection 系ライブラリとの接続点になる（§2） |
| kotlinx.serialization | △ | 将来のアドオン `enumizer-serialization`（label ベースの KSerializer）で対応できる。`@Serializable sealed` の既定であるポリモーフィック形式とはワイヤ形状が異なる点に注意 |
| Jackson / Gson / Moshi 等 | × → △ | 各フレームワークは `java.lang.Enum` を特別扱いするため自動では効かない。アダプタを提供する余地はある（将来のアドオン） |
| ORM（Exposed / JPA） | × → △ | `Enum<T>` 境界の API（`enumerationByName` 等）は使えない。label ベースのカスタムマッピングのレシピを文書で提供する |
| Compose 安定性 | ○ | kind はシングルトンの object であり、stable 推論と相性が良い |

### reified ヘルパを提供しない理由

`enumishEntries<T>()` / `enumishValueOf<T>()` のような reified ヘルパは提供しない。
reflection を使わない実現手段では、**MPP のプラットフォーム間で挙動を揃えられない**ためである。

reified ヘルパを reflection なしで実現するには、コンパイラが**呼び出し点を Companion への直接参照に書き換える**
（intrinsic 方式）しかない。ところがこの書き換えは、プラットフォームごとにまったく別の機構で行われる。

- **JVM**: プラグイン向けの公開拡張点（`JvmIrIntrinsicExtension`）があり、型引数が未解決の段階では
  バイトコードマーカーを `.class` に残して後から完成させられるため、全経路で書き換えを保証できる
- **klib（JS / Native / Wasm）**: 公式（`kotlin.enums.enumEntries`）はバックエンドの lowering として
  **すべてのインライン展開の後**に置換しているが、プラグインが立てられる `IrGenerationExtension.generate()` は
  Fir2Ir 末尾、すなわちあらゆる展開より**前**にしか位置しない。コンパイラ本体も `IrIntrinsicExtension` の
  KDoc で「intrinsic はインライナの都合でプラットフォーム固有に行われ、現状は JVM のみサポートする」と
  明記しており、これは工夫で埋められる差ではなく**構造的な制約**である

帰結として、ヘルパを自前の `inline` 関数で包んだ場合（下の `parseOrDefault` のような、ごく自然に書きたくなる形）に
**JVM では動くが klib では実行時例外になる**という、プラットフォーム間で挙動が割れる API になってしまう。

```kotlin
inline fun <reified T : Enumish> parseOrDefault(s: String, default: T): T =
    enumishValueOfOrNull<T>(s) ?: default   // JVM: 動く / klib: 実行時例外
```

さらに本プロジェクトはランタイム reflection を禁じているため、kotlinx.serialization のように
「intrinsic が効かなければランタイム解決へフォールバックする」という逃げ道が使えない。同じ機構を借りながら
**失敗モードだけが実行時例外に悪化する**という非対称を抱えることになる。

一方で、ヘルパが無くて困る場面はほとんど無い。`enumishEntries<T>()` と書ける状況では `T` が静的に判っているので、
`SI.Enumish.entries` と直接書けば済む。ヘルパはジェネリックなユーティリティを書くときの糖衣にすぎず、
そのユーティリティこそが上記で壊れる形そのものである。**MPP 対応を一級要件とする以上、
プラットフォームで挙動が割れる API は表に出さない**。

このため設計は reified ヘルパに関わる構成要素（runtime-api のヘルパ・IR の intrinsic 書き換え・専用の診断・
専用の検証項目）を持たない（設計00 の V 表で V6 が欠番なのはこの項目に対応する）。

### 末端は非 final でもよい（拡張点を開いたまま使える）

sealed でない継承者はすべて末端として扱う。**final なクラスや object だけでなく、
open class / abstract class / interface / fun interface も末端になり、通常どおり生成の対象となる**
（非 final な末端への生成は未検証項目 V10。不成立時は sealed でも final でもない継承者をエラーにする縮退となる。§9）。

```kotlin
@Enumize
sealed interface Shape {
    data class Circle(val r: Double) : Shape          // 末端（final）
    abstract class Polygon : Shape                    // 末端（abstract）— 拡張点として開いておく
    interface Custom : Shape                          // 末端（interface）— 第三者が実装できる
}

Shape.Enumish.entries   // [Circle, Custom, Polygon] — 末端の数だけ。サブタイプでは増えない
```

**階層外にサブタイプをいくつ作っても entries は変わらない**のが要点である。
`class Triangle : Shape.Polygon()` を別モジュールで定義しても、`Triangle` は新しい kind を作らず、
`asEnumish()` の実装を `Polygon` から継承して **`Polygon` の kind に吸収される**。

```kotlin
val t: Shape = Triangle()
t.asEnumish()   // Shape.Polygon.Companion
t.label         // "Polygon"
```

値単位の `when` の網羅性も、`is Polygon ->` の枝がサブタイプをすべて覆うため成立する。
つまり「分類の粒度は固定したまま、各分類の実装は開いておく」という設計が素直に書ける。

制約は 1 つだけで、**ある型が 2 つ以上の末端のサブタイプになってはならない**（どの kind に対応するか
決まらないため。§8）。なお階層外で複数の末端 interface を実装した場合は、`asEnumish()` の
戻り値型が両立しないため言語側でもコンパイルが通らない。

### enum に対する優位点

- エントリーがデータを持てる（`data class` 継承者 = パラメタライズドなバリアント）
- 値単位の網羅 when + スマートキャスト
- 多段の分類が可能（中間 sealed によるグルーピング）
- **末端を非 final にでき、分類を固定したまま実装を開けておける**（上記。enum には無い自由度。未検証項目 V10。§9）
- Java 21 のパターンマッチングとの親和性
- companion 単位の拡張性（kind に対して拡張関数を生やせる）

## 4. label という命名の理由と、ordinal 相当を提供しない理由

### label（name にしない理由）

enum class が階層の末端になるケース（§1 の `Builtin`）では、enum 定数は `Enum.name` を**final メンバー**として
持っている。基底 API が `name` を名乗ると:

1. メンバーによる暗黙の充足 — 階層側に抽象プロパティ `name` を宣言してもコンパイルエラーにはならず、
   enum 末端では final メンバー `Enum.name` がその実装として**黙って採用される**（実測）。kind の label で
   あるべきところに定数名（`"HELP"`）が返り、final のため override で正すこともできない
2. 拡張シャドーイング — 拡張プロパティ `name` を用意しても、enum 定数上ではメンバー `Enum.name` が優先され、
   **静的型によって返る値が変わる**静かな罠になる

`label` はこの罠を構造的に回避する命名であり、将来のケース変換等、表示用のカスタマイズを受ける名前としても
適する。ただし `label` もドメインモデルで頻出の名前であり、ユーザー側のメンバーによる拡張シャドーイング
（§2 の注意）のリスクは残る。これはチェッカー警告と「確実な取得は `asEnumish()` 経由」という規約で対処する。

### ordinal 相当と Comparable を提供しない理由

enum の `ordinal` に相当するプロパティと、それに基づく `Comparable` は**提供しない**。
アプリケーション上の意義が薄く、弊害の方が大きいためである。

- sealed 階層の序数は enum のように「宣言順」で定まらない。コンパイラが提供する継承者順（§5）に
  従うほかなく、**末端や外側クラスの改名で値が変動する**
- したがって永続化にも通信にも使えず、「使ってはならない値」を API 表面に置くことになる
- 序数を前提とする操作（`EnumSet` 相当の効率的な実装など）は、将来 runtime-api の内部で `entries` 上の位置を
  使えば実現でき、公開 API として序数を露出する必要はない
- `Comparable` は序数の存在が前提である（enum の `compareTo` は ordinal 比較）。序数を持たない以上
  「何順で比較するのか」の自然な答えが無いため、併せて提供しない。並べ替えが必要な場合は
  `sortedBy { it.label }` のように**意味の明確な基準を利用側が選ぶ**方が健全である

### toString について

kind の `toString` は次の 2 原則で扱う。

1. **表示のカスタマイズは常に利用側が勝つ**: 明示的な `toString` 実装を持つ kind に、プラグインは何もしない。
   `toString` は表示専用であり、変えても `entries` / `valueOf` / `asEnumish` の整合性には影響しないため、
   手動定義をチェッカーの禁止対象にもしていない（§8。`Any` のメンバーである以上どのクラスでも override でき、
   言語仕様上これを禁じる手段も無い）
2. **`Any` の既定表示を許容しない**: 明示的な実装を持たない kind には、プラグインが `label` を返す `toString` を
   **必ず override 生成する**（kind が companion object の場合も末端 object の場合も同様）。kind の表示が
   明示実装なしに `クラス名@ハッシュ` 形式（`Any` の既定実装）へ落ちる構成は存在させない

「明示的な `toString` 実装がある」と見なし、原則 1 により生成しないのは次のケースである。

- **kind 自身が `toString` を手動宣言している**: ユーザー定義をそのまま採用する（重ねて生成すると再宣言の衝突になる）
- **kind が継承経路上に `Any` 以外の具象 `toString` を持つ**: kind（companion / 末端 object）の親クラスが独自の
  `toString` を実装している構成など。生成するとそれを override してしまい、利用側が意図した表示を潰す
- **末端 data object**: 言語が単純名を返す `toString` を自動合成しており、この合成実装の存在が生成しない理由である。
  **label と表示が一致するかどうかは判定に関与しない** — 将来の label のケース変換（下記のカスタマイズ）で
  label と単純名が一致しなくなった場合も、data object の `toString` は生成せず、言語が合成する単純名のままとする

なお**末端 enum class の kind（= その companion）は特別扱いしない** — 普通の末端 class の companion と同様、
上記の 2 原則で生成の有無を判定する（通常は `toString() = label` が生成される）。enum 定数側の表示
（`Enum.toString()`。既定は `name` を返し、実装側が override してよい）と kind 側の表示は、管轄の異なる別物として
併存する（例: 定数の表示は `"HELP"`、kind の表示は `"Builtin"`）。原則 2 の保証は網羅的である —
どの kind にも手動宣言・継承実装・data object の合成・生成の label のいずれかが必ず具象実装として存在する。

なお kind の supertype が `toString` を**抽象として再宣言**している場合（abstract class での
`abstract override fun toString()`、または interface での抽象再宣言 — これは `Any` の実装では充足されない。§2）、
プラグインの生成はこの要求の充足には使えず、kind 側に手動の `toString` 実装が必要である
（無ければ言語の「抽象メンバー未実装」エラーになる。表示の実装要求を、生成が黙って肩代わりする形は採らない）。

確実に label を得たい場合は、いずれのケースでも `toString` ではなく `label` を参照すること。

### カスタマイズ（v1 では非対応）

`@Enumize` のパラメータによるカスタマイズ — label のケース変換（アッパースネークケース・ケバブケース等）、順序の明示指定、生成 Enumish への
追加基底 interface（プロパティ / 関数の追加用。生成メンバーの具体 override は許容しない）— は
いずれも将来拡張であり、**v1 では非対応**である。追加基底 interface は `interface MyKind : Enumish` の形で
定義したものを、プラグインが生成 Enumish の supertype として注入する想定である。
kind 以外による生成 Enumish / 基底 Enumish（runtime-api の `Enumish`）の手動実装は v1 でも禁止されないため
（§8 の「許容」）、この将来拡張が新たに加えるのは注入の自動化と全 kind への一括適用である。

## 5. entries の順序

`entries` の順序は、**Kotlin コンパイラが sealed 継承者一覧として提供する順序**に合わせる。
コンパイラは継承者一覧を **FQN（ClassId）文字列の序数昇順（大文字小文字を区別・ロケール非依存）に正規化**して
メタデータへ直列化しており、`KClass.sealedSubclasses`（kotlin-reflect）や KSP が返す順序もこれである。

> Kotlin 2.4.0 実測: ネストされた末端 `S.Aaa` / `Box.Bbb`・トップレベルの末端 `Mmm` / `Zzz` / `aLower` を混在させた階層で
> `sealedSubclasses = [Box.Bbb, Mmm, S.Aaa, Zzz, aLower]` — **FQN 序数順**（単純名順なら Aaa が先頭、
> 宣言順なら Zzz が先頭、大小無視なら aLower が先頭になるため、いずれでもないことが判別できる）。

**プラグインは並べ替えに一切介入しない。** コンパイラが渡す継承者リストをそのまま使い、中間 sealed に
到達したらその継承者リストへ再帰的に降りる。この走査で現れた順序がそのまま `entries` になる。

- **中間 sealed が無い階層**では、`entries` はコンパイラが提供する順序そのもの、すなわち上記の FQN 序数順である。
  末端がすべて基底にネストしている、またはすべてトップレベルにある構成なら、単純名（= 既定の label）の昇順と一致する
- **中間 sealed がある階層**では、中間の位置にその継承者が入れ子に展開されるため、
  **全体としては FQN 序数順にならない場合がある**。中間 sealed の継承者が中間の内側にネストしていない構成がこれにあたる:

  ```kotlin
  sealed interface SI
  sealed interface Mid : SI     // pkg/Mid
  object Aaa : Mid              // pkg/Aaa  ← Mid の内側ではなくトップレベル
  object Bbb : SI               // pkg/Bbb

  // SI の継承者は [Bbb, Mid] → Mid を展開して entries = [Bbb, Aaa]
  ```

  末端が中間 sealed の内側にネストしている通常の構成では、ネストした末端の FQN が中間の FQN を接頭辞に持つため、
  結果的に FQN 序数順と一致する

**性質（enum の宣言順との違い）**:

- **宣言順ではない**。宣言を並べ替えても `entries` の並びは変わらない
- 順序が変わるのは**末端（またはその外側クラス）の改名・追加・削除**、および階層の入れ子構造の変更のときである
- 中間 sealed を持つ階層では `sealedSubclasses` が直接の継承者（中間 sealed を含む）を返すのに対し
  `entries` は末端までフラット化するため、**要素の集合も並びも `sealedSubclasses` とは一致しない**
  （一致するのは中間 sealed が無い場合に限られる）

この正規化順はコンパイラの実装詳細であり**公式な保証は無い**（宣言順を提供してほしいという要望は、KSP 側で not-planned として
クローズ済みである）。ただしコンパイラは継承者一覧を**属性へ格納する時点で FQN 順に正規化する**ため
（設計00 §6.1）、**ソースの配置（ファイル名・ファイル順・宣言位置）には依存しない**。
プラグインが並べ替えに介入しなくても、この性質はそのまま `entries` に引き継がれる。
本プラグインは (a) Kotlin のマイナーバージョン毎のアーティファクト分割（§7）、
(b) 順序の回帰を検出する決定性テスト（設計00 §9）によってこれを受容する。
**`entries` 上の位置（`indexOf` の値）を永続化に使ってはならない** — 改名で変動するためである。
永続化には label または独自プロパティを使うこと。順序の明示指定（`@Enumize(order = ...)` 等）は将来拡張である。

## 6. 利用感の違い（enum からの読み替え）

| enum での操作 | 本プラグインでの操作 |
|---|---|
| `MyEnum.entries` | `SI.Enumish.entries`（`.Enumish` が 1 段挟まる） |
| `MyEnum.valueOf("A")` | `SI.Enumish.valueOf("A")` |
| `e.name` | `kind.label`（値からは `si.label` 拡張、または `si.asEnumish().label`） |
| `e.ordinal` | 対応物なし（§4）。必要なら `SI.Enumish.entries.indexOf(kind)`（永続化不可） |
| `e1 < e2` | 対応物なし（§4）。`sortedBy { it.label }` 等、意味の明確な基準を選ぶ |
| `when (e) { MyEnum.A -> }` | 値単位: `when (si) { is SI.Foo -> }` / kind 単位: `when (si.asEnumish()) { SI.Foo.Companion -> }` |
| `Enum<*>`（任意の enum） | `Enumish`（任意の kind。複数階層の Companion は `Companion<Enumish>` で束ねられる。§2） |

その他の体感差:

- **entries の並びは宣言順ではない**: 基本は名前（FQN）順で、中間 sealed がある階層では入れ子展開による
  例外がある（§5）。enum の「上から順」の感覚は成立しないが、代わりにソースの配置（ファイル・宣言位置）に依存しない
- **エントリーの実体が 2 種類ある**: 末端 object は「値 = kind」だが、末端 class は「値（インスタンス多数）と kind（companion）が別物」。
  `SI.Foo(42) != SI.Foo(43)` だが `SI.Foo(42).asEnumish() === SI.Foo(43).asEnumish()`
- **kind 単位の when における枝の書き方**: 末端 class の kind は `SI.Foo.Companion ->` と書く（`SI.Foo ->` という companion 短縮形が
  網羅性の判定に算入されるかは検証項目 V1 に含まれ、成立すればこちらを正典とする）
- **kind 単位の when では値の型は絞り込まれない**: `when (si.asEnumish())` の分岐内でも `si` の静的型は元のままである。
  Kotlin の contract は「特定のオブジェクトを返したらレシーバはこの型」という関係を表現できず
  （`returns()` に指定できるのは `true` / `false` / `null` のみ）、`asEnumish()` は override メンバーなので
  そもそも contract を書けない（いずれも実測で確認）。**値の型が必要な場合は値単位の `when (si)` を使う**
  — そちらは sealed の地力でスマートキャストが効く
- **初期化タイミング**: enum はクラスの静的初期化時に全定数が一括で初期化されるが、entries は初回アクセス時の遅延初期化である。
  初回アクセスまで実行時異常が顕在化しない点が異なる
- **初期化再入の禁止**: kind（companion / 末端 object）の初期化子・init ブロックから階層の
  `entries` / `valueOf` を参照してはならない（遅延初期化の再入で StackOverflow になりうる。
  enum のコンストラクタから `values()` に触れないのと同種の制約）
- **型パラメータ付き sealed も対象にできる**（enum は型パラメータを持てない）: `sealed class S<T>` に `@Enumize` を
  付与できる。生成される `S.Enumish` は型パラメータを持たず、kind は `S<*>` の分類子である — 型引数は kind の
  同一性に影響しない（同じ末端のインスタンスであれば `Foo<Int>` でも `Foo<String>` でも同じ kind に分類される）
- **IDE**: IntelliJ の K2 モードはサードパーティ FIR プラグインをデフォルトでロードしない（KTIJ-29248）。
  当面は「**CLI / Gradle ビルドは正しく通るが、エディタ上では生成 API が未解決表示になる**」という状態が既定の体験になる

| モジュール | 内容 |

| `runtime-api` | `@Enumize`・基底型（`Enumish` / `Enumish.Companion<out T>` / `Enumized<out T>`）・`EntriesHolder` の基底クラス（`EnumishEntriesHolder<T>`）・拡張プロパティ（`Enumized<T>.label`）（§2。MPP・reflection 非依存） |

| `gradle-plugin` | `KotlinCompilerPluginSupportPlugin`。全コンパイレーション（main / test / metadata / 全ターゲット）へ適用し、`runtime-api` を自動追加（オプションで無効化可） |

- **K2 のみ**サポート。実用下限は **Kotlin 2.4**。根拠は、プラグインが生成したクラスの中にネストされたクラス
  （本プラグインの `SI.Enumish.Companion`）を **Analysis API が解決できない**不具合 KT-84625 が 2.4.0-Beta2 で
  修正されたことである。**これは IDE / Analysis API 側の下限であり、CLI / Gradle の codegen 自体はこの修正に依存しない**（§6 の IDE の項も参照）
- コンパイラプラグイン API は「リリース毎に破壊的変更が入る」ことが公式に宣言されているため、
  **Kotlin のマイナーバージョン毎にアーティファクトを分割**して配布する
- 階層（sealed 基底から末端までの範囲）は言語仕様上、同一パッケージ・同一モジュール・（MPP では）同一ソースセットに閉じる。
  末端が非 final な場合、そのサブタイプは階層の外側にあってよい（別モジュールでもよい。§3）。
  `@Enumize` を expect / actual 宣言に付与することは、v1 ではエラーとする（expect は actual 毎に階層が変わりうるため。
  actual は生成物の注入 — supertype `Enumized<T>` やネスト宣言 `SI.Enumish` — が expect-actual マッチングと
  両立するか未検証のため）
- **対象はソースに書かれた宣言に限る**。基底も継承者も、当該モジュールのソース上の宣言であることを前提とする。
  **他のコンパイラプラグインが生成した宣言と組み合わせた場合の動作は v1 では未定義**である
  （本プラグインの判定・診断はフロントエンドで動くため、そこに存在しない宣言は観測できない。設計00 §1）

### モジュールを跨いだ利用

- 生成 API（`SI.Enumish` とそのメンバー）は通常の宣言としてメタデータ / klib に載るため、
  **プラグインを適用していない利用側モジュールからも普通に参照できる**（プラグインが必要なのは生成する側だけである）
- モジュールを跨いだ kind 単位の網羅 when（else 省略）は、生成 Enumish の継承者一覧がメタデータへ直列化されること
  （未検証項目 V1）に依存する。縮退時は else が必要
- 末端の追加はライブラリの ABI 変更（sealed サブクラス一覧はメタデータの一部）として利用側の再コンパイルを正しく誘発する
- 旧バイナリと実行時にだけ組み合わさる場合も、entries は実行時に解決されるので「実行時に存在する版の集合」が返る
  （このため entries アクセサは inline にしない）

## 8. 制限事項（チェッカーがエラーにする構成）

enum 的意味論（entries の完全性・label の一意性・kind の一意対応）を守るため、以下はコンパイルエラーとする。
診断 ID と検査の詳細は [設計01](コンパイラプラグイン設計01.md) を参照。

| 構成 | 理由 |
|---|---|
| `@Enumize` を sealed class / sealed interface 以外（fun interface を含む）に付与 | 階層が定義できない |
| `@Enumize` を expect / actual 宣言に付与 | expect: actual 毎に階層が変わりうる。actual: 生成物の注入（supertype・ネスト宣言）が expect-actual マッチングと両立するか未検証（いずれも v1 制限） |
| 1 つのクラスが 2 つ以上の `@Enumize` 階層に属する（入れ子・兄弟とも） | `Enumized<A>` / `Enumized<B>` を異なる型引数で二重に継承することになり、言語仕様違反になる |
| 階層内のある型が 2 つ以上の末端のサブタイプになる（例: `abstract class A : SI` と `class B : A(), SI`） | どちらの kind に対応するか一意に定まらない。階層外で複数の末端 interface を実装した場合も同様だが、そちらは言語側でもコンパイル不能になる |
| 末端が inner class | inner class は companion を持てない（言語制約） |
| kind が基底の本体スコープから参照できない。具体的には (a) 別ファイルの private なトップレベルの末端、(b) 末端 class の private / protected な既存 companion | entries を組み立てるコードは基底の内側（`SI.Enumish` の中）に生成されるため、そこから各 kind を名前で参照できる必要がある。**基底の中にネストされた private な末端は参照できるので対象外**である |
| 末端の可視性が基底より広く（sealed interface 階層で言語上成立する構成）、かつ companion の実効可視性が末端未満 | `asEnumish` の返り値型（companion の型・生成 Enumish へのフォールバックのいずれも）が露出エラー無しに書けない（[エッジケースへの対応方針](エッジケースへの対応方針.md) §1.3） |
| 階層の末端 class の companion が同一階層の末端でもある | 同一オブジェクトに kind が二重対応してしまう |
| label（既定 = 末端宣言の単純名。**companion 自身が末端である場合に限り**その宣言名）の重複 | `valueOf` の解決が一意に定まらない。sealed の末端は同一パッケージ内の任意のクラスの中にネストできるため、enum と違って単純名の衝突が起こりうる |
| 生成対象メンバーを**その生成先クラス**が手動宣言・継承している（kind = 末端 object / 末端の companion での `label` / `enumizedClass`、生成 Enumish での `enumishCompanion` / `enumizedClass`、その Companion での `entries` / `valueOf` / `valueOfOrNull`、末端での `asEnumish`） | 生成と衝突（`is Enumish` と言える supertype 宣言の重複だけなら許容）。※ `toString` は対象外（明示実装があれば生成せず利用側定義を採用する。§4）。※ 末端 class **自身**が `label` を持つ構成は、このエラーではなく下記の警告になる（生成先は companion のため） |
| 型引数の異なる手動継承（`: Enumized<別の型>` 等） | 言語仕様違反（同一の総称インターフェースを異なる型引数で二重に継承すること）への合流を先回りして検出する |
| 基底に既存のネスト宣言 `Enumish` がある | 生成名と衝突 |
| 末端 class に companion が無く自動生成の候補判定も働かない（typealias 経由の supertype 等の稀なケース） | 明示的な `companion object` の宣言を要求する |
| 階層の継承者が別ソースセットに存在 | 言語仕様違反（コンパイラ本体の診断への補足説明） |

警告: 階層メンバーが `label` という可視メンバーを宣言している場合（拡張シャドーイング。§2）。

許容: kind 以外のクラスが生成 Enumish / 基底 Enumish を手動で実装すること（末端 class 自身による実装を含む）は、
それ自体ではエラーにしない。エラーになるのは生成への干渉が生じる構成 — 生成対象メンバーの衝突・ネスト名
`Enumish` の衝突・`Enumized<別の型>` の二重継承（いずれも上表） — だけである。手動実装で作られる値は kind では
ないため entries に含まれず `valueOf` でも解決されない — enum 的 API が保証する対象は kind に閉じており、
手動実装はこの保証を壊さない。生成 Enumish が sealed で出荷される場合（V1）、手動実装は言語の sealed 制約
（同一モジュール・同一パッケージ）に従い、kind 単位の網羅 when にはその実装の枝も必要になる。
手動実装が生成 Enumish の継承者一覧（sealed メタデータ）へ正しく載ることは V1 の検証範囲に含める。

### 基底の可視性は制限ではない

上表の制限は**個々の kind が基底から参照できるか**という一点だけを見ており、**基底自身の可視性は問わない**。
`private` / `internal` な sealed 基底に `@Enumize` を付けてよく、生成 API はその基底が見える範囲で
通常どおりすべて使える。成立の理由・利用例・可視性が混在する階層（internal / private の末端・companion を
含む構成）の帰結は [エッジケースへの対応方針](エッジケースへの対応方針.md) §1 を参照。

## 9. 既知の未検証項目（設計上の縮退経路つき）

設計には、プロトタイプで確認する未検証項目がある。全項目（V1〜V11。V2 は V2-a / V2-b の 2 項、V6 は欠番 — reified ヘルパの不提供に対応。§3）の一覧と詳細は
[設計00](コンパイラプラグイン設計00.md) の V 表を参照。下表は**利用者から見て影響の大きい項目の抜粋**であり、
番号は設計00 の V 表に対応する（抜粋した各項目には縮退経路が定義されている）。

| V | 項目 | 不成立時の縮退 |
|---|---|---|
| V1 | 生成 `Enumish` の sealed 化（kind 単位の when での else 省略。メタデータへの直列化・when の各枝形（companion kind と object kind の等値枝・`is` 枝）の被覆・手動実装の継承者一覧への反映（§8 の「許容」）・IDE を含む） | 非 sealed で出荷し else を要求する |
| V3 | 末端 class への companion の自動生成（コンパイラのフェーズ順の制約により、supertype が未解決の段階で「この class は階層の末端か」を判定せねばならない。この制約が回避できないことは Kotlin 公式のコードで確認済みであり、supertype を根拠に companion を生成する前例も JetBrains 管理のプラグインには無いため、リスクの高い項目である） | 明示的な `companion object` を要求する |
| V4 | enum class への `asEnumish()` メンバーの生成 | 末端 enum class をエラーにする |
| V10 | **非 final な末端**（open / abstract class・interface・fun interface）への生成（§3 の「拡張点を開いたまま使う」構成） | 非 final な末端を許容せず、sealed でも final でもない継承者をエラーにする |
