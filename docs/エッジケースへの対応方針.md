# エッジケースへの対応方針

本書はエッジケース — 可視性の混在・`@Enumize` 対象への手動 supertype・label の決定と名前被り・
チェッカーエラー該当時の生成挙動 — の扱いを定める。  
扱いは本書を正とする（利用者視点の仕様全般の正は [概要.md](概要.md)）。  
用語は [設計00](コンパイラプラグイン設計00.md) §1 に従う。  
「実測」は Kotlin 2.4.10（JVM / K2）でのコンパイル確認（生成物相当の手書き模擬を含む）を指す。  
検証項目（§4 の E 表）は本書が管理し、設計00 §10 から参照される。

## 1. 可視性に internal / private が含まれる階層

**基底の可視性も、個々の kind の可視性も、制限ではない。** `private` / `internal` な sealed 基底に `@Enumize`
を付けてよく、生成 API はその基底が見える範囲で通常どおりすべて使える。  
生成物の宣言自体は public でも、実効可視性は外側の宣言に自動的に一致する
（階層 API は基底・値 / kind API は末端。帰属は設計00 §4・生成宣言の可視性規則は設計01 §1）。  
基底本体スコープから名前参照できない kind（private / protected な既存 companion・
別ファイルの private トップレベル末端・private 外側クラスの末端）も、**IR-only アクセサ**（メタデータ非搭載＝ABI
非追加。概要 §8・設計02 §4.3）経由で entries に載る。  
可視性で減衰するのは静的表現力（kind の名指し・網羅 when・IDE 補完）だけである。

```kotlin
// SI.kt
@Enumize
private sealed interface SI {          // ファイル内に閉じた基底
    data object Bar : SI
    data class Foo(val v: Int) : SI
}

// 同一ファイル内なら、生成 API はすべて通常どおり使える
private fun pick(si: SI): String {
    SI.Enumish.entries                 // OK
    SI.Enumish.valueOf("Bar")          // OK
    return when (si.asEnumish()) {     // OK（else 不要）
        SI.Bar -> "bar"
        SI.Foo.Companion -> "foo"
    }
}
```

`when` の else 省略が可視性に阻まれるのは、階層（基底と kind）の可視範囲の**外側**から書いた場合だけである —
判定は呼び出し側の位置に依存し、上の例のとおり private 基底と同一ファイル内の when は else なしで網羅する（設計00
§5.2）。

### 1.1 実測: 言語側の挙動

| # | 構成 | 結果 |
|---|---|---|
| 1 | internal open class を public class が継承 | エラー `EXPOSED_SUPER_CLASS` |
| 2 | internal / private な interface を public class が実装（internal sealed interface の public 末端を含む） | **診断なし** |
| 3 | public クラスの public メンバーが internal companion 型を返す | エラー `EXPOSED_FUNCTION_RETURN_TYPE` |
| 4 | public メンバーの override を internal へ狭める | エラー `CANNOT_WEAKEN_ACCESS_PRIVILEGE` |
| 5 | internal な interface を public interface が継承 | エラー `'public' sub-interface exposes its 'internal' supertype` |

露出検査が働くのはスーパークラスと interface の継承（extends 形）であり、class が interface を実装する形（implements
形）には働かない（#1・#5 と #2 の対比）。  
したがって sealed **interface** 階層で **基底より広い末端**が言語上成立するのは **class 系末端**（class / object / enum
class / value class）に限り、interface / fun interface 末端は #5 によりコンパイル不能である（将来 implements
形にも検査が追加された場合は当該構成が言語エラーへ合流するだけで、本節の規則に変更は要らない）。
#3 は返り値型フォールバック（§1.3）の、#4 は「生成物の internal 化は不成立」（§1.4）の根拠である。

### 1.2 方針と構成別の帰結

**実行時機能は可視性構成に依らず完全に提供し、減衰するのは静的表現力のみ**（内訳は §1 冒頭）。  
可視性は静的検査の概念であり実行時挙動に関与しないため、これは現設計のままで成立する。  
internal な末端を entries から除外する等のモードは、entries の完全性・asEnumish の全域性と両立しないため設けない（帰結:
label は kind の可視範囲の外からも entries / valueOf 経由で観測される）。

public 構成との API 分離は、既存の帰属の 2 群がそのまま可視範囲の分離になるため、**追加の生成分岐を設けない**:

- **階層 API**（基底ファイル帰属: entries / valueOf / `SI.Enumish` の名指し）= 基底の実効可視性
- **値・kind API**（末端ファイル帰属: asEnumish / label / toString / enumizedClass）= 各末端・companion の実効可視性

| 構成 | 帰結 |
|---|---|
| internal / private 基底（末端も同等以下） | 全生成物が基底の可視範囲に閉じ、範囲内では全機能（本節冒頭） |
| public 基底 + 可視性の低い末端（internal・基底内ネストの private） | 生成形状は不変。可視範囲の外からは当該 kind を名指しできず when は else 要。entries / valueOf / label は動作する |
| public 末端 class + internal companion | asEnumish の返り値型が `SI.Enumish` へフォールバック（§1.3 規則 2） |
| public 基底 + internal 中間 sealed | 影響なし（中間 sealed には何も生成されず、生成 API にも現れない） |
| **基底より広い末端**（internal 基底 + public な class 系末端など。1.1 #2。interface / fun interface 末端は露出検査でコンパイル不能 = 1.1 #5） | 階層 API は internal・値・kind API は public という分離が生じる。可視範囲の外からは値・kind API のみ利用可。asEnumish 呼び出しと label 拡張の型推論、label / enumizedClass の直接解決（override が companion 自身に生成される）、公開基底 `Enumish` への upcast は成立し、upcast 後は enumishCompanion 経由で実行時に entries へ到達できる。具体型 companion からの enumishCompanion 直接参照は共変 override の返り値型が不可視のためコンパイル不能（E-2 の実測。§4 注記）。companion が末端未満なら §1.3 規則 3 |
| private / protected な既存 companion・別ファイルの private トップレベル末端・private 外側クラスの末端 | IR-only アクセサ経由で entries に載る（§1.4・設計02 §4.3）。名指し不可のため可視範囲の外からの網羅 when は else 要 |

生成メンバーは宣言 public のため JVM 名のマングリングは起きない。
可視性の低い kind も継承者一覧・inheritors 属性には通常どおり載る。

### 1.3 asEnumish の返り値型（設計01 §5.4 の一般化）

末端 L・その companion C・生成 Enumish T、eff = 実効可視性として:

1. `eff(C) ≥ eff(L)` → C の型（具体型・既定）
2. `eff(T) ≥ eff(L)` → T へフォールバック（現行 設計01 §5.4）
3. いずれも不成立 → 診断エラー（`ENUMIZE_KIND_TYPE_NOT_DENOTABLE` — 設計01 §7.2。修正方法: C の可視性を L 以上に、
   または L を基底以下に）

返り値型は `Enumized<T>.asEnumish` の共変 override として T のサブタイプでなければならず、
基底 Enumish まで広げるさらなるフォールバックは不成立（調査結果）。  
規則 3 が生じるのは「基底より広い末端 + companion が末端未満」のみ。  
判定は既存フォールバックと同じ実効可視性判定で完結する。  
末端 object の kind は自身を返すため対象外。

### 1.4 参照不能 kind の IR-only アクセサ（採用）と不採用の緩和策

「private な内容であっても entries は全種取得可能」を方針とし、
基底本体スコープから名前参照できない kind は **IR-only アクセサ**経由で entries に載せる（配置規則は設計02 §4.3）。  
FIR には宣言を作らないためメタデータに載らず（ABI 非追加）、外部ソースからは参照できない。  
これにより下表の 2 案を採用する。  
全 klib ターゲットと clean / incremental / from-cache での成立は結合テストで確認済み。

| 案 | 結論 |
|---|---|
| private / protected companion の許容 | **採用（IR-only アクセサ）**。末端クラス内にネストした IR-only object から private / protected companion を intra-scope 参照する（synthetic アクセサ方式は ABI 追加になるため採らない） |
| 別ファイルの private トップレベル末端・private 外側クラスの末端の許容 | **採用（IR-only アクセサ）**。末端ファイルのトップレベル IR-only 関数から file-private な kind を同一ファイル内参照する（トップレベル生成は P3・KT-66735 に触れるが、既存ファイルへの IR-only 追加は全 klib を通る — 実測） |
| 生成メンバー・生成 Enumish の internal 化 | 不成立。生成メンバーは全て public 宣言（runtime-api の基底型・`Any`）の override であり、可視性を狭められない（1.1 #4） |
| 可視性コピー方式 | 不採用（設計01 §1） |
| モジュール外可視の kind のみを返す `publicEntries` 等の追加 | 見送り。必要になった時点で再検討 |

可視性の編集による ABI 変動は設計00 §5.3 #7-c のとおり（規則 1 ⇔ 2 の切替として伝播。規則 3 への出入りは診断の発火・
解除。private への変更でも entries 構築は IR-only アクセサ経由で成立し、kind の名指し側だけが言語の可視性に従う）。

## 2. `@Enumize` 対象への手動 supertype（Enumized 相当の親）

現行（v1）: 型引数まで一致する手動宣言は注入スキップ、`Enumized<K>`（K ≠ `SI.Enumish`）は
`ENUMIZE_MANUAL_SUPERTYPE_MISMATCH`（設計01 §4）。  
判定は間接継承（`interface MyBase : Enumized<K>` 経由）も対象とする。

### 2.1 将来拡張の方針: 検査を通る K は生成の基底として採用する

`Enumized<K>` の手動継承があり K が §2.2 を通る場合、MISMATCH とせず次のとおり生成する:

- `Enumized<SI.Enumish>` の注入をスキップし、**生成 Enumish の supertype を基底 Enumish から K へ差し替える**（K :
  Enumish のため基底 Enumish は推移的に維持される）。  
  他の生成は不変
- kind は K のサブタイプになるため、末端の asEnumish の具体型 override は `Enumized<K>.asEnumish` の override
  として成立する（手書き模擬で実測済み）

利用側の変化は「基底経由の asEnumish の静的型が K になる」ことだけである（entries / valueOf / label 拡張は不変）。  
K は非 sealed（§2.2-3）のため kind-when の else 省略は失われる。  
概要 §4 の将来拡張（追加基底 interface）との対比:

| 観点 | 手動 `Enumized<K>` | 追加基底 interface（概要 §4） |
|---|---|---|
| 生成 Enumish の supertype | K | 基底 Enumish + 指定 interface |
| 基底経由の asEnumish の静的型 | K | `SI.Enumish` |
| kind-when の else 省略 | 失われる | 維持 |
| 主用途 | 値側の独自基底を持つ既存階層の取り込み | kind 側へのメンバー追加 |

いずれも「生成メンバーへの干渉（具象 override・シグネチャ衝突・
型引数不一致）が無い限りユーザーの基底指定は許容する」という原則の実現形であり、以後の拡張もこの原則で判断する。

### 2.2 K の検査条件（チェッカーロジック案）

1. interface である（生成 Enumish は sealed interface であり class を継承できない）
2. 基底 Enumish のサブタイプである（`Enumized<out T : Enumish>` の境界により言語側でも強制される。先回り診断）
3. **sealed でない** — 収集器はソース宣言の sealed にしか属性を設定せず（実測。設計00 §5.2）、
   生成 Enumish が K の継承者一覧に載らないため、K が sealed だと K に対する when の網羅性が不健全になる
4. supertype 経路に生成 Enumish（自・他階層とも）・当該階層の型を含まない（循環・他階層の kind-when への汚染の禁止）
5. 経路上（基底 Enumish まで）に生成対象メンバー（label / enumizedClass / enumishCompanion）の具象実装が無い（概要 §4
   の追加基底 interface と同じ規則。abstract な共変再宣言は可。toString は 2 原則の枠内で扱う）
6. `eff(K) ≥ eff(基底)`（下回ると基底の可視範囲の一部で asEnumish の静的型が名指し不能になる）

K の abstract 追加メンバーは各 kind に実装が要求される（言語の通常規則）。  
自動生成 companion はユーザーコードを持てないため、該当する末端 class では明示的な companion
の宣言が必要になる（帰結として文書化する）。

### 2.3 成立性と代替（E-1）

生成 Enumish の実体構築時（早ければ SUPER_TYPES — 設計01 §3）までに K の ClassId が要り、
基底の解決済み supertype にこの時点で依存できるかは未検証（E-1）。  
不成立時は現行 MISMATCH のまま。  
代替として `@Enumize` の KClass パラメータで K を指定する形は、COMPILER_REQUIRED_ANNOTATIONS
で確定するため位相リスクが無い。

## 3. label の決定と名前被り（label 衝突）

label は「明示指定（`@EnumishLabel`） > 階層の `labelCase` によるケース変換 > 既定 = 末端宣言の単純名」で決まる
（優先順位の全体像・`LabelCase` のケース集合・変換規則は概要 §4）。  
ClassId の衝突は言語上定義できないため、「名前被り」とは**最終 label** の衝突であり、`ENUMIZE_LABEL_CLASH`
エラーとする（概要 §8）。回避は末端の改名、または `@EnumishLabel` による明示指定。

`@EnumishLabel(value: String)`（runtime-api・CLASS target・BINARY）の規則:

- 付与先は label の由来となる宣言（末端。companion 自身が末端ならその companion、
  末端 enum class ならその enum class 宣言）。明示指定にケース変換は適用されない
- **衝突判定は最終 label で行い**、明示指定同士・既定名との衝突に加え、
  ケース変換で初めて衝突する単純名の組（`FooBar` / `FOO_BAR` → `FOO_BAR`）も `ENUMIZE_LABEL_CLASH`。  
  空・空白の値、末端宣言以外（基底・中間 sealed・階層外・kind を担うだけの companion）への付与は
  `ENUMIZE_INVALID_LABEL`。  
  それ以外の形式制約は課さない（valueOf は完全一致照合 — 概要 §2）
- **entries の順序には影響しない**（順序は ClassId 由来 — 概要 §5）。明示指定が安定させるのは label だけ
- toString は label getter 経由のため自動追随する（設計02 §5.3 が織り込み済み）。data object の toString
  は言語合成のまま（概要 §4）
- `@EnumishLabel` は末端宣言に付くため P1 / P2 に影響しない。`@Enumize(labelCase = ...)` は基底の編集であり、
  基底の ABI 変更として末端側生成物（label / toString）の再コンパイルを誘発する。  
  label 変更が valueOf 呼び出し側の文字列を壊すことはコンパイル時に検出されない（enum の定数改名と同種）
- 末端の改名時に旧名を明示指定として与えれば、永続化済み label との互換を保てる

## 5. チェッカーエラー該当時の生成挙動

生成 NG 条件（概要 §8 の診断）に該当する階層でも、**宣言の形状生成は常に行い、診断のみで止める**（後続エラーのカスケード
は許容する）。  
診断（CHECKERS）は宣言生成より後のフェーズで走るため（設計00 §3）、
エラーになる階層でも生成宣言の形状は FIR 上に作られる（コンパイルはエラーで打ち切られ、IR の生成 — ボディ充填と kind の
toString（設計02 §5.3） — には進まない）。

個別の衝突に規定済みの「生成スキップ + 診断」（設計01 §5.1・§5.3）は、この方針の例外とする。  
階層単位のエラー（LABEL_CLASH 等）を生成時に判定して抑止する案は、フェーズ制約・
診断の単調性（設計00 §8）と両立しないため採らない。  
帰結として、エラーのある階層でも IDE では生成 API が補完・解決に現れる。
