# コンパイラプラグイン設計 01: FIR 部分の詳細

本書は FIR（フロントエンド）側の詳細設計を定める。全体感・用語（kind・手動実装・階層など）・成果物対応表・
IC 原則（P1/P2/P3）は [設計00](コンパイラプラグイン設計00.md) を前提とし、本書では再定義しない。
利用者視点の仕様は [概要.md](概要.md) を正とする。

FIR 側の責務は次の 3 つに限られる:

1. **宣言の形状**の生成 — ネスト分類子（生成 Enumish・その Companion・末端の companion）、メンバーシグネチャ、supertype 注入
2. **診断**（チェッカー）
3. 生成 Enumish への **sealed inheritors 属性の lazy 登録**

ボディは一切作らない（IR が充填する。[設計02](コンパイラプラグイン設計02.md)）。
シグネチャは継承者の集合に依存させない（P2）。

## 1. 生成宣言の契約（全拡張に共通）

K2 の宣言生成 API（Kotlin リポジトリの `docs/fir/fir-plugins.md`）の契約に従う:

- `generate*` 系コールバックは**副作用フリー**であること（IDE キャッシュがリトライしうる）
- 返す宣言は `FirResolvedDeclarationStatus` / `FirResolvedTypeRef` / BODY_RESOLVE 済み相当の状態で返すこと
- ボディは FIR では作らない（プラグインキー付き origin を立て、IR 側で充填する）
- **FIR フェーズで階層リストを計算してプラグイン内の可変状態に貯めない**（P2 / フェーズ契約違反。
  階層の列挙が必要な処理は IR 側か lazy 属性（§5.2）に閉じる）
- プラグインが生成した classifier を supertype 等で参照するときは、名前解決を経ず
  `ClassId.constructClassLikeType` で直接参照する

すべての生成宣言・生成メンバーには本プラグインの `GeneratedDeclarationKey`（以下 `EnumizeKey`）を origin として付与する。
IR 側はこのキーで充填対象を発見する。

**可視性**: 生成するネスト宣言・メンバーは**原則として `public` で宣言する**（実効可視性は外側の宣言により
自動的に制限されるため、`@Enumize` 対象より広く漏れることはない）。`@Enumize` 対象の可視性をコピーする方式は採らない。

これは「**`@Enumize` 対象が `private` であっても、その可視範囲の内側からは生成 API がすべて通常どおり参照できる**」
ことを要件とするためである（概要 §8「基底の可視性は制限ではない」）。可視性をコピーすると、たとえば
「private なトップレベル基底と、同一ファイル内の別宣言として置かれた末端」のような構成で、生成 Enumish が
基底の本体内でしか可視でなくなり、末端に注入する supertype と `asEnumish` の返り値型が不可視になって成立しない。

**例外は `$EntriesHolder` のみ**である。klib で IR-only の直列化が不成立で FIR 生成へ切り替える場合、これは `private` で生成する
（§5.1・設計00 §10.1）。参照元が同じ `SI.Enumish` の内側にある生成 Companion に限られ、外部から名指しされる
経路が存在しないため、上記の要件とは衝突しない。

## 2. 拡張の登録と述語

```kotlin
class EnumizeExtensionRegistrar : FirExtensionRegistrar() {
    override fun ExtensionRegistrarContext.configurePlugin() {
        +::EnumizeSupertypeGenerationExtension
        +::EnumizeDeclarationGenerationExtension
        +::EnumizeAdditionalCheckersExtension
    }
}
```

- `@Enumize`（`org.wrongwrong.sealedClassEnumizer.Enumize`）はトップレベルのアノテーションクラスであり、
  述語（predicate）が要求する「トップレベルアノテーション」条件を満たす
- 各拡張は `registerPredicates` で `DeclarationPredicate.create { annotated(EnumizeFqName) }` を登録する。
  これにより COMPILER_REQUIRED_ANNOTATIONS フェーズで `@Enumize` が解決され、
  `session.predicateBasedProvider` で対象クラスを判定できるようになる
- **注意**: 述語でマッチできるのは「`@Enumize` が付いた基底」だけである。末端・companion は無アノテーションのため、
  述語ではなく「自身の supertype」から階層に属するかどうかを判定する必要がある（§3・§6 のフェーズ問題）。
  ただしこれは**判定材料の話であって、コールバックが呼ばれるかどうかの話ではない**:
  `FirGeneratedMemberDeclarationsStorage.getExtensionsForClass` は非生成クラスに対して登録済みのすべての拡張を
  無条件に返すため、`getNestedClassifiersNames` 等は**述語マッチの有無に関わらず、すべてのクラスに対して呼ばれる**。
  述語によるガードはプラグイン側の自主的な絞り込みにすぎず、無アノテーションの末端にもコールバックは到達する。
- FIR の `DeclarationPredicate` に**supertype ベースのマッチは存在しない**
  （`annotated` / `metaAnnotated` / `parentAnnotated` / `ancestorAnnotated` はいずれもアノテーションと
  レキシカルな入れ子関係のみを見る）。「特定アノテーションが付いた型を継承しているクラス」を述語で拾う手段は無い。

## 3. フェーズと処理の対応

| FIR フェーズ | 本プラグインの処理 | その時点で参照してよい情報 |
|---|---|---|
| COMPILER_REQUIRED_ANNOTATIONS | （コンパイラが `@Enumize` を解決） | — |
| COMPANION_GENERATION | **ソースクラスのネスト分類子の「名前」がすべて確定する**（`getNestedClassifiersNames` の戻り値集合。object 以外の末端へ companion を自動生成するかどうかの候補判定（§6 の raw-ref 追跡）と、基底への `Enumish` の名前の両方） | 各クラスの**未解決** supertype ref・ファイルの import・symbol provider・述語マッチ・`classKind`・`rawStatus`（`resolvedStatus` は**不可**） |
| SUPER_TYPES | supertype 注入（§4）。生成 Enumish の**実体の構築**（`generateNestedClassLikeDeclaration`）は classifier が解決される時点＝早ければこの段階で走り、そこで inheritors の lazy 登録を仕掛ける（§5.2） | 処理中クラスの解決済み supertype ref（`computeAdditionalSupertypes` の引数） |
| SEALED_CLASS_INHERITORS | （コンパイラ本体がソース宣言の sealed の継承者を収集。生成 Enumish は宣言としては走査されない） | — |
| STATUS 以降（メンバースコープの解決） | メンバーシグネチャの生成（§5.3）・生成クラスを owner とするネスト分類子の生成（生成 Enumish 内の Companion 等） | 対象クラスの解決済み supertypes |
| CHECKERS | 診断（§7） | 完全解決済みの宣言 |

フェーズ順で最重要の制約は **COMPANION_GENERATION が SUPER_TYPES より前に走る**ことである。
つまり「この class は階層の末端か？」を解決済み supertype で判定できない時点で、companion を生成するかどうかを決めねばならない。

なお「COMPANION_GENERATION で確定するのは `getNestedClassifiersNames` が返す**名前の集合**であり、
`generateNestedClassLikeDeclaration` による**実体の構築**は classifier が解決される時点（早ければ SUPER_TYPES）に走る」
という区別が重要である。判定材料の制約がかかるのは前者（名前を返すか否かの決定）である。

**この制約は companion に限らず、ソースクラスへのネスト分類子の生成すべてに及ぶ**:
`FirCompanionGenerationTransformer` はモジュール内のすべてのソース `FirRegularClass` に対して `Outer.Companion` を
問い合わせるため、その過程で各クラスの `getNestedClassifiersNames` の**戻り値集合全体**が
COMPANION_GENERATION 時点で評価され、`nestedClassifierCache` に固定される。
したがって「companion をやめて別名のネスト object にする」といった回避策では制約を逃れられない。
基底への `Enumish` の生成（§5.1）が安全なのはフェーズが遅いからではなく、**述語だけで判定しているから**である
（述語は COMPILER_REQUIRED_ANNOTATIONS = COMPANION_GENERATION より前に解決済み）。

一方、`getCallableNamesForClass` / `generateFunctions` / `generateProperties`（§5.3）は STATUS 以降に走るため
この制約を受けず、解決済み supertype を自由に参照できる（kotlinx.serialization も同じ切り分けで
`resolvedSuperTypes` を実使用している）。この問題の扱いは §6 に隔離する。

## 4. FirSupertypeGenerationExtension

`computeAdditionalSupertypes`（追加のみ・除去不可）で以下を注入する:

| 対象 | 注入する supertype | 対象の判定方法 |
|---|---|---|
| `@Enumize` 対象（基底 SI） | `Enumized<SI.Enumish>` | 述語マッチ |
| 末端 object / 末端 data object | `SI.Enumish` | 自身の解決済み supertype ref から、階層に属するかどうかを判定（下記） |
| 末端の**既存** companion（外側が enum class・open / abstract class・interface・fun interface の場合を含む。**生成 companion は本表の対象外** — 下記） | `SI.Enumish` | 外側クラス（末端）が階層に属するかどうかを判定（下記） |

- 生成する型参照は `ClassId.constructClassLikeType` で構成する（`SI.Enumish` は同じプラグインが生成する
  classifier のため名前解決を経ない）。
- 生成 Enumish 自体・その Companion・**プラグインが生成する末端の companion** への supertype は
  **生成時に直接指定**する（§5.1）。本拡張はプラグイン生成の companion を訪問しないため、
  注入では kind が生成 Enumish のサブタイプにならない（既存 companion への注入は
  上表のとおり働く）。実験的 API `computeAdditionalSupertypesForGeneratedNestedClass` には依存しない。
- **階層に属するかどうかの判定**（末端 object・companion 用）: `needTransformSupertypes` / `computeAdditionalSupertypes` が
  受け取る「処理中クラスの解決済み supertype ref」を起点に、supertype が
  (a) `@Enumize` 付き sealed → 直接の末端、(b) sealed（無アノテーション）→ その supertype を再帰的に辿って
  `@Enumize` に到達すれば中間 sealed 経由の末端、と判定する。中間 sealed（別ファイル）の supertype の解決順に
  依存する場合は、raw-ref 追跡（§6 と同じ機構）を併用する。
- **companion の supertype 注入のタイミング**: companion の supertype 解決は外側クラス（末端）の supertype 解決後に
  走る（同一ファイル内で外側が先）。外側が階層に属するかどうかを判定できる前提で注入する。
- **型パラメータ付きの基底・末端**: `sealed class S<T>` も対象である。注入する `Enumized<S.Enumish>` は基底の
  型パラメータと無関係に付与できる（生成 Enumish は型パラメータを持たない。kind は `S<*>` の分類子であり、
  型引数は kind の同一性に影響しない）。型パラメータ付きの末端 class `Foo<T> : S<T>` も同様で、
  companion は型パラメータを持たないため `S.Enumish` の注入・`asEnumish()` の生成に影響しない。
- **手動継承との共存**:
  - 対象が既に**型引数まで一致する** supertype（`Enumized<SI.Enumish>` / `SI.Enumish`）を手動宣言している場合、注入をスキップする
  - 型引数が異なる場合（`Enumized<他の型>` 等）は注入せず、CHECKERS で `ENUMIZE_MANUAL_SUPERTYPE_MISMATCH` を報告する
    （照合は ClassId の一致だけでなく**型引数込み**で行う。注入してしまうと「同一の総称インターフェースを
    異なる型引数で二重に継承している」という言語エラーがユーザーへ生で露出するため、プラグイン診断で先回りする）。
    なお基底 `Enumish` は非ジェネリックなので、その手動継承が型引数の衝突を起こすことはない。
    基底 Enumish の手動実装と、階層内による生成 Enumish の実装はエラーにしない（概要 §8 の許容）。
    階層外による生成 Enumish の直接実装は ENUMIZE_MANUAL_IMPL_OUTSIDE_HIERARCHY でエラーにする（設計00 §5.2・§8）。
    検査条件を満たす `Enumized<K>` を許容し K を生成 Enumish の supertype に採用する拡張は、成立条件・検証項目
    （E-1）込みで [エッジケースへの対応方針](エッジケースへの対応方針.md) §2 が定める（E-1 不成立時は本診断のまま）

## 5. FirDeclarationGenerationExtension

### 5.1 ネスト分類子の生成

**`getNestedClassifiersNames(classSymbol)` / `generateNestedClassLikeDeclaration(owner, name)`**:

| owner | 返す名前 | 生成内容 |
|---|---|---|
| `@Enumize` 対象 SI | `Enumish` | sealed interface。modality = SEALED、visibility = Public、supertypes =［基底 `Enumish`（非ジェネリックなので型引数の構築は不要）］、origin = `EnumizeKey`。**sealed inheritors の lazy 登録**（§5.2） |
| 生成 Enumish | `Companion`（`SpecialNames.DEFAULT_NAME_FOR_COMPANION_OBJECT`） | companion object。supertypes =［`Enumish.Companion<SI.Enumish>`］、origin = `EnumizeKey`。多段ネスト生成（生成クラスの中への生成）は plugin-sandbox の `ExternalClassGenerator` と `Fir2IrConverter` の再帰処理で行われる（**コンパイラ本体側**）。ただしコンパイラ本体の `FirCompanionGenerationTransformer` はソース宣言しか走査せず、生成クラスには `companionObjectSymbol` を連結しないため、**生成時に構築して `replaceCompanionObjectSymbol` で自前連結する**（連結しないと companion 経由の短縮形 `SI.Enumish.entries` が解決されない。内部属性 `ownerGenerator` の刻印を含む実装詳細は実装ノート §2）。なお同じ構成を **Analysis API** が解決できない不具合 KT-84625（`Analysis API. FIR` / `Analysis API. Providers and Caches`。Fixed）が 2.4.0-Beta2 で修正されており、これが**実用下限 2.4 の IDE 側の根拠**である（CLI の codegen はこの修正に依存しない。§9） |
| companion を持たない末端（§6 の候補判定が真。**class / enum class / open / abstract class・interface・fun interface を含む**） | `Companion` | companion object。supertype `SI.Enumish` は**生成時に直接指定**する（§4 の注入はプラグイン生成の companion に届かない。候補判定の誤検知で supertype が誤付与される構成は、後続フェーズの正式判定に基づく診断で顕在化する）。メンバーは §5.3 のとおり解決済みの型によるガードを通して付与する。origin = `EnumizeKey` |
| 生成 Enumish（**klib で不成立の場合の代替でのみ**） | `$EntriesHolder` | object。supertypes =［`EnumishEntriesHolder<SI.Enumish>`］、visibility = **Private**（§1 の唯一の例外）、origin = `EnumizeKey`。コンストラクタは `createDefaultPrivateConstructor(generateDelegatedNoArgConstructorCall = true)` で生成する（`EnumishEntriesHolder` のコンストラクタは no-arg のため、runtime-api の変更なしにそのまま適合する = 設計00 §10.1）。`enumizedRootClass` / `createEntries` の override シグネチャも FIR で宣言し、ボディは IR で充填する（設計02 §4.2）。**既定の設計ではこの行は存在しない** — `$EntriesHolder` は IR-only で生成するためである（設計02 §4） |

- SI に既存のネスト宣言 `Enumish` がある場合は生成せず、CHECKERS で `ENUMIZE_RESERVED_NAME_CLASH` を報告する。
- **末端に既存 companion がある場合は生成しない**（流用。supertype は §4、メンバーは §5.3 で注入）。
  これは最適化ではなく**必須のガード**である: コンパイラ本体の `FirCompanionGenerationProcessor` は
  `companionObjectSymbol != null` のクラスにプラグインが companion を生成すると
  `errorWithAttachment("Plugin generated duplicated companion object: ...")` で即座に落ちる（診断ではなく内部エラー）。
  判定には `@OptIn(SymbolInternals::class)` で `owner.companionObjectSymbol` を直接読む
  （`resolvedCompanionObjectSymbol` は COMPANION_GENERATION への lazy resolve を要求するため、
  このフェーズ内からは使えない）。kotlinx.serialization / kotlin-dataframe も同じガードを置いている。

### 5.2 生成 Enumish への sealed inheritors 属性

コンパイラの `FirSealedClassInheritorsProcessor` は**ソースファイルの FIR ツリーだけ**を走査するため、
プラグインが生成したクラスが**宣言として**走査されることはない。生成 Enumish を sealed として機能させるには、
`FirRegularClass.setSealedClassInheritors` の **lazy オーバーロード**（`() -> List<ClassId>`）で
プラグイン自身が登録する:

- 登録タイミング: 生成 Enumish の構築時（SUPER_TYPES 段階で呼ばれうる）。**計算は登録せず遅延**し、
  実際の列挙は網羅性検査（CHECKERS）以降まで走らせない（SUPER_TYPES 段階で階層を列挙すると、フェーズ違反のリスクがあるため）
- 列挙内容: **生成 Enumish のすべての直接実装**（設計00 §5.2）。すなわち
  (1) すべての kind の ClassId（末端が object ならその ClassId、それ以外なら companion の ClassId）—
  基底 SI の sealed inheritors 属性（`getSealedClassInheritors`）を起点に、中間 sealed を再帰的に展開して得る —
  と、(2) 階層内の手動実装（末端 class 自身による直接実装）の ClassId である — 階層走査の過程で検出できる。
  階層外の直接実装は列挙経路が無く（収集器は生成 sealed に属性を設定しない — 実測。設計00 §5.2）、
  `ENUMIZE_MANUAL_IMPL_OUTSIDE_HIERARCHY` でエラーにするため、一覧はこの 2 種で完全である
- **並べ替えは行わず、収集した順のまま登録する**（設計00 §6.2）。
  `setSealedClassInheritors` は lazy オーバーロードも含めて**属性へ格納する時点で FQN 順にソートする**ため
  （設計00 §6.1）、プラグイン側で整える必要はない
- 生成 Enumish は sealed である。メタデータへの直列化・等値枝と `is` 枝の算入は JVM で確認済みで、
  未検証範囲（klib・利用側の再検査・短縮形・IDE）は設計00 §5.2・§10 の通りである

### 5.3 メンバーシグネチャの生成

**`getCallableNamesForClass(classSymbol)` / `generateProperties` / `generateFunctions`**:

| 対象クラス | 生成するメンバー（シグネチャのみ・ボディ無し） |
|---|---|
| 生成 Enumish | `override val enumishCompanion: SI.Enumish.Companion`（default 実装として宣言。基底の `Companion<Enumish>` を宣言側共変により具体型へ絞り込む）/ `override val enumizedClass: KClass<out SI>`（**抽象**として宣言。基底の `KClass<out Enumized<*>>` を共変絞り込みし、実装は各 kind が持つ — ボディはどこにも生成しない。型パラメータ付き基底では `KClass<out S<*>>`） |
| 生成 Enumish の Companion | `override val entries: List<SI.Enumish>` / `override fun valueOf(value: String): SI.Enumish` / `override fun valueOfOrNull(value: String): SI.Enumish?`（**`@JvmStatic` は v1 では付与しない** — 設計00 §4.1。Java からは interface 上の static フィールド `Companion` 経由） |
| 末端 object / 末端 data object | `override val label: String` / `override val enumizedClass: KClass<末端の型>` / `override fun asEnumish(): <末端の型>` |
| 末端 class（final / data / value class、および **open / abstract class**） | `override fun asEnumish(): <companion の型>`（返り値型は §5.4）。abstract / open の場合も生成先は当該 class 自身であり、**サブタイプはこの実装を継承して同じ kind に吸収される**（設計00 §4.1） |
| 末端 interface / 末端 fun interface | `override fun asEnumish(): <companion の型>` を **default 実装**として生成する（interface に本体つきメンバーを置く。JVM では default メソッドとして lowering される）。fun interface の場合、`Enumized` から継承する抽象 `asEnumish` をこの生成が埋めるため、SAM の抽象メソッドが 1 つに保たれる（この形の確認は未検証。設計00 §10） |
| 末端 enum class | `override fun asEnumish(): <companion の型>`（`ENUMIZE_ENUM_LEAF_UNSUPPORTED` は発火させず定義のみ残置） |
| kind となる companion（既存・生成とも。外側が class / enum class / interface のいずれでも同一） | `override val label: String` / `override val enumizedClass: KClass<外側の末端の型>` |

**`toString` は FIR の生成対象ではない**（宣言・ボディとも IR-only で生成する = 設計02 §5.3）。
`toString` の解決スロットは `Any` が全型に提供しており FIR 宣言なしで呼び出せるうえ、kind（object / companion）は
サブクラス化できないため、FIR 宣言の効果（解決可能性・メタデータへの掲載）に消費者が存在しない。
生成の有無の判定（概要 §4 の 2 原則）も、supertype が完全解決済みの IR 側で行う。
帰結として、kind の supertype が `toString` を**抽象再宣言**している構成では FIR に実装が無いため、
コンパイラ本体の「抽象メンバー未実装」エラーになる — kind 側の手動実装が必要である（概要 §4。
プラグイン診断は不要 — 本体エラーがそのまま修正方法を示す）。

共通事項:

- 対象クラスが階層に属するかどうかの判定は、この時点では解決済み supertypes を安全に参照できる
  （メンバースコープの解決は SUPER_TYPES より後）ため、解決済みの型で行う
- すべて `FirResolvedDeclarationStatus`（visibility = Public、modality は override に応じ FINAL / OPEN —
  生成 Enumish の `enumizedClass` のみ ABSTRACT = 上表）・解決済み型・origin = `EnumizeKey` で返す
- ユーザーが同名メンバーを手動宣言している場合は**生成せず**、CHECKERS で `ENUMIZE_MANUAL_MEMBER_CONFLICT` を報告する
  （`toString` は FIR の生成対象外であり、手動宣言があっても IR 側が生成をスキップするだけで診断はしない = §7.2・設計02 §5.3）
- 中間 sealed には何も生成しない
- kind は `enumishCompanion` を override しない（生成 Enumish の default 実装を継承する。
  返り値型が object 型 `SI.Enumish.Companion` まで絞り込まれているため、仮に利用側が override しても
  同じオブジェクトを返す以外の実装は書けない）
- **末端が非 final の場合も生成先は末端自身**である。階層外のサブタイプには何も生成しない
  （生成する必要が無い — 継承した `asEnumish` がそのまま正しい kind を返し、`enumizedClass` は
  分類の代表である末端自身の class リテラルを返す。概要 §2）。
  これは P1 とも整合する: 生成物の帰属は常に階層内のファイルに閉じ、利用側モジュールへ漏れない

### 5.4 asEnumish の返り値型の規則

末端 L・その companion C・生成 Enumish T、eff = 実効可視性として、次の順で決める
（[エッジケースへの対応方針](エッジケースへの対応方針.md) §1.3 の規則の FIR 実装。
末端 object の kind は自身を返すため常に具体型であり、本規則の対象外）:

1. `eff(C) ≥ eff(L)` — **具体型**（`Foo.Companion`）を返り値型にする（既定。生成 companion は宣言 public のため
   実効可視性が L を下回ることがなく、常にこの段になる）
2. `eff(T) ≥ eff(L)` — `SI.Enumish` へフォールバックする（例: public クラスの internal companion。具体型を使うと
   「public メンバーのシグネチャが可視性の低い型を公開する」エラーになるため）
3. いずれも満たさない — `ENUMIZE_KIND_TYPE_NOT_DENOTABLE` を報告する（§7.2。基底より広い可視性の末端で
   companion の実効可視性が末端未満の場合にのみ生じる。基底 Enumish へのさらなるフォールバックは、
   返り値型が `Enumized<T>.asEnumish` の共変 override として T のサブタイプでなければならないため成立しない）

判定は**実効可視性**で行う。生成メンバーは `public` と宣言するが実効可視性は外側の宣言に従うため（§1）、
たとえば private 基底の中の末端であれば、その companion が internal でも実効可視性は private 側が優位となり
露出エラーは起きず、フォールバックも発生しない。private / protected の既存 companion はフォールバック以前に
kind として参照不能なので `ENUMIZE_KIND_NOT_ACCESSIBLE`（§7）。

## 6. 末端への companion 自動生成（COMPANION_GENERATION の候補判定）

**問題**: companion の自動生成は COMPANION_GENERATION フェーズで行う必要があるが、その時点では
どのクラスも supertype が未解決であり、「この class は階層の末端か」を解決済み型で判定できない。

**確認済みの事実**（Kotlin 公式リポジトリのコードで確認）:

- `FirResolvePhase` の順序は RAW_FIR → IMPORTS → COMPILER_REQUIRED_ANNOTATIONS → **COMPANION_GENERATION → SUPER_TYPES** →
  SEALED_CLASS_INHERITORS → TYPES → STATUS → … であり、フェーズの契約は「上位フェーズの情報を要求してはならない」と明記されている
- CLI は「全ファイル × フェーズ N → 全ファイル × フェーズ N+1」の順で回すため、
  「別ファイルの基底なら先に解決済みかもしれない」という抜け道は存在しない
- このフェーズで `resolvedSuperTypes` を読むと、CLI では未解決 ref への unchecked cast がそのまま残って後で ClassCastException となり、
  IDE（Analysis API）では `FirLazyResolveContractViolationException` になる
- **前例調査**: kotlinx.serialization は companion を自動生成しているが、その判定は述語（対象クラス自身のアノテーション）と
  `classKind` / `rawStatus.modality` のみで、supertype を一切見ていない（sealed 階層では継承者側にも `@Serializable` を
  必須とし、階層の走査は IR まで遅延している）。plugin-sandbox の `CompanionGenerator` も判定材料は述語のみ。
  **supertype を根拠に companion を生成する前例は JetBrains 管理のプラグインに 1 件も無い**

**方針**: 判定を 2 段に分ける。

1. **候補判定（COMPANION_GENERATION・保守的）** — companion を生成するか否か**だけ**をここで決める
2. **正式判定（SUPER_TYPES 以降・解決済み型）** — supertype 注入・メンバー生成・診断はすべて解決済みの型でガードする

### 6.1 候補判定アルゴリズム（raw supertype ref の保守的追跡）

対象: companion を持たない class / interface 宣言（object・enum entry・inner class 等は対象外。enum class・open / abstract class・interface・fun interface は対象）。
**interface への companion 自動生成は COMPANION_GENERATION で行える**（`FirCompanionGenerationTransformer` が
`FirRegularClass` 全般を対象とすることによる。公式プラグインに interface へ companion を生成する前例が無い用法である）。

1. 対象 class の source 上の supertype ref から**名前**を取り出す（`FirUserTypeRef` の qualifier）
2. sealed の言語規則により、階層の supertype 候補は「同一パッケージのトップレベル」または「外側クラスのネスト」に
   限られることを利用し、名前から ClassId 候補を構成する。**候補の選択は名前解決のスコープ順に忠実**にする:
   外側クラスのネスト分類子（レキシカルに内側が優先）→ 同一パッケージのトップレベル の順で
   **最初に解決される候補のみ**を検査対象とし、外側候補への「ついで照会」はしない
   （シャドーイングによる誤検知と、階層外クラスへの照会が IC の lookup 追跡に載らないリスクの両方を避ける）。
   トップレベルに「同一ファイル」という優先段は無い（同名のトップレベル分類子は同一パッケージ内で
   再宣言エラーになるため、パッケージ内で 1 つに定まる）。ただし**明示 import は同一パッケージの
   トップレベルより優先される**ため、ファイルの import に同名で別パッケージのクラスがあれば、その名前は
   候補から外す（別パッケージの型は sealed の言語規則により階層の supertype になり得ない）
3. 候補 ClassId を symbol provider で引き、
   (a) `@Enumize` 付き（COMPILER_REQUIRED_ANNOTATIONS で解決済み）の sealed なら**候補確定**、
   (b) sealed（無アノテーション）なら中間 sealed の可能性があるため、その class の raw supertype 名を
   同じ手順で**再帰的に追跡**する（同一パッケージ内に閉じるため停止する。訪問済みガードで循環を防ぐ）
4. 候補確定した場合のみ `getNestedClassifiersNames` が `Companion` を返す（§5.1）

**実装要件（CLI / IDE の一致のため必須）**:

- 判定の入力は **COMPILER_REQUIRED_ANNOTATIONS までに確定する情報だけ**に限定する: 述語マッチ・`classKind`・
  `rawStatus`（`resolvedStatus` は STATUS フェーズを要求するため**不可**）・raw な `fir.superTypeRefs`・
  ファイルの import・symbol provider への照会
- **フェーズ非依存の純関数として実装する**。「解決済み supertype が取れればそちらを使う」という日和見的な実装は
  禁止である: `nestedClassifierCache` は CLI では失効しない恒久キャッシュだが、Analysis API では
  アクセス後 5 秒で失効し SOFT 参照で回収されうるため、フェーズに依存した判定を書くと
  **CLI と IDE で生成結果が食い違う**（同一入力に対して常に同一の答えを返すこと）

### 6.2 誤検知・見逃しの扱い

- **誤検知**（生成したが実は末端でなかった）: 空の companion が残るだけで、supertype・メンバーは
  正式判定でガードされるため注入されない。ただし FIR で生成した companion は `@Metadata` に載る ABI 要素なので、
  誤検知の発生・消滅が IC の lookup 追跡に記録されるか（clean / incremental の生成物のバイト一致を破らないか）を
  V3 で確認し、残余があればテストの既知除外として明文化する
- **見逃し**（typealias・import エイリアス経由の supertype 等、raw-ref では追えない形）: CHECKERS の
  完全性検査（「階層の末端 class に kind が無い」）で `ENUMIZE_COMPANION_REQUIRED` を報告し、
  ユーザーに `companion object` の明示的な宣言を促す。**明示的な companion は常に完全なワークアラウンド**である
- 候補判定は final class / enum class / abstract class / interface / value class で機能する。残る確認は symbol provider への照会が lookup として記録されるか（§8）だけであり、記録されない場合は自動生成を諦めて末端 class に常に明示的な companion を要求する代替をとる

## 7. チェッカー（FirAdditionalCheckersExtension）

### 7.1 実装の設計制約

- **単調性**: マルチラウンド IC では階層の部分集合ビューで CHECKERS が走るラウンドが存在しうる
  （初回ラウンドで不完全な基底が出ても次ラウンドで階層全体が揃う、というコンパイラの固定点動作）。
  診断は部分集合ビューで**偽陽性を出してはならない**。すべての検査を「見えている宣言の性質に対する条件検査」として
  実装し、「階層全体の完全性」への量化を前提にしない
- 報告位置は原則として「ユーザーが修正すべき宣言」とする（例: LABEL_CLASH は衝突する両方の末端、MANUAL_MEMBER_CONFLICT は
  当該の手動メンバー）
- メッセージには必ず「どうすれば直るか」を含める（例: COMPANION_REQUIRED → 「companion object を明示的に宣言してください」）
- 診断が発火する階層でも宣言の形状生成は行われる（生成フェーズは CHECKERS より前 — §3）。個別衝突の生成スキップ
  （§5.1・§5.3）を除き、エラーを理由に生成を抑止しない（エッジケースへの対応方針 §5）

### 7.2 診断カタログ（検査ロジック詳細）

| ID | 深刻度 | 検査対象と条件 |
|---|---|---|
| ENUMIZE_NOT_SEALED | error | `@Enumize` 付き宣言が sealed class / sealed interface でない（enum・annotation・object・非 sealed class / interface、および fun interface。sealed fun interface が言語側で許容されるかは V9 で確認し、通る場合もここでエラー） |
| ENUMIZE_ON_EXPECT | error | `@Enumize` 付き宣言が expect（v1 制限。actual ごとに階層が変わりうるため） |
| ENUMIZE_ON_ACTUAL | error | `@Enumize` 付き宣言が actual（v1 制限。生成物の注入 — supertype `Enumized<T>`・ネスト宣言 `SI.Enumish` — が expect-actual マッチングと両立するか未検証のため。概要 §7） |
| ENUMIZE_MULTIPLE_FAMILIES | error | クラスの解決済み supertype 経路上に**異なる** `@Enumize` 基底が 2 つ以上ある（兄弟階層の交差 `object X : SI1, SI2`、中間 sealed の交差を含む）。放置すると、`Enumized<A>` / `Enumized<B>` の異なる型引数による二重継承や、`asEnumish` / `enumishCompanion` の実装の衝突が言語エラーとして露出するため、先回りする |
| ENUMIZE_NESTED_IN_HIERARCHY | error | `@Enumize` 階層のメンバー（中間・末端）自身に `@Enumize` が付与されている（MULTIPLE_FAMILIES の特殊ケースだが「アノテーションを外す」という別の修正方法を案内するため個別 ID） |
| ENUMIZE_AMBIGUOUS_KIND | error | 階層内のある型が 2 つ以上の末端のサブタイプになり、kind が一意に定まらない。階層内で検出できるのは「末端どうしがサブタイプ関係にある」形（例: `abstract class A : SI` と `class B : A(), SI` — B は A の kind と自身の kind の両方に対応してしまう）。**階層外の型が複数の末端 interface を実装する形**（例: 別モジュールの `class X : SI.LeafA, SI.LeafB`）は階層のコンパイル時には検出できないが、`asEnumish()` の default 実装を 2 つ継承するため明示的な override が強制され、返り値型（`LeafA.Companion` / `LeafB.Companion`）の共通 subtype が `Nothing` しか無いため、常に例外を投げる病的な実装を除き**言語側でも成立しない**（プラグインを適用した利用側モジュールでは本診断でも報告する）。修正方法: どちらの末端に属するかを 1 つに決める |
| ENUMIZE_INNER_LEAF | error | 末端が inner class（inner class は companion を持てないという言語制約により、kind を用意できない） |
| ENUMIZE_KIND_NOT_ACCESSIBLE | error | kind が基底の本体スコープから参照できない: 別ファイルの private なトップレベルの末端、private / protected な既存 companion。（SI 内にネストされた private 末端は参照可能なので対象外） |
| ENUMIZE_KIND_TYPE_NOT_DENOTABLE | error | `asEnumish` の返り値型が構成できない: 末端の実効可視性が companion と生成 Enumish（実効可視性 = 基底）の双方を上回る（基底より広い可視性の末端 — エッジケースへの対応方針 §1 — で companion が末端未満の場合。§5.4 の規則 3）。修正方法: companion の可視性を末端以上にする、または末端の可視性を基底以下へ狭める |
| ENUMIZE_COMPANION_LEAF_CONFLICT | error | 階層の末端 class の companion 自身が同一階層の末端でもある（`class Host : SI { companion object : SI }`）。同一のオブジェクトに kind が二重に対応し、label / entries の一意性が壊れるため。※階層外クラスの companion が単独で末端になるのは許容（kind = その companion、label = companion の宣言名） |
| ENUMIZE_LABEL_CLASH | error | 2 つ以上の kind の label（既定 = 末端宣言の単純名。**companion 自身が末端である場合に限り**その宣言名、既定 `Companion`）が一致。末端 class の kind を担うだけの companion は末端ではないため、その宣言名（`Foo.Companion` / `Foo.Factory` 等）は label に影響しない。sealed の末端は同一パッケージ内の任意のクラスにネストすることが許されるため、enum と異なり単純名の衝突が起こりうる |
| ENUMIZE_MANUAL_MEMBER_CONFLICT | error | 生成対象メンバー（kind = 末端 object / 末端の companion での `label` / `enumizedClass`、生成 Enumish での `enumishCompanion` / `enumizedClass`、その Companion での `entries` / `valueOf` / `valueOfOrNull`、末端での `asEnumish`。**`toString` は対象外** — 手動実装を尊重して生成をスキップする。概要 §4・設計02 §5.3）を対象クラスが手動宣言している、**または**階層外のユーザー interface から同名メンバーの default 実装を継承している（生成した override が黙って置き換えると、ユーザーの意図を破壊するため）。「継承のみの手動宣言」として許容されるのは、supertype の宣言の重複（型引数が一致するもの）に限られる。なお生成 Enumish とその Companion は全体がプラグイン生成物であり、ユーザーがメンバーを手動宣言する構文経路も、v1 で supertype にユーザー型が入る経路も無い — この 2 つの生成先の列挙は生成対応の記録であり、実際に検査が発火しうるのは kind（末端 object・既存 companion）と末端の宣言に対してである |
| ENUMIZE_MANUAL_IMPL_OUTSIDE_HIERARCHY | error | 直接の supertype に生成 Enumish を持つクラスが、その階層のメンバー（末端 class 自身による実装を含む）でも、階層の末端の kind を担う companion でもない。sealed の継承者一覧へ反映する経路が無く、JVM では PermittedSubclasses により実行時拒否になるため先回りする（設計00 §5.2）。検査は宣言単体の supertype に対する条件検査であり単調（§7.1）。修正方法: 当該階層のメンバーにする（基底も実装する）か、supertype を外す |
| ENUMIZE_MANUAL_SUPERTYPE_MISMATCH | error | 手動宣言された `Enumized<T>` / 生成 Enumish 系 supertype の型引数が生成内容と不一致（§4。型引数込みで照合する） |
| ENUMIZE_RESERVED_NAME_CLASH | error | `@Enumize` 対象に既存のネスト宣言 `Enumish` がある |
| ENUMIZE_COMPANION_REQUIRED | error | 階層の末端 class に companion が無い（§6 の候補判定が働かなかった稀なケース。typealias / import エイリアス経由の supertype 等）。修正方法: companion object の明示的な宣言 |
| ENUMIZE_CROSS_SOURCE_SET | error | 階層の継承者が別のソースセットに存在（コンパイラ本体の診断に対する補足説明。@Enumize の文脈での意味を案内） |
| ENUMIZE_EXTENSION_SHADOWED | warning | 階層のメンバー（基底を含む）が `label` という名前の可視メンバーを宣言しており、`Enumized` の拡張プロパティが呼び出し点でシャドーイングされうる |
| ENUMIZE_ENUM_LEAF_UNSUPPORTED | error | 階層に末端 enum class が存在する（enum 末端は生成対象のため発火させず、定義のみ残置） |

**階層内の手動実装と基底 Enumish の実装は診断対象外である**（概要 §8 の許容。設計00 §8）。
許容される手動実装で作られる値は kind ではないため entries / valueOf に現れず、enum 的 API の保証を
壊さない。エラーになるのは、生成への干渉が生じる構成
（MANUAL_MEMBER_CONFLICT / MANUAL_SUPERTYPE_MISMATCH / RESERVED_NAME_CLASH）と、
階層外による生成 Enumish の直接実装（MANUAL_IMPL_OUTSIDE_HIERARCHY — 継承者一覧へ反映する経路が
無いため。設計00 §5.2）である。

### 7.3 KtDiagnosticFactory の定義方針

- `KtDiagnosticFactory*` と `RootDiagnosticRendererFactory` への登録という標準構成
- メッセージは英語（診断 ID とパラメータで機械可読性を確保）。上表の「修正方法」を含める

## 8. lookup / IC への配慮

- 通常経路（述語マッチ・解決済み supertype の参照・sealed inheritors 属性の読み取り）はコンパイラ本体の
  解決機構を通るため、`FirLookupTrackerComponent` への記録は本体側で行われる（プラグイン独自の記録は原則不要。
  階層不変条件が dirty の伝播を担う）
- 例外は §6 の候補判定における symbol provider への照会である。この照会が lookup として記録されるか
  （= 候補クラスの出現・消滅・アノテーションの変化で判定元のファイルが dirty になるか）は残る確認事項である
  （候補判定自体は機能する。IC 回帰マトリクス = V7 と併せて確認する）。
  記録されない場合は、誤検知による companion の出現条件が IC で追跡されず、clean / incremental の生成物が食い違いうる。
  そのため、スコープの解決順による候補の限定（§6.1-2）で誤検知自体を最小化した上で、残余をテストの既知除外として文書化する

## 9. IDE（Analysis API）配慮

- サードパーティの FIR プラグインはデフォルトではロードされない（KTIJ-29248）。ロードされない環境では、
  生成 API の参照箇所だけが未解決になる（P2 により被害範囲は限定される）
- ロードされる環境（KEFS 等）向けの規約: `generate*` の副作用フリー・宣言の resolved 状態・lazy 属性の
  評価タイミング（§5.2）を守ることが、CLI と IDE で挙動を一致させる前提になる
- 生成 sealed（§5.2）の網羅性が Analysis API の独自 provider で機能するかは未検証（設計00 §10）
