# コンパイラプラグイン設計 01: FIR 部分の詳細

本書は FIR（フロントエンド）側の詳細設計を定める。  
全体感・用語（kind・手動実装・階層など）・成果物対応表・IC 原則（P1/P2/P3）は [設計00](コンパイラプラグイン設計00.md)
を前提とし、本書では再定義しない。  
利用者視点の仕様は [概要.md](概要.md) を正とする。

FIR 側の責務は次の 3 つに限られる:

1. **宣言の形状**の生成 — ネスト分類子（生成 Enumish・その Companion・末端の companion）、
   メンバーシグネチャ、supertype 注入
2. **診断**（チェッカー）
3. 生成 Enumish への **sealed inheritors 属性の lazy 登録**

ボディは一切作らない（IR が充填する。[設計02](コンパイラプラグイン設計02.md)）。  
シグネチャは継承者の集合に依存させない（P2）。

## 1. 生成宣言の契約（全拡張に共通）

K2 の宣言生成 API（Kotlin リポジトリの `docs/fir/fir-plugins.md`）の契約に従う:

- `generate*` 系コールバックは**副作用フリー**であること（IDE キャッシュがリトライしうる）
- 返す宣言は `FirResolvedDeclarationStatus` / `FirResolvedTypeRef` / BODY_RESOLVE 済み相当の状態で返すこと
- ボディは FIR では作らない（プラグインキー付き origin を立て、IR 側で充填する）
- **FIR フェーズで階層リストを計算してプラグイン内の可変状態に貯めない**（P2 / フェーズ契約違反。
  階層の列挙が必要な処理は IR 側か lazy 属性（§5.2）に閉じる）
- プラグインが生成した classifier を supertype 等で参照するときは、
  名前解決を経ず `ClassId.constructClassLikeType` で直接参照する

すべての生成宣言・生成メンバーには本プラグインの `GeneratedDeclarationKey`（以下 `EnumizeKey`）を origin
として付与する。  
IR 側はこのキーで充填対象を発見する。

**可視性**: 生成するネスト宣言・メンバーは**原則として `public` で宣言する**（実効可視性は外側の宣言により自動的に制限さ
れるため、`@Enumize` 対象より広く漏れることはない）。  
`@Enumize` 対象の可視性をコピーする方式は採らない。

これは「**`@Enumize` 対象が `private` であっても、その可視範囲の内側からは生成 API がすべて通常どおり参照できる**」こと
を要件とするためである（概要 §8「基底の可視性は制限ではない」）。  
可視性をコピーすると、たとえば「private なトップレベル基底と、同一ファイル内の別宣言として置かれた末端」のような構成で、
生成 Enumish が基底の本体内でしか可視でなくなり、末端に注入する supertype と `asEnumish`
の返り値型が不可視になって成立しない。

この方針に例外は無い（`$EntriesHolder` は FIR の生成物ではない = §5.1・設計02 §4）。

## 2. 拡張の登録と述語

登録する拡張は `EnumizeFirExtensionRegistrar` のとおり 4 つ（`EnumizeHierarchyResolver`・supertype 生成・宣言生成・
チェッカー）である。

- `EnumizeHierarchyResolver` は生成拡張ではなく、**階層照会のセッション単一コンポーネント**
  （`FirExtensionSessionComponent`）である。  
  階層への所属判定・kind と label の導出・`asEnumish` の返り値型の決定（§5.4）・生成 Enumish
  の継承者の列挙（§5.2）といった階層に関する照会をここへ集約し、supertype 注入（§4）・宣言生成（§5）・
  チェッカー（§7）は `session.enumizeHierarchyResolver` でこの単一インスタンスを共有する。  
  所属判定の実体は §6.1 の raw supertype 追跡であり、照会側はフェーズを問わず同じ入口を使う。  
  label の導出は最終 label（明示 `@EnumishLabel` > 階層の `labelCase` による変換 > 単純名 — 概要 §4・
  エッジケースへの対応方針 §3）であり、プロジェクト既定（CLI オプション `labelCase`。欠落時 AS_DECLARED）は
  registrar 経由でコンストラクタへ注入される。annotation 引数（enum エントリ・文字列）の読み取りは
  チェッカーからのみ行われ、解決済みの引数マッピングを前提にできる（enum エントリはソース由来の解決済み参照と
  逆直列化形 `FirEnumEntryDeserializedAccessExpression` の両形を扱う。IR 側は同一規則を IR 上で再計算する —
  設計02 §5.2）
- `@Enumize`（`io.github.projectmapk.sealedClassEnumizer.Enumize`）はトップレベルのアノテーションクラスであり、
  述語（predicate）が要求する「トップレベルアノテーション」条件を満たす
- 各拡張と本コンポーネントは `registerPredicates` で
  `DeclarationPredicate.create { annotated(EnumizeFqName) }` を登録する。  
  これにより COMPILER_REQUIRED_ANNOTATIONS フェーズで `@Enumize` が解決され、`session.predicateBasedProvider`
  で対象クラスを判定できるようになる。  
  `@EnumishLabel` も同様に述語登録するが、これは compiler-required 化（型・引数の早期解決）のためであり、
  宣言の検出には使わない（label の読み取りはチェッカー・IR が付与先の宣言から直接行う）
- **注意**: 述語でマッチできるのは「`@Enumize` が付いた基底」だけである。  
  末端・companion は無アノテーションのため、述語ではなく「自身の
  supertype」から階層に属するかどうかを判定する必要がある（§3・§6 のフェーズ問題）。  
  ただしこれは**判定材料の話であって、コールバックが呼ばれるかどうかの話ではない**:
  `FirGeneratedMemberDeclarationsStorage.getExtensionsForClass`
  は非生成クラスに対して登録済みのすべての拡張を無条件に返すため、`getNestedClassifiersNames`
  等は**述語マッチの有無に関わらず、すべてのクラスに対して呼ばれる**。  
  述語によるガードはプラグイン側の自主的な絞り込みにすぎない。
- FIR の `DeclarationPredicate` に**supertype ベースのマッチは存在しない**（`annotated` / `metaAnnotated` /
  `parentAnnotated` / `ancestorAnnotated` はいずれもアノテーションとレキシカルな入れ子関係のみを見る）。  
  「特定アノテーションが付いた型を継承しているクラス」を述語で拾う手段は無い。

## 3. フェーズと処理の対応

| FIR フェーズ | 本プラグインの処理 | その時点で参照してよい情報 |
|---|---|---|
| COMPILER_REQUIRED_ANNOTATIONS | （コンパイラが `@Enumize` を解決） | — |
| COMPANION_GENERATION | **ソースクラスのネスト分類子の「名前」がすべて確定する**（`getNestedClassifiersNames` の戻り値集合。object 以外の末端へ companion を自動生成するかどうかの候補判定（§6 の raw-ref 追跡）と、基底への `Enumish` の名前の両方） | 各クラスの**未解決** supertype ref・ファイルの import・symbol provider・述語マッチ・`classKind`・`rawStatus`（`resolvedStatus` は**不可**） |
| SUPER_TYPES | supertype 注入（§4）。生成 Enumish の**実体の構築**（`generateNestedClassLikeDeclaration`）は classifier が解決される時点＝早ければこの段階で走り、そこで inheritors の lazy 登録を仕掛ける（§5.2）。**生成メンバーの「名前」の集合**（`getCallableNamesForClass`）もここで評価されて固定される（下記） | 処理中クラスの解決済み supertype ref（`computeAdditionalSupertypes` の引数）。ただし `getCallableNamesForClass` から見える自身の `superTypeRefs` は**未解決** |
| SEALED_CLASS_INHERITORS | （コンパイラ本体がソース宣言の sealed の継承者を収集。生成 Enumish は宣言としては走査されない） | — |
| STATUS 以降（メンバースコープの解決） | メンバーシグネチャの構築（§5.3 の `generateProperties` / `generateFunctions`）・生成クラスを owner とするネスト分類子の生成（生成 Enumish 内の Companion 等） | 対象クラスの解決済み supertypes |
| CHECKERS | 診断（§7） | 完全解決済みの宣言 |

フェーズ順で最重要の制約は **COMPANION_GENERATION が SUPER_TYPES より前に走る**ことである。  
つまり「この class は階層の末端か？」を解決済み supertype で判定できない時点で、companion
を生成するかどうかを決めねばならない。

なお「COMPANION_GENERATION で確定するのは `getNestedClassifiersNames`
が返す**名前の集合**であり、`generateNestedClassLikeDeclaration` による**実体の構築**は classifier
が解決される時点（早ければ SUPER_TYPES）に走る」という区別が重要である。  
判定材料の制約がかかるのは前者（名前を返すか否かの決定）である。

**この制約は companion に限らず、ソースクラスへのネスト分類子の生成すべてに及ぶ**: `FirCompanionGenerationTransformer`
はモジュール内のすべてのソース `FirRegularClass` に対して `Outer.Companion` を問い合わせるため、
その過程で各クラスの `getNestedClassifiersNames` の**戻り値集合全体**が COMPANION_GENERATION
時点で評価され、`nestedClassifierCache` に固定される。  
したがって「companion をやめて別名のネスト object にする」といった回避策では制約を逃れられない。  
基底への `Enumish` の生成（§5.1）が安全なのはフェーズが遅いからではなく、**述語だけで判定しているから**である（述語は
COMPILER_REQUIRED_ANNOTATIONS = COMPANION_GENERATION より前に解決済み）。

**同じ制約はメンバー名の集合にも及ぶ**（実測）: `FirSupertypeResolverVisitor` はクラスの supertype を解決する過程で、
そのクラスの生成ネスト分類子へ supertype を配るために宣言済みメンバースコープを構築し
（`addSupertypesToGeneratedNestedClasses` → `generatedNestedClassifiers` → `declaredMemberScope`）、
その中で `getCallableNamesForClass` を呼ぶ。  
**このとき解決中のクラス自身の `superTypeRefs` は未解決であり**、
戻り値の名前集合は `FirGeneratedMemberDeclarationsStorage` に固定される。  
したがって「どのメンバー名を生成するか」の判定材料も COMPANION_GENERATION
相当に限られ、**階層への所属判定は raw な supertype ref からも解決後と同じ答えを返せなければならない**（§6.1）。  
raw で追えない表記は、後続フェーズで解決済み型を見て正すことができず、メンバー生成ごと欠落する。  
一方 `generateFunctions` / `generateProperties`（§5.3）はシグネチャの構築時に走るため、
解決済み supertype を自由に参照できる。  
この問題の扱いは §6 に隔離する。

## 4. FirSupertypeGenerationExtension

`computeAdditionalSupertypes`（追加のみ・除去不可）で以下を注入する:

| 対象 | 注入する supertype | 対象の判定方法 |
|---|---|---|
| `@Enumize` 対象（基底 SI） | `Enumized<SI.Enumish>` | 述語マッチ |
| 末端 object / 末端 data object | `SI.Enumish` | 自身の解決済み supertype ref から、階層に属するかどうかを判定（下記） |
| 末端の**既存** companion（外側が enum class・open / abstract class・interface・fun interface の場合を含む。**生成 companion は本表の対象外** — 下記） | `SI.Enumish` | 外側クラス（末端）が階層に属するかどうかを判定（下記） |

- 生成する型参照は `ClassId.constructClassLikeType` で構成する（`SI.Enumish` は同じプラグインが生成する classifier
  のため名前解決を経ない）。
- 生成 Enumish 自体・その Companion・**プラグインが生成する末端の companion** への supertype は
  **生成時に直接指定**する（§5.1）。  
  本拡張はプラグイン生成の companion を訪問しないため、注入では kind が生成 Enumish のサブタイプにならない（既存
  companion への注入は上表のとおり働く）。  
  実験的 API `computeAdditionalSupertypesForGeneratedNestedClass` には依存しない。
- **階層に属するかどうかの判定**（末端 object・companion 用）: `needTransformSupertypes` / `computeAdditionalSupertypes`
  が受け取る「処理中クラスの解決済み supertype ref」を起点に、supertype が (a) `@Enumize` 付き sealed → 直接の末端、(b)
  sealed（無アノテーション）→ その supertype を再帰的に辿って `@Enumize` に到達すれば中間 sealed 経由の末端、
  と判定する。  
  中間 sealed（別ファイル）の supertype の解決順に依存する場合は、raw-ref 追跡（§6 と同じ機構）を併用する。
- **companion の supertype 注入のタイミング**: companion の supertype 解決は外側クラス（末端）の supertype
  解決後に走る（同一ファイル内で外側が先）。  
  外側が階層に属するかどうかを判定できる前提で注入する。
- **型パラメータ付きの基底・末端**: `sealed class S<T>` も対象である。  
  注入する `Enumized<S.Enumish>` は基底の型パラメータと無関係に付与できる（生成 Enumish は型パラメータを持たない。kind
  は `S<*>` の分類子であり、型引数は kind の同一性に影響しない）。  
  型パラメータ付きの末端 class `Foo<T> : S<T>` も同様で、companion は型パラメータを持たないため `S.Enumish`
  の注入・`asEnumish()` の生成に影響しない。
- **手動継承との共存**:
  - 対象が既に**型引数まで一致する** supertype（`Enumized<SI.Enumish>` / `SI.Enumish`）を手動宣言している場合、
    注入をスキップする
  - 照合は supertype の**頭・型引数とも typealias 展開後の ClassId** で行う（型引数が別名の `Enumized<A>` も、
    頭そのものが別名の `: A` も一致として扱う）。  
    型の同一性は表記に依らないため、表層の ClassId で比較すると別名が不一致と誤判定される（§6.1 の「supertype
    の書き方で末端の扱いを変えない」と同じ原則を、解決済み型の照合側でも守る）。  
    解決済み型の展開はエイリアス自身の解決状況に依存し、エイリアスが階層より先に解決されない配置（同一ファイル・
    処理順で後になる別ファイル）では展開が届かないため、頭の照合は §6.1 の raw
    追跡へ落として展開する（この配置では言語側もエイリアスを展開しないまま IR へ進むため、
    基底の supertype の頭に使うと言語側で失敗する — 概要 §7 の既知の制限）
  - 型引数が異なる場合（`Enumized<他の型>` 等）は注入せず、CHECKERS で `ENUMIZE_MANUAL_SUPERTYPE_MISMATCH`
    を報告する（照合は ClassId の一致だけでなく**型引数込み**で行う。
    注入してしまうと「同一の総称インターフェースを異なる型引数で二重に継承している」という言語エラーがユーザーへ生で露出
    するため、プラグイン診断で先回りする）。  
    なお基底 `Enumish` は非ジェネリックなので、その手動継承が型引数の衝突を起こすことはない。  
    基底 Enumish の手動実装と、階層内による生成 Enumish の実装はエラーにしない（概要 §8 の許容）。  
    階層外による生成 Enumish の直接実装は ENUMIZE_MANUAL_IMPL_OUTSIDE_HIERARCHY でエラーにする（設計00 §5.2・§8）。  
    検査条件を満たす `Enumized<K>` を許容し K を生成 Enumish の supertype に採用する拡張は、成立条件・
    検証項目（E-1）込みで [エッジケースへの対応方針](エッジケースへの対応方針.md) §2 が定める（E-1
    不成立時は本診断のまま）

## 5. FirDeclarationGenerationExtension

### 5.1 ネスト分類子の生成

**`getNestedClassifiersNames(classSymbol)` / `generateNestedClassLikeDeclaration(owner, name)`**:

| owner | 返す名前 | 生成内容 |
|---|---|---|
| `@Enumize` 対象 SI | `Enumish` | sealed interface。modality = SEALED、visibility = Public、supertypes =［基底 `Enumish`（非ジェネリックなので型引数の構築は不要）］、origin = `EnumizeKey`。**sealed inheritors の lazy 登録**（§5.2） |
| 生成 Enumish | `Companion`（`SpecialNames.DEFAULT_NAME_FOR_COMPANION_OBJECT`） | companion object。supertypes =［`EnumishCompanion<SI.Enumish>`］、origin = `EnumizeKey`。多段ネスト生成（生成クラスの中への生成）は plugin-sandbox の `ExternalClassGenerator` と `Fir2IrConverter` の再帰処理で行われる（**コンパイラ本体側**）。ただしコンパイラ本体の `FirCompanionGenerationTransformer` はソース宣言しか走査せず、生成クラスには `companionObjectSymbol` を連結しないため、**生成時に構築して `replaceCompanionObjectSymbol` で自前連結する**（連結しないと companion 経由の短縮形 `SI.Enumish.entries` が解決されない）。なお同じ構成の Analysis API 側の解決には KT-84625 の修正（2.4.0-Beta2）が要り、これが**実用下限 2.4 の IDE 側の根拠**である（CLI の codegen はこの修正に依存しない。§9） |
| companion を持たない末端（§6 の候補判定が真。**class / enum class / open / abstract class・interface・fun interface を含む**） | `Companion` | companion object。supertype `SI.Enumish` は**生成時に直接指定**する（§4 の注入はプラグイン生成の companion に届かない。候補判定の誤検知で supertype が誤付与される構成は、後続フェーズの正式判定に基づく診断で顕在化する）。メンバーは §5.3 のとおり解決済みの型によるガードを通して付与する。origin = `EnumizeKey` |

- SI に既存のネスト宣言 `Enumish` がある場合は生成せず、CHECKERS で `ENUMIZE_RESERVED_NAME_CLASH` を報告する。
- **末端に既存 companion がある場合は生成しない**（流用。supertype は §4、メンバーは §5.3 で注入）。  
  これは最適化ではなく**必須のガード**である: コンパイラ本体の `FirCompanionGenerationProcessor` は
  `companionObjectSymbol != null` のクラスにプラグインが companion を生成すると
  `errorWithAttachment("Plugin generated duplicated companion object: ...")` で即座に落ちる（診断ではなく内部エラー）。  
  判定には `@OptIn(SymbolInternals::class)` で `owner.companionObjectSymbol` を直接読む（`resolvedCompanionObjectSymbol`
  は COMPANION_GENERATION への lazy resolve を要求するため、このフェーズ内からは使えない）。  
  kotlinx.serialization / kotlin-dataframe も同じガードを置いている。
- **`$EntriesHolder` は FIR では生成しない**。  
  生成 Enumish の中への IR-only 生成であり、klib への直列化を含めて設計02 §4 が扱う（したがって §1
  の可視性方針の対象にもならない）

### 5.2 生成 Enumish への sealed inheritors 属性

コンパイラの `FirSealedClassInheritorsProcessor` は**ソースファイルの FIR ツリーだけ**を走査するため、
プラグインが生成したクラスが**宣言として**走査されることはない。  
生成 Enumish を sealed として機能させるには、`FirRegularClass.setSealedClassInheritors` の
**lazy オーバーロード**（`() -> List<ClassId>`）でプラグイン自身が登録する:

- 登録タイミング: 生成 Enumish の構築時（SUPER_TYPES 段階で呼ばれうる）。  
  **計算は登録せず遅延**し、実際の列挙は網羅性検査（CHECKERS）以降まで走らせない（SUPER_TYPES 段階で階層を列挙すると、
  フェーズ違反のリスクがあるため）
- 列挙内容: **生成 Enumish のすべての直接実装**（設計00 §5.2）。  
  すなわち (1) すべての kind の ClassId（末端が object ならその ClassId、
  それ以外なら companion の ClassId）— 基底 SI の sealed inheritors 属性（`getSealedClassInheritors`）を起点に、
  中間 sealed を再帰的に展開して得る — と、(2) 階層内の手動実装（末端 class 自身による直接実装）の ClassId である —
  階層走査の過程で検出できる。  
  階層外の直接実装は列挙経路が無く（収集器は生成 sealed に属性を設定しない — 実測。
  設計00 §5.2）、`ENUMIZE_MANUAL_IMPL_OUTSIDE_HIERARCHY` でエラーにするため、一覧はこの 2 種で完全である
- **並べ替えは行わず、収集した順のまま登録する**（設計00 §6.2）。  
  `setSealedClassInheritors` は lazy オーバーロードも含めて**属性へ格納する時点で FQN 順にソートする**ため（設計00
  §6.1）、プラグイン側で整える必要はない
- 生成 Enumish は sealed である。  
  メタデータ / klib への直列化、等値枝・`is` 枝・companion 短縮形の算入、
  利用側モジュールでの網羅性の再検査はいずれも確認済みであり、未検証範囲（IDE）は設計00 §5.2・§10 の通りである

### 5.3 メンバーシグネチャの生成

**`getCallableNamesForClass(classSymbol)` / `generateProperties` / `generateFunctions`**:

| 対象クラス | 生成するメンバー（シグネチャのみ・ボディ無し） |
|---|---|
| 生成 Enumish | `override val enumishCompanion: SI.Enumish.Companion`（default 実装として宣言。基底の `EnumishCompanion<Enumish>` を宣言側共変により具体型へ絞り込む）/ `override val enumizedClass: KClass<out SI>`（**抽象**として宣言。基底の `KClass<out Enumized<*>>` を共変絞り込みし、実装は各 kind が持つ — ボディはどこにも生成しない。型パラメータ付き基底では `KClass<out S<*>>`） |
| 生成 Enumish の Companion | `override val entries: List<SI.Enumish>` / `override fun valueOf(value: String): SI.Enumish` / `override fun valueOfOrNull(value: String): SI.Enumish?`（**`@JvmStatic` は v1 では付与しない** — 設計00 §4.1。Java からは interface 上の static フィールド `Companion` 経由） |
| 末端 object / 末端 data object | `override val label: String` / `override val enumizedClass: KClass<末端の型>` / `override fun asEnumish(): <末端の型>` |
| 末端 class（final / data / value class、および **open / abstract class**） | `override fun asEnumish(): <companion の型>`（返り値型は §5.4）。abstract / open の場合も生成先は当該 class 自身であり、**サブタイプはこの実装を継承して同じ kind に吸収される**（設計00 §4.1） |
| 末端 interface / 末端 fun interface | `override fun asEnumish(): <companion の型>` を **default 実装**として生成する（interface に本体つきメンバーを置く。JVM では default メソッドとして lowering される）。fun interface の場合、`Enumized` から継承する抽象 `asEnumish` をこの生成が埋めるため、SAM の抽象メソッドが 1 つに保たれる（ラムダによる SAM 変換がそのまま使えることを全ターゲットで実測確認済み） |
| 末端 enum class | `override fun asEnumish(): <companion の型>` |
| kind となる companion（既存・生成とも。外側が class / enum class / interface のいずれでも同一） | `override val label: String` / `override val enumizedClass: KClass<外側の末端の型>` |

**`toString` は FIR の生成対象ではない**（宣言・ボディとも IR-only で生成する = 設計02 §5.3）。  
`toString` の解決スロットは `Any` が全型に提供しており FIR 宣言なしで呼び出せるうえ、kind（object /
companion）はサブクラス化できないため、FIR 宣言の効果（解決可能性・メタデータへの掲載）に消費者が存在しない。  
生成の有無の判定（概要 §4 の 2 原則）も、supertype が完全解決済みの IR 側で行う。  
帰結として、kind の supertype が `toString` を**抽象再宣言**している構成では FIR に実装が無いため、
コンパイラ本体の「抽象メンバー未実装」エラーになる — kind 側の手動実装が必要である（概要 §4。
プラグイン診断は不要 — 本体エラーがそのまま修正方法を示す）。

共通事項:

- 対象クラスが階層に属するかどうかの判定は §6.1 の追跡で行う。  
  `generateProperties` / `generateFunctions` は解決済み supertypes を安全に参照できるが、
  名前集合を返す `getCallableNamesForClass` は SUPER_TYPES 中に呼ばれて自身の supertype が未解決でありうる（§3）ため、
  判定は raw / 解決済みのどちらの ref からも同じ答えになる必要がある
- すべて `FirResolvedDeclarationStatus`（visibility = Public、modality は override に応じ FINAL / OPEN — 生成 Enumish
  の `enumizedClass` のみ ABSTRACT = 上表）・解決済み型・origin = `EnumizeKey` で返す
- ユーザーが同名メンバーを手動宣言している場合は**生成せず**、CHECKERS で `ENUMIZE_MEMBER_CONFLICT`
  を報告する（`toString` は FIR の生成対象外であり、手動宣言があっても IR 側が生成をスキップするだけで診断はしない =
  §7.2・設計02 §5.3）
- 中間 sealed には何も生成しない
- kind は `enumishCompanion` を override しない（生成 Enumish の default 実装を継承する。
  返り値型が object 型 `SI.Enumish.Companion` まで絞り込まれているため、
  仮に利用側が override しても同じオブジェクトを返す以外の実装は書けない）
- **末端が非 final の場合も生成先は末端自身**である。  
  階層外のサブタイプには何も生成しない（生成する必要が無い — 継承した `asEnumish` がそのまま正しい kind
  を返し、`enumizedClass` は分類の代表である末端自身の class リテラルを返す。概要 §2）。  
  これは P1 とも整合する: 生成物の帰属は常に階層内のファイルに閉じ、利用側モジュールへ漏れない

### 5.4 asEnumish の返り値型の規則

末端 L・その companion C・生成 Enumish T、eff = 実効可視性として、
次の順で決める（[エッジケースへの対応方針](エッジケースへの対応方針.md) §1.3 の規則の FIR 実装。
末端 object の kind は自身を返すため常に具体型であり、本規則の対象外）:

1. `eff(C) ≥ eff(L)` — **具体型**（`Foo.Companion`）を返り値型にする（既定。
   生成 companion は宣言 public のため実効可視性が L を下回ることがなく、常にこの段になる）
2. `eff(T) ≥ eff(L)` — `SI.Enumish` へフォールバックする（例: public クラスの internal companion。
   具体型を使うと「public メンバーのシグネチャが可視性の低い型を公開する」エラーになるため）
3. いずれも満たさない — `ENUMIZE_KIND_TYPE_NOT_DENOTABLE` を報告する（§7.2。
   基底より広い可視性の末端で companion の実効可視性が末端未満の場合にのみ生じる。
   基底 Enumish へのさらなるフォールバックは、返り値型が `Enumized<T>.asEnumish` の共変 override として T
   のサブタイプでなければならないため成立しない）

判定は**実効可視性**で行う。  
生成メンバーは `public` と宣言するが実効可視性は外側の宣言に従うため（§1）、たとえば private 基底の中の末端であれば、
その companion が internal でも実効可視性は private 側が優位となり露出エラーは起きず、フォールバックも発生しない。  
private / protected の既存 companion は基底本体スコープから名前参照できないが、entries 構築は IR-only
アクセサ経由で行う（設計02 §4.3・概要 §8）ためエラーにはせず、`asEnumish` の返り値型は本規則で決まる（多くは規則 2
のフォールバック）。

## 6. 末端への companion 自動生成（COMPANION_GENERATION の候補判定）

**問題**: companion の自動生成は COMPANION_GENERATION フェーズで行う必要があるが、
その時点ではどのクラスも supertype が未解決であり、「この class は階層の末端か」を解決済み型で判定できない。

**確認済みの事実**（Kotlin 公式リポジトリのコード）:

- `FirResolvePhase` の順序は RAW_FIR → IMPORTS → COMPILER_REQUIRED_ANNOTATIONS →
  **COMPANION_GENERATION → SUPER_TYPES** → SEALED_CLASS_INHERITORS → TYPES → STATUS → … であり、
  フェーズの契約は「上位フェーズの情報を要求してはならない」と明記されている
- CLI は「全ファイル × フェーズ N → 全ファイル × フェーズ N+1」の順で回すため、
  「別ファイルの基底なら先に解決済みかもしれない」という抜け道は存在しない
- このフェーズで `resolvedSuperTypes` を読むと、CLI では未解決 ref への unchecked cast がそのまま残って後で
  ClassCastException となり、IDE（Analysis API）では `FirLazyResolveContractViolationException` になる
- **前例調査**: kotlinx.serialization は companion を自動生成しているが、
  その判定は述語（対象クラス自身のアノテーション）と `classKind` / `rawStatus.modality` のみで、supertype
  を一切見ていない（sealed 階層では継承者側にも `@Serializable` を必須とし、階層の走査は IR まで遅延している）。  
  plugin-sandbox の `CompanionGenerator` も判定材料は述語のみ。  
  **supertype を根拠に companion を生成する前例は JetBrains 管理のプラグインに 1 件も無い**

**方針**: 判定を 2 段に分ける。

1. **候補判定（COMPANION_GENERATION）** — companion を生成するか否か**だけ**をここで決める。  
   判定材料は §6.1 の raw 追跡であり、これは階層への所属判定が使うものと同一である（supertype
   の書き方で末端の扱いを変えないため）
2. **正式判定（SUPER_TYPES 以降・解決済み型）** — supertype 注入・メンバーの構築・
   診断は解決済みの型でガードする（生成メンバーの**名前の集合**だけは §3 のとおり raw 段階で確定する）

### 6.1 候補判定アルゴリズム（raw supertype ref の追跡）

対象: **手動宣言の** companion を持たない class / interface 宣言（object・enum entry・inner class 等は対象外。enum
class・open / abstract class・interface・fun interface は対象）。  
自動生成した companion が既に連結されているクラスは対象のままである（下記の実装要件）。  
**interface への companion 自動生成は COMPANION_GENERATION で行える**（`FirCompanionGenerationTransformer` が
`FirRegularClass` 全般を対象とすることによる。公式プラグインに interface へ companion を生成する前例が無い用法である）。

1. 対象 class の source 上の supertype ref から**名前**を取り出す（`FirUserTypeRef` の qualifier）
2. 名前から ClassId 候補を構成する。  
   **候補の選択は名前解決のスコープ順に忠実**にする: 外側クラスのネスト分類子（レキシカルに内側が優先）→ ファイルの明示
   import → 同一パッケージのトップレベル → star import の順で **最初に解決される候補のみ**を検査対象とし、
   外側候補への「ついで照会」はしない（シャドーイングによる誤検知と、
   階層外クラスへの照会が IC の lookup 追跡に載らないリスクの両方を避ける）。  
   トップレベルに「同一ファイル」という優先段は無い（同名のトップレベル分類子は同一パッケージ内で再宣言エラーになるた
   め、パッケージ内で 1 つに定まる）。  
   **明示 import は同一パッケージのトップレベルより優先される**ため、名前がファイルの明示 import に束縛されていれば、
   その import 先だけが候補になる（辿れない場合も後続の候補へは落とさない）。  
   import 先は別パッケージでもそのまま候補とする — 別パッケージの **クラス**は sealed の言語規則により階層の supertype
   になり得ないので探索はそこで止まるが、**typealias は別パッケージにあっても展開先が階層の基底になりうる**ためである。  
   スコープ順で解決できない名前は、パッケージ名から書かれた**FQN 表記**として解釈する（同一パッケージ配下のネスト参照 →
   トップレベル宣言 の 2 形を候補とする。typealias は言語規則によりトップレベル限定のため、
   別パッケージのエイリアスもこの 2 形で届く）
3. 候補 ClassId を symbol provider で引き、(a) `@Enumize` 付き（COMPILER_REQUIRED_ANNOTATIONS で解決済み）の sealed
   なら**候補確定**、(b) sealed（無アノテーション）なら中間 sealed の可能性があるため、
   その class の raw supertype 名を同じ手順で**再帰的に追跡**する（中間 sealed は言語規則により同一パッケージに閉じる。
   エイリアスの展開を含めて訪問済みガードで循環を防ぐ）
4. 候補確定した場合のみ `getNestedClassifiersNames` が `Companion` を返す（§5.1）

**この追跡は候補判定だけのものではない**。  
§3 のとおり階層への所属判定は SUPER_TYPES 中にも（`getCallableNamesForClass` 経由で、
自身の supertype が未解決のまま）確定するため、**supertype の表記は raw 段階ですべて解決できなければならない**（上記のス
コープ順・FQN 表記・typealias / import エイリアスの展開）。  
追跡から漏れた表記は companion 自動生成を落とすだけでは済まず、supertype 注入・メンバー生成・
診断のすべてが欠落して「階層に属さない末端」になる（＝コンパイラ本体の abstract member 未実装エラーに合流する）。  
このため**候補判定と所属判定は同じ追跡を使い、supertype の書き方で末端の扱いを変えない**。

**実装要件（CLI / IDE の一致のため必須）**:

- 判定の入力は **COMPILER_REQUIRED_ANNOTATIONS までに確定する情報だけ**に限定する:
  述語マッチ・`classKind`・`rawStatus`（`resolvedStatus` は STATUS フェーズを要求するため**不可**）・raw な
  `fir.superTypeRefs`・typealias の raw な `expandedTypeRef`・ファイルの import・symbol provider への照会
- 基底判定のアノテーション照合（述語の補完。IC ラウンド外のファイル由来 = 前ラウンドのメタデータからの
  逆直列化は述語にマッチしないため、BINARY で残る `@Enumize` を直接照合して拾う）は、
  **未解決の型参照を許容する**形で実装する。  
  本判定は SUPER_TYPES 中にも呼ばれ、その時点のソース宣言には型未解決のアノテーション
  （述語登録済みの `@Enumize` / `@EnumishLabel` と組み込みの compiler-required 以外の任意のユーザー
  アノテーション）が付きうる。標準の `hasAnnotation` は各アノテーションの `coneType` 取得で
  未解決参照に対して ICE になるため使えない（`coneTypeSafe` による読み飛ばし。読み飛ばしが安全なのは、
  ソース由来の `@Enumize` は述語登録の効果で常に解決済みであり、この照合が観測すべき参照は
  解決済みに限られるためである）
- **フェーズ非依存の純関数として実装する**。  
  「解決済み supertype が取れればそちらを使う」という日和見的な実装は禁止である: `nestedClassifierCache` は CLI
  では失効しない恒久キャッシュだが、Analysis API ではアクセス後 5 秒で失効し SOFT 参照で回収されうるため、
  フェーズに依存した判定を書くと **CLI と IDE で生成結果が食い違う**（同一入力に対して常に同一の答えを返すこと）
- **自前の生成結果を判定の入力にしない**。  
  `companionObjectSymbol` は判定材料だが、見るのは「手動宣言の companion
  があるか」だけであり、`FirCompanionGenerationProcessor` が連結した **生成 companion の有無で答えを変えてはならない**。  
  `getNestedClassifiersNames` は COMPANION_GENERATION 後にも再評価される — KMP では宣言側（common
  フラグメント）とは別のセッションが直列化時にネスト分類子スコープを構築し直し、その場でネスト分類子名の集合を問い直す。  
  生成済みを理由に候補から外すと、そこで名前集合が空になり **companion がメタデータ / klib のネスト索引から落ちる**（別
  コンパイレーションからの名指しが解決不能になる。§5.1）

### 6.2 誤検知・見逃しの扱い

- **誤検知**（生成したが実は末端でなかった）: 空の companion が残るだけで、supertype・
  メンバーは正式判定でガードされるため注入されない。  
  FIR で生成した companion は `@Metadata` に載る ABI 要素だが、候補判定のスコープ解決を変える跨ファイル編集で
  clean / incremental の生成物のバイト一致が保たれることは実測確認済みである（§8）
- **見逃し**: 候補判定は所属判定と同じ追跡（§6.1）を使うため、**supertype の表記に由来する見逃しは持たない**（typealias・import
  エイリアス・FQN 表記・star import のいずれでも companion は自動生成される）。  
  名前解決が届かない表記が仮に残る場合、それは候補判定だけでなく所属判定ごと成立せず、
  生成も診断も行われないままコンパイラ本体の abstract member 未実装エラーになる（§6.1）。  
  したがって「階層の末端 class に kind が無い」という完全性検査は成立せず、
  専用診断（`ENUMIZE_COMPANION_REQUIRED`）は**持たない**。  
  明示的な `companion object` はそのまま kind として流用される
- 候補判定は final class / enum class / abstract class / interface / value class で機能する。
  エイリアス経由の supertype では、判定が依存する先に**エイリアス宣言のファイル**も含まれる
  （エイリアスの張り替えが末端の生成物を変えるため）。
  ただし `asEnumish` などのメンバー生成も同じ依存を持つため、依存の種類が増えるわけではない。
  この依存が IC で追跡されること（エイリアスの付け替え・宣言ファイルの張り替えで判定元が dirty になり
  clean / incremental の生成物一致を保つこと）は実測確認済みである（§8）

## 7. チェッカー（FirAdditionalCheckersExtension）

### 7.1 実装の設計制約

- **単調性**: マルチラウンド IC では階層の部分集合ビューで CHECKERS
  が走るラウンドが存在しうる（初回ラウンドで不完全な基底が出ても次ラウンドで階層全体が揃う、
  というコンパイラの固定点動作）。  
  診断は部分集合ビューで**偽陽性を出してはならない**。  
  すべての検査を「見えている宣言の性質に対する条件検査」として実装し、「階層全体の完全性」への量化を前提にしない
- **1 ラウンドの診断の集合は clean ビルドと一致するとは限らない**。  
  報告先が検査中の宣言に限られる以上、当事者のファイルがそのラウンドに入らなければ報告は後続ラウンドへ回る（実測:
  新規ファイルで同名末端を 2 つ追加した基底不在ラウンドは `ENUMIZE_LABEL_CLASH` を報告するが、
  利用側の kind-when の網羅性エラーはそのラウンドには現れない）。  
  単調性が禁じるのは偽陽性であり、報告の遅延は許容する
- 報告位置は原則として「ユーザーが修正すべき宣言」とする（例: LABEL_CLASH は衝突する両方の末端、MEMBER_CONFLICT
  は手動宣言なら当該メンバー・継承のみなら継承しているクラスの宣言）
- **報告先は検査中の宣言に限る**: 診断の座標系は検査中のファイルに紐づくため、
  他ファイルの宣言の `source` で報告するとそのオフセットが検査中ファイルの座標として解釈され、無関係な位置に付く。  
  階層全体を見て判定する検査も、報告は「当事者それぞれの検査時に自分の宣言へ」行う（LABEL_CLASH は末端側で、
  自分の label が階層内の他の末端と衝突しているかを判定する）。  
  この形は IC の部分集合ビューとも整合し、当該ラウンドでコンパイルされる当事者に必ず報告が出る
- メッセージには必ず「どうすれば直るか」を含める（例: RESERVED_NAME_CLASH → 「既存のネスト宣言を改名してください」）
- 診断が発火する階層でも宣言の形状生成は行われる（生成フェーズは CHECKERS より前 — §3）。  
  個別衝突の生成スキップ（§5.1・§5.3）を除き、エラーを理由に生成を抑止しない（エッジケースへの対応方針 §5）

### 7.2 診断カタログ（検査ロジック詳細）

| ID | 深刻度 | 検査対象と条件 |
|---|---|---|
| ENUMIZE_NOT_SEALED | error | `@Enumize` 付き宣言が sealed class / sealed interface でない（enum・annotation・object・非 sealed class / interface・fun interface）。`sealed fun interface` は言語側が拒否するため本診断には到達しない |
| ENUMIZE_ALIASED_ANNOTATION | error | `@Enumize` が typealias / import 別名の表記で付与されている。述語（基底認識）はエイリアス展開前の COMPILER_REQUIRED_ANNOTATIONS で確定するため、この表記では生成が一切走らない。CHECKERS では解決済みアノテーションとして観測できるため、「述語不一致かつ解決済み照合が一致」という差分で検出し、静かな非生成を許さない（FQN 表記・通常 import は述語に載り生成へ到達する）。エイリアス表記の受理（候補判定への raw エイリアス追跡の拡張）は将来判断 |
| ENUMIZE_ON_EXPECT | error | `@Enumize` 付き宣言が expect（v1 制限。actual ごとに階層が変わりうるため） |
| ENUMIZE_ON_ACTUAL | error | `@Enumize` 付き宣言が actual（v1 制限。生成物の注入 — supertype `Enumized<T>`・ネスト宣言 `SI.Enumish` — が expect-actual マッチングと両立するか未検証のため。概要 §7） |
| ENUMIZE_MULTIPLE_HIERARCHIES | error | クラスが sealed 連鎖を辿って到達する**異なる** `@Enumize` 基底を 2 つ以上持つ（兄弟階層の交差 `object X : SI1, SI2`、中間 sealed の交差を含む）。放置すると、`Enumized<A>` / `Enumized<B>` の異なる型引数による二重継承や、`asEnumish` / `enumishCompanion` の実装の衝突が言語エラーとして露出するため、先回りする |
| ENUMIZE_NESTED_IN_HIERARCHY | error | `@Enumize` 階層のメンバー（中間・末端）自身に `@Enumize` が付与されている（MULTIPLE_HIERARCHIES の特殊ケースだが「アノテーションを外す」という別の修正方法を案内するため個別 ID） |
| ENUMIZE_AMBIGUOUS_KIND | error | 階層内のある型が 2 つ以上の末端のサブタイプになり、kind が一意に定まらない。階層内で検出できるのは「末端どうしがサブタイプ関係にある」形（例: `abstract class A : SI` と `class B : A(), SI` — B は A の kind と自身の kind の両方に対応してしまう）。**階層外の型が複数の末端 interface を実装する形**（例: 別モジュールの `class X : SI.LeafA, SI.LeafB`）は階層のコンパイル時には検出できないが、`asEnumish()` の default 実装を 2 つ継承するため明示的な override が強制され、返り値型（`LeafA.Companion` / `LeafB.Companion`）の共通 subtype が `Nothing` しか無いため、常に例外を投げる病的な実装を除き**言語側でも成立しない**（プラグインを適用した利用側モジュールでは本診断でも報告する）。修正方法: どちらの末端に属するかを 1 つに決める |
| ENUMIZE_INNER_LEAF | error | 末端が inner class（inner class は companion を持てないという言語制約により、kind を用意できない） |
| ENUMIZE_KIND_TYPE_NOT_DENOTABLE | error | `asEnumish` の返り値型が構成できない: 末端の実効可視性が companion と生成 Enumish（実効可視性 = 基底）の双方を上回る（基底より広い可視性の末端 — エッジケースへの対応方針 §1 — で companion が末端未満の場合。§5.4 の規則 3）。修正方法: companion の可視性を末端以上にする、または末端の可視性を基底以下へ狭める |
| ENUMIZE_COMPANION_LEAF_CONFLICT | error | 階層の末端 class の companion 自身が同一階層の末端でもある（`class Host : SI { companion object : SI }`）。同一のオブジェクトに kind が二重に対応し、label / entries の一意性が壊れるため。※階層外クラスの companion が単独で末端になるのは許容（kind = その companion、label = companion の宣言名） |
| ENUMIZE_LABEL_CLASH | error | 2 つ以上の kind の**最終 label**（明示 `@EnumishLabel` > 階層の `labelCase` による変換 > 既定 = 末端宣言の単純名。**companion 自身が末端である場合に限り**その宣言名、既定 `Companion`。概要 §4・エッジケースへの対応方針 §3）が一致。明示指定同士・明示指定と既定名の衝突、ケース変換で初めて衝突する単純名の組（`FooBar` / `FOO_BAR`）を含む。末端 class の kind を担うだけの companion は末端ではないため、その宣言名（`Foo.Companion` / `Foo.Factory` 等）は label に影響しない。sealed の末端は同一パッケージ内の任意のクラスにネストすることが許されるため、enum と異なり単純名の衝突が起こりうる |
| ENUMIZE_INVALID_LABEL | error | `@EnumishLabel` の不正: 値が空・空白のみ、または付与先が label の由来となる末端宣言でない（基底・中間 sealed・階層外クラス・kind を担うだけの companion への付与）。付与先の判定は「1 つ以上の階層に sealed 連鎖で到達し、かつ自身が非 sealed」で行い、複数階層所属のエラー構成では MULTIPLE_HIERARCHIES に委ねて重ねては報告しない。空白の明示 label は label の決定上は無指定と同じ扱いへ倒し、衝突判定を安定させる（エッジケースへの対応方針 §3）。検査は専用チェッカー（EnumizeEnumishLabelChecker）が担う |
| ENUMIZE_MEMBER_CONFLICT | error | 生成対象メンバー（kind = 末端 object / 末端の companion での `label` / `enumizedClass`、生成 Enumish での `enumishCompanion` / `enumizedClass`、その Companion での `entries` / `valueOf` / `valueOfOrNull`、末端での `asEnumish`。**`toString` は対象外** — 手動実装を尊重して生成をスキップする。概要 §4・設計02 §5.3）を対象クラスが手動宣言している、**または**階層外のユーザー interface から同名メンバーの default 実装を継承している（生成した override が黙って置き換えると、ユーザーの意図を破壊するため）、**または**クラス supertype（階層内外を問わない）から final 具象メンバーを継承している（生成 override が final を踏み、コンパイル通過後の実行時クラスロードで IncompatibleClassChangeError になるため。検査は JVM シグネチャが実際に衝突する宣言種別 — `label` / `enumizedClass` はプロパティ・`asEnumish` は引数もレシーバも無い関数 — の非 private final に限る。open 具象は生成 override が勝つため許容・Java 親クラス由来は言語の Accidental override 検査が塞ぐ）。「継承のみの手動宣言」として許容されるのは、supertype の宣言の重複（型引数が一致するもの）に限られる。なお生成 Enumish とその Companion は全体がプラグイン生成物であり、ユーザーがメンバーを手動宣言する構文経路も、v1 で supertype にユーザー型が入る経路も無いため、実際に検査が発火しうるのは kind（末端 object・既存 companion）と末端の宣言である |
| ENUMIZE_MANUAL_IMPL_OUTSIDE_HIERARCHY | error | 直接の supertype に生成 Enumish を持つクラスが、その階層のメンバー（末端 class 自身による実装を含む）でも、階層の末端の kind を担う companion でもない。sealed の継承者一覧へ反映する経路が無く、JVM では PermittedSubclasses により実行時拒否になるため先回りする（設計00 §5.2）。検査は宣言単体の supertype に対する条件検査であり単調（§7.1）。修正方法: 当該階層のメンバーにする（基底も実装する）か、supertype を外す |
| ENUMIZE_MANUAL_SUPERTYPE_MISMATCH | error | 手動宣言された `Enumized<T>` / 生成 Enumish 系 supertype の型引数が生成内容と不一致（§4。型引数込みで照合する） |
| ENUMIZE_RESERVED_NAME_CLASH | error | `@Enumize` 対象に既存のネスト宣言 `Enumish` がある |
| ENUMIZE_EXTENSION_SHADOWED | warning | 階層のメンバー（基底を含む）が `label` という名前の可視メンバーを宣言または継承しており、`Enumized` の拡張プロパティが呼び出し点でシャドーイングされうる。実害はメンバーの由来に依らないため継承経路（階層外 interface の default 実装・基底の宣言）も検査する。対象外は 2 つ — Enumish 由来の `label`（runtime-api `Enumish` と生成 Enumish。kind の値そのものを返す）と、kind 自身（末端 object）が継承する `label`（生成される `label` が override する）。報告位置は自クラスの宣言があればそのメンバー、継承のみなら当該クラスの宣言（§7.1）で、いずれもメッセージが宣言元のクラスを示す |

**階層の継承者が別ソースセットにある構成に対する補足診断は持たない**（コンパイラ本体の診断に委ねる。設計00 §7）。  
別ソースセットの継承者は基底の sealed 継承者一覧に載らない —
載らないからこそ言語エラー（`Extending sealed classes or interfaces from a different module is prohibited.`）になる —
ため、継承者一覧を辿るプラグインの検査からは原理的に観測できない。  
本体の診断が sealed の同一モジュール制約を明示しており補足の必要性も薄いため、
プラグイン側の診断は設けない（TC-DIAG-061 / TC-MPP-051 は言語エラーへの合流を固定する）。

**階層内の手動実装と基底 Enumish の実装は診断対象外である**（概要 §8 の許容。設計00 §8）。  
許容される手動実装で作られる値は kind ではないため entries / valueOf に現れず、enum 的 API の保証を壊さない。  
エラーになるのは、生成への干渉が生じる構成（MEMBER_CONFLICT / MANUAL_SUPERTYPE_MISMATCH /
RESERVED_NAME_CLASH）と、階層外による生成 Enumish の直接実装（MANUAL_IMPL_OUTSIDE_HIERARCHY —
継承者一覧へ反映する経路が無いため。設計00 §5.2）である。

### 7.3 メッセージの方針

診断 ID とメッセージの定義は `EnumizeErrors` / `EnumizeErrorMessages` が持つ。  
メッセージは英語（診断 ID とパラメータで機械可読性を確保）とし、上表の「修正方法」を含める。

## 8. lookup / IC への配慮

- 通常経路（述語マッチ・解決済み supertype の参照・sealed inheritors
  属性の読み取り）はコンパイラ本体の解決機構を通るため、`FirLookupTrackerComponent`
  への記録は本体側で行われる（プラグイン独自の記録は原則不要。
  既存 kind を触る編集では階層不変条件が dirty の伝播を担う。
  新規末端の追加と中間 sealed の単独編集では基底ファイルがラウンドに入らない = 設計00 §1）
- 例外は §6 の候補判定における symbol provider への照会である。  
  この照会の帰結 — スコープ解決を変える跨ファイル編集（typealias の付け替え・宣言ファイルの張り替え・
  同一パッケージの囮の削除）で判定元のファイルが dirty になり、clean / incremental の生成物のバイト一致と
  失敗パリティが保たれること — は実測確認済みである（ケース06 の BLD-45）。  
  スコープの解決順による候補の限定（§6.1-2）は、照会先を名前解決と同じ範囲に保つ前提として維持する

## 9. IDE（Analysis API）配慮

- サードパーティの FIR プラグインはデフォルトではロードされない（KTIJ-29248）。  
  ロードされない環境では、生成 API の参照箇所だけが未解決になる（P2 により被害範囲は限定される）
- ロードされる環境（KEFS 等）向けの規約: `generate*` の副作用フリー・
  宣言の resolved 状態・lazy 属性の評価タイミング（§5.2）を守ることが、CLI と IDE で挙動を一致させる前提になる
- 生成 sealed（§5.2）の網羅性が Analysis API の独自 provider で機能するかは未検証のまま
  **検証対象外と判断済み**である（CLI 側の網羅性は確定済み）
