# 実装ノート（プロダクションコード v1）

本書は設計資料（[設計00](コンパイラプラグイン設計00.md)・[設計01](コンパイラプラグイン設計01.md)・[設計02](コンパイラプラグイン設計02.md)・[エッジケースへの対応方針](エッジケースへの対応方針.md)）
に書かれていない、**プロダクションコード固有の実装事項**を記録する。  
仕様の正は各設計資料が持ち、V 項目の検証状況は設計00 §10（未検証範囲）が持つ。  
本書は他資料への**補足**であり、参照は常に本書から他資料へ向かう（ソースコードおよび設計資料・概要・
テスト資料から本書を参照しない。それらが要する内容は各資料自身が持つ）。  
実測環境: Kotlin 2.4.20-Beta1（K2 / JVM）・Gradle 9.6.1。

## 1. モジュール構成と検証状態

- `runtime-api`（MPP: jvm / js / wasmJs / wasmWasi / linuxX64 / mingwX64 / macosX64 /
  macosArm64）・`compiler-plugin`・`gradle-plugin`（plugin id `io.github.projectmapk.sealed-class-enumizer`）を実装済み。  
  パッケージルートは `io.github.projectmapk.sealedClassEnumizer`（group=io.github.projectmapk に統一）。  
  `compiler-plugin` の単体テストは名前定数と runtime-api 宣言の一致検証（`EnumizeNamesTest`。§2-6）のみで、
  生成挙動の検証は `integration-test` が持つ。
- `integration-test` は[テスト戦略](test/テスト戦略.md)の構成どおり独立 composite build
  として、**8 モジュールすべてを実装済み**である。
  - `producer-jvm`: 同一モジュール box 92 テスト（19 クラス）。  
    フィクスチャは合成階層をケース群毎のサブパッケージ（si / zoo / enumleaf / vis.* / order.* / manual.* 等・
    約 21 群）へ分けて置く（[フィクスチャ構成](test/フィクスチャ構成.md) §1）。  
    sealed の同一パッケージ制約は群単位の配置で保たれ、階層内の FQN 相対順序も変わらない。
  - `consumer-pure-jvm`（未適用・30）/ `consumer-plugin-jvm`（適用・7）/ `downstream-subtype-jvm`（6）/
    `java-consumer`（Java 21・8）: 跨モジュール参照・else 無し kind-when（V1-a。companion 短縮形の枝はプラグイン適用側の
    `consumer-plugin-jvm` が持つ）・E-2 外部観測・非 final 末端の下流吸収・Java 相互運用（Companion フィールド経由・
    網羅 switch・static アクセサ不在の固定）。
  - `mpp-producer`（55）/ `mpp-consumer`（12）: jvm / js / wasmJs / wasmWasi / mingwX64（ホスト依存）の全ターゲット box と
    metadata（V5）・中間ソースセット（webMain）・跨モジュール共通コード参照。
  - `gradle-integration`: TestKit 137 テスト（17 クラス・フィクスチャ 27）。  
    診断は束ねフィクスチャ（diag-fail / diag-ok / diag-cross / diag-mpp）を 1 ビルドで全件行位置照合し、
    IC 回帰 / 決定性 / ABI 伝播 / 旧バイナリ差し替え / 基底不在ラウンド / 実挙動固定プローブ（probe-*）を持つ
    （[フィクスチャ構成](test/フィクスチャ構成.md) §3）。  
    フィクスチャは親ビルドを composite 参照せず、ローカル Maven へ公開した成果物から座標で解決する（TestKitHarness）。
- runtime-api の明示宣言は、プロジェクト参照の消費側では持たない（gradle-plugin が runtime-api を api で自動公開する —
  概要 §7）。  
  推移メタデータを持たない依存形態など、別要因で要するモジュールのみが持つ。
- 仕様と実挙動の乖離は[修正方針案](修正方針案.md)が持つ。  
  該当テストは仕様どおりのアサートのまま `@Ignore` / `@Disabled` とする。

## 2. 実装固有の事項（設計資料に無い実装詳細）

1. **生成 Enumish の companion 連結における `ownerGenerator` の刻印**（設計01 §5.1 の companion 自前連結に対応する）。  
   生成した companion を `replaceCompanionObjectSymbol` で自前連結する際、`FirGeneratedScopes.getExtensionsForClass`
   が要求する内部属性 `ownerGenerator` は provider 経由でしか刻印されない。  
   `EnumizeOwnerGeneratorPatch` がリフレクションで刻印する（Kotlin のマイナーバージョン毎のアーティファクト分割 — 概要
   §7 — の下でバージョンに固定される）。
2. **生成プロパティの backing field の除去**。  
   FIR の生成宣言が default アクセサ形（`FirDefaultPropertyGetter`）のため、Fir2Ir が backing field
   を実体化することがあり、interface 上ではインスタンスフィールドとなって不正な class file（`ClassFormatError`）になる。  
   IR のボディ充填時に `backingField = null` で除去する。
3. **`CompilerPluginRegistrar.pluginId`** は 2.4 系で必須の abstract プロパティである。
4. **`ENUMIZE_MANUAL_IMPL_OUTSIDE_HIERARCHY` の対象認識は origin だけに依らない**。  
   `FirDeclarationOrigin.Plugin` は IC ラウンド外のファイル由来（前ラウンドのメタデータからの逆直列化）では失われる。  
   階層外の手動実装はラウンドを跨いで参照されるため、対象認識は「@Enumize 付き基底の直下の
   `Enumish`」という構造判定で行う（基底がラウンドに入らないラウンドは実在するため、origin
   だけに依る判定は階層メンバーについても安全でない）。  
   `@Enumize` の判定も述語（ソース宣言限定）に加えて、アノテーションの直接照合（Retention が BINARY
   のためメタデータに残る）で補う。  
   IC ラウンド（基底ファイルがラウンド外）でも発火することを確認済み。
5. **参照不能 kind の IR-only アクセサの klib 直列化**（設計02 §4.3）。  
   `EnumizeKindAccessorIrGenerator` が末端クラス内ネスト `object`（`get()`）または末端ファイルのトップレベル
   `internal fun` として IR-only アクセサを生成する。  
   **既存の IrFile へのトップレベル IR-only 宣言の追加・ユーザークラスへの IR-only ネスト object の追加が、全 klib ターゲット（js / native / wasmJs / wasmWasi）の直列化・リンクを通ること**を
   mpp-producer で実測した（`$EntriesHolder`（生成クラス内へのネスト）の klib 直列化は設計02 §4.1
   のとおり実測確認済みであり、本項はより制約の強い配置 — 既存 IrFile へのトップレベル追加・
   ユーザークラスへのネスト追加 — まで通ることの確認である）。  
   アクセサの `get()` は internal 宣言のため JVM では名前マングリングされるが、
   同一モジュールの `createEntries` からの呼び出しは IR シンボル参照で解決される。
6. **プラグイン本体は runtime-api をロードせず、名前定数はリテラルで持つ**。  
   `EnumizeNames` の値は `Name.identifier` のリテラルであり、compiler-plugin は runtime-api へ `testImplementation`
   でしか依存しない。  
   公式・著名プラグインと同じ構成である（kotlinx-serialization / Compose / assignment はいずれも POM に依存を持たず、jar
   にも runtime のクラスを含まない。アノテーション引数名も serialization は `AnnotationParameterNames`
   にリテラルで持つ。Poko は annotations を `testImplementation` にのみ持ち、
   アノテーション FQN は CLI オプションで受ける）。  
   宣言をロードして名前を導出する構成も成立はするが、**Kotlin/Native のコンパイラプラグインクラスパスは推移依存を解決しない**（JVM
   / JS とは異なる。実測: 依存として配ると `compileKotlinMingwX64` が `ClassNotFoundException` になる）ため plugin jar
   への同梱が必須になり、relocation で ClassId が静かにずれる経路を抱える。  
   リテラルと runtime-api の宣言の一致は `EnumizeNamesTest` が担保する。  
   宣言側の参照から期待値を組み立てて 1 回の `assertEquals` で比較するため、改名すると失敗して更新漏れを検知できる。  
   宣言元の外から参照できない protected メンバー（`enumizedRootClass` / `createEntries`）はテスト内の
   `EnumizeEntriesHolderProbe`（可視性を広げた `abstract override` のみ）を経由し、
   値引数名（`valueOf` の `value`）はテストにのみ入れた kotlin-reflect で取得する。

## 3. 敵対的検証（診断テスト）で発見・修正した欠陥

K2 コンパイラを直接起動する一時的な診断テスト（発火 23 件・非発火 17 件、
ケースは[ケース04-診断](test/ケース04-診断.md)の DIA 系に対応）で検出し、compiler-plugin 本体で修正済みの欠陥である。  
そのテスト一式は撤去済みで、診断の常設テストは gradle-integration の TestKit diag テストが持つ
（常設ケースの一覧は[ケース04-診断](test/ケース04-診断.md)が持つ）。

1. **間接継承経由の `Enumized<別型>` が未検出**（エッジ §2「判定は間接継承も対象とする」との差分）。  
   基底の supertype 閉包に対する検査と、注入スキップ判定の推移化で修正（DIA-47）。
2. **階層外クラスの companion が単独で末端になる許容構成が不成立**（設計01 §7.2 COMPANION_LEAF_CONFLICT
   の注記との差分）。  
   companion への supertype 注入もメンバー生成も行われず ABSTRACT_MEMBER_NOT_IMPLEMENTED になっていた。  
   companion 自身の末端判定を外側基準の kind 判定より先に行う分岐で修正（DIA-30）。
3. **typealias 経由の supertype で「明示的な companion は常に完全なワークアラウンド」（設計01 §6.2）が破綻**。  
   解決済み ref の ClassId がエイリアスのままで階層判定・注入・メンバー生成がすべて素通りしていた。  
   解決済み型の `fullyExpandedType` 展開と、raw 段階でのエイリアス追跡で修正（候補判定も同じ追跡を用い、
   追跡の有無を切り替えるフラグは持たない — 設計01 §6.2）。

このほか `ENUMIZE_ON_EXPECT` は `-Xmulti-platform` 下で発火し、expect 宣言への生成も ICE
を起こさない（実測。`ENUMIZE_ON_ACTUAL` を含む常設の診断検証は gradle-integration の TestKit diag テストが持つ）。  
継承者の別ソースセット逸脱は、別ソースセットの継承者が基底の sealed 継承者一覧に載らず検査対象になりえない（実測）。  
このため補足診断（旧 `ENUMIZE_CROSS_SOURCE_SET`）は持たず、コンパイラ本体の診断に委ねる（設計01 §7.2）。
