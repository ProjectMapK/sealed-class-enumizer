本書は sealed-class-enumizer コンパイラプラグインのアーキテクチャ全体感（FIR → IR 生成の流れ、
責務分割、インクリメンタルコンパイル設計、診断・テスト・リスク）を定める。

## 1. 前提と用語

- **K2 のみ**サポート（K1 は考慮しない）。実用下限は **Kotlin 2.4** である。
  コンパイラプラグイン API はリリース毎に破壊的変更が入ると公式に宣言されているため、Kotlin のマイナーバージョン毎にアーティファクトを分割する。
- **適用対象はソース宣言に限る（v1）**。`@Enumize` 対象の基底も階層の継承者も、
  **当該モジュールのソースに書かれた宣言**であることを前提とする。
  **他のコンパイラプラグインが生成した宣言に対する動作は v1 の対象外とし、挙動は未定義**とする。内訳:
  - **FIR に存在しない sealed 基底**（IR でのみ生成された sealed 等）は認識しない。本プラグインの述語判定・
    supertype 注入・診断はすべて FIR フェーズで動くため、FIR に無い宣言はそもそも観測できない
  - **他プラグインが FIR で生成したクラス**を `@Enumize` 対象や階層の継承者として扱うことは考慮しない。
    プラグイン間の生成順序に保証が無く、コンパイラ本体の継承者収集もソース宣言の sealed しか対象にしないためである
  - ただしこれは**他プラグインの生成物**についての限定である。本プラグイン自身が生成したクラスへ
    さらに生成する多段ネスト（`SI.Enumish` → その `Companion`・メンバー）は設計の前提であり、対象内である（V2-a）
- **基底 Enumish**: runtime-api の `io.github.projectmapk.sealedClassEnumizer.Enumish`（非ジェネリック interface。
  `label` / `enumishCompanion` / `toString` を持つ。`ordinal` 相当と `Comparable` は提供しない = 概要 §4）
- **生成 Enumish**: `@Enumize` 対象毎に生成されるネスト sealed interface（例: `SI.Enumish`）
- **EntriesHolder 基底**: runtime-api の `EnumishEntriesHolder<T>`（abstract class）。生成される EntriesHolder の基底で、
  entries の遅延構築と label による探索を持つ（概要 §2）。本書で無限定に「基底クラス」と書いた場合は
  `@Enumize` 対象の sealed 基底を指し、`EnumishEntriesHolder` を指すときは常に名前で書く
- **sealed 階層（以下単に「階層」）**: `@Enumize` 対象の sealed 基底から、sealed の継承者関係を**末端に到達するまで**
  辿って得られる閉じた集合。sealed の継承者は言語仕様上、同一パッケージ・同一モジュール
  （MPP では同一ソースセット）に閉じるため、階層もこの範囲に収まる。
  **末端が非 final の場合、そのサブタイプは階層に含まれない**（下記）
- **末端**: 階層のうち **sealed でない型**。sealed の継承者追跡がここで止まるため「末端」と呼ぶ。
  final な具象型（final class / data class / value class / enum class / object / data object）に加え、
  **open class / abstract class / interface / fun interface も末端になる**。
  宣言の種類で限定するときは「末端 class」「末端 object」「末端 interface」のように前置修飾で書く
  （条件節として述語化する「末端が class の場合」は可。「class の末端」のような後置形は用いない）
- **中間 sealed**: 階層内の sealed な継承者。entries には登場しない（末端のみ登場）
- **末端のサブタイプ**: 非 final な末端（open / abstract class・interface）を継承する型。
  階層外（別モジュールを含む）に自由に作れるが、**階層にも entries にも含まれない**。
  新しい kind を作らず、継承元の末端の kind に吸収される（§4.1）
- **kind**: 末端 1 つに対応する生成 Enumish のインスタンス（末端が object ならそれ自身、class なら companion）
- **階層不変条件**: 階層内のいずれかのファイルが dirty になったら、階層の全ファイルが同一ビルドで再コンパイルされる。
  JVM + Gradle で実測確認済み。集合が変化した際の一括再コンパイルは、コンパイラの実装コミットに明文化された設計意図である。
  **JPS / Maven / JS・Native の klib IC は別実装であり未検証（V8）** — 本書の IC 保証の記述はすべてこの限定の下にある

## 3. 処理パイプライン全体像

```
[FIR フェーズ列]                                    [プラグインの動作]
 RAW_FIR
 IMPORTS
 COMPILER_REQUIRED_ANNOTATIONS   … @Enumize の解決（predicate 登録による）
 COMPANION_GENERATION            … ソースクラスのネスト分類子の「名前」がすべて確定する:
                                     基底への SI.Enumish（述語判定のみ）
                                     末端 class への companion（設計01 §6 の raw-ref 追跡判定）
 SUPER_TYPES                     … supertype 注入:
                                     SI               += Enumized<SI.Enumish>
                                     末端 object      += SI.Enumish
                                     末端の companion += SI.Enumish
                                    生成 Enumish の実体構築もここで走りうる
                                    （その際に inheritors の lazy 登録を仕掛ける。§5.2）
 SEALED_CLASS_INHERITORS         … コンパイラ本体が「ソース宣言の」sealed の継承者を収集
                                    （生成 Enumish は対象外なので上記の lazy 登録で補う）
 TYPES / STATUS / ...
 (メンバースコープ解決)           … 生成クラスを owner とするネスト分類子生成（SI.Enumish.Companion）と
                                    メンバーシグネチャ生成（entries/valueOf/…/label/asEnumish）
 BODY_RESOLVE
 CHECKERS                        … プラグイン診断（§8）
        │
        ▼ fir2ir
[IR]
 IrGenerationExtension           … EntriesHolder（IR-only）生成、全生成メンバーのボディ充填
        │
        ▼ 各バックエンド lowering / シリアライズ（JVM class / klib / metadata）
```

FIR は「宣言の形状」（シグネチャ・supertype・診断）だけを担い、**ボディは一切作らない**。
IR がすべてのボディと IR-only の実体（EntriesHolder）を作る。この分割は好みではなく、
IC 安全性の根幹である（§5 の P2）。

## 4. 成果物対応表（何を・どの層で・どのファイルに帰属させて生成するか）

entries / valueOf の実体は IR-only の EntriesHolder へ委譲する（IC 帰属の一元化 = P1 と、実装詳細の ABI からの隔離）。

対象例: `@Enumize sealed interface SI`（ファイル Si.kt）、末端 class `Foo`（Foo.kt）、末端 object `Bar`（Bar.kt）。

| 成果物 | 宣言層 | ボディ層 | 帰属ファイル | 継承者の集合への依存 |
|---|---|---|---|---|
| `SI : Enumized<SI.Enumish>`（supertype 追加） | FIR (SupertypeGeneration) | — | Si.kt | なし |
| `SI.Enumish`（sealed interface : 基底 `Enumish`） | FIR (DeclarationGeneration, nested) | — | Si.kt | inheritors 属性のみ（§5.2） |
| `SI.Enumish.Companion : Enumish.Companion<SI.Enumish>` | FIR（多段ネスト生成） | — | Si.kt | なし |
| `Companion.entries` / `valueOf` / `valueOfOrNull`（override 宣言） | FIR（シグネチャのみ） | IR（ホルダー委譲） | Si.kt | ボディのみ間接 |
| `SI.Enumish.enumishCompanion`（override val・default 実装。返り値型を `SI.Enumish.Companion` へ共変絞り込み） | FIR（シグネチャ） | IR（`Companion` 返却） | Si.kt | なし |
| **EntriesHolder**（`SI.Enumish` 内ネスト object : `EnumishEntriesHolder<SI.Enumish>`。IR-only のため Kotlin ソースから不可視 = 設計02 §4.1） | **IR のみ** | `createEntries()` の実装（kind の列挙）と FQN のコンストラクタ引数のみ | Si.kt | **あり（ここに集約）** |
| 末端が object の場合: supertype `SI.Enumish` 追加 | FIR (SupertypeGeneration) | — | Bar.kt | なし |
| 末端が class / interface の場合: companion（既存流用 or 新規生成）へ supertype `SI.Enumish` 追加。open / abstract class・interface・fun interface を含む（§4.1） | FIR | — | Foo.kt | なし |
| kind の `label` override | FIR（シグネチャ） | IR（単純名の const） | 末端側のファイル | なし |
| kind の `toString` override（**末端 data object と末端 enum class はスキップ**。利用側の override は許容。§4.1） | FIR（シグネチャ） | IR（label 返却） | 末端側のファイル | なし |
| 末端の `asEnumish()` override | FIR（シグネチャ） | IR | 末端側のファイル | なし |

この表の要点は、**継承者の集合に依存する生成物が「Si.kt 帰属」だけに閉じている**ことである（P1/P2 の実装）。
末端側のファイルへの生成物（label / toString / asEnumish / companion）は、いずれも「自分自身と基底」にしか依存しない。

### 4.1 表の補足

- **中間 sealed には何も生成しない**（asEnumish は抽象のまま継承される）。
- **非 final な末端（open / abstract class・interface・fun interface）も末端として扱い、通常どおり生成する**。
  末端 class と同じく companion が kind になり、`label` / `toString` / `asEnumish` を生成する
  （interface の場合、`asEnumish` は default 実装として生成する）。
  **これが entries の完全性を壊さない**のが要点である: 第三者が階層外で末端のサブタイプを作れるが、
  そのサブタイプは `asEnumish()` の実装を末端から継承するため、**新しい kind を作らず継承元の kind に吸収される**。
  entries の要素は「階層内の末端」で決まり、階層外のサブタイプの有無に依存しない。
  値単位の `when` の網羅性も、`is <末端>` の枝がサブタイプをすべて覆うため成立する。
  したがって非 final な末端は「拡張点を開いたまま enum 的 API を得る」ための正当な構成である。
  ただし**ある型が 2 つ以上の末端のサブタイプになると kind が一意に定まらない**ため、
  これは `ENUMIZE_AMBIGUOUS_KIND`（§8）で禁じる。
- **`ordinal` 相当と `Comparable` は提供しない**（概要 §4）。
  sealed 階層の序数は宣言順に定まらず（コンパイラが提供する継承者順に従う = §6）、改名で変動するため永続化に使えず、
  「使ってはならない値」を API 表面に置く弊害の方が大きいという判断である。`Comparable` は序数の存在が
  前提であるため併せて不提供とした。
  帰結として、順序に依存する生成物は EntriesHolder の `entries` の並びと生成 Enumish の inheritors 属性の並び
  （§5.2）の 2 つだけであり（いずれも Si.kt 帰属）、**末端側のファイルには順序に由来する値を一切焼き込まない**
  （P1 の維持が単純になる）。
- **entries の保持・遅延初期化・label による探索は runtime-api の基底クラス `EnumishEntriesHolder<T>` に集約する**
  （概要 §2 に実装込みで記載）。生成する EntriesHolder が担うのは
  **supertype の指定（型引数 = `EnumishEntriesHolder<SI.Enumish>`）・FQN のコンストラクタ引数・
  `createEntries()` の実装（kind を §6 の順序で並べる）の 3 つだけ**である（概要 §2・設計02 §4.1）。
  生成される valueOf / valueOfOrNull は `EntriesHolder.getByLabel(value)` / `getByLabelOrNull(value)` への
  1 行委譲になり、例外メッセージ（enum と同形式・FQN つき）も `EnumishEntriesHolder` 側が組み立てる
  （label の一意性は ENUMIZE_LABEL_CLASH が保証。設計02 §4 / §5.1）。
  EntriesHolder は IR-only（ABI 保証外）であり、実装方式の変更を Kotlin ABI に露出させない継ぎ目として機能する。
- **`toString` は各 kind 側へ生成する**（interface には Any メンバーの default 実装を書けないという言語制約のため）。
  ただし次の 2 つはスキップする。いずれも「言語または実装側が既に toString を持っている」ケースであり、
  `toString` は override 可能なメンバーである以上、プラグインが上書きしに行くべきではないという判断による。
  - **末端 data object**: 言語が単純名を返す `toString` を自動合成するためである。
  - **末端 enum class**: enum は言語自身が `Enum.toString()`（既定は `name` を返し、override 可能）を持ち、
    実装側がこれを override することも一般的である。kind である companion 側にプラグインが別の `toString` を
    生成すると、同一の enum に対して「定数の表示」と「kind の表示」という 2 系統が並立し、
    実装側の override 意図と食い違う。表示の既定は言語側に委ねる。
  また `toString` は**利用側の override を許容**し、診断（§8 の ENUMIZE_MANUAL_MEMBER_CONFLICT）の対象にしない
  — `Any` のメンバーである以上どのクラスでも override でき、言語仕様上、禁じる手段が無く、
  かつ表示にしか影響しないため（entries / valueOf / asEnumish の整合性は損なわれない）。
  帰結として、将来 label のカスタマイズを導入して label と単純名が一致しなくなった場合、
  **data object の `toString` は単純名を返し続ける**（言語合成が使われるため label には追随しない）。
  これは仕様上の制約として文書化する（概要 §4）。
- **`enumishCompanion` は基底で `Companion<Enumish>` と宣言し、生成 Enumish が具体型
  （`SI.Enumish.Companion`）へ共変 override する**。`Companion<out T>` の宣言側共変により、
  静的型が `SI.Enumish` なら `enumishCompanion.entries` が `List<SI.Enumish>` として型付く（実測）。
  複数階層の Companion を束ねる用途も射影なしの `List<Enumish.Companion<Enumish>>` で満たせる（実測。概要 §2）。
- **`@JvmStatic` は v1 では付与しない**。Java からは `SI.Enumish.Companion.INSTANCE` を経由して
  `getEntries()` / `valueOf(...)` / `valueOfOrNull(...)` を呼ぶ（`entries` はプロパティなので Java 側では `getEntries()`）。
  **将来拡張**として、これらへ `@JvmStatic` を付与し `SI.Enumish.getEntries()` 形の static アクセスを
  可能にする余地は残す（`entries()` という呼び出し形は目標としない）。ただし interface companion のメンバーへの
  適用自体は可能（JVM target 1.8+）である一方、ソース Kotlin では **override メンバーへの `@JvmStatic` が禁止**
  されており、生成宣言（= override）にも同じ検査が及ぶ可能性が高い。**この不確実性を v1 に持ち込まないため、
  付与自体を見送る**（付与しないことによる機能上の損失は Java からの呼び出し形だけであり、他ターゲットには影響しない）。

## 5. IC 設計

「基底と継承者のファイルが分かれていて片方だけが編集されても壊れない」ことは、本プラグインの一級要件である。
本設計はこれを自前の依存追跡で解こうとせず、**コンパイラが sealed のために既に持っている性質に相乗りする**方針を採る。

**依拠する事実（階層不変条件・§1）**: Kotlin コンパイラ自身が (a) `when` の網羅性の検査と
(b) sealed サブクラス一覧のメタデータへの焼き込み、という 2 つの目的のために、**sealed 階層を常に 1 単位として
再コンパイルする**。継承者の集合が変化したときに階層を一括で再コンパイルすることは、コンパイラの実装コミットに
明文化された設計意図であり、「階層内のいずれかのファイルが dirty になれば階層の全ファイルが同一ビルドで
再コンパイルされる」ことを JVM + Gradle で実測確認済みである
（JPS / Maven / JS・Native の klib IC は別実装のため、個別の検証項目としている = V8）。

この事実があるため、プラグインは「継承者の集合に依存する生成物を、必ず一緒に再コンパイルされる場所に置く」だけでよい。
たとえば基底 `SI`（`Si.kt`）と末端 `Foo`（`Foo.kt`）が別ファイルにあり `Foo.kt` だけを編集した場合も、
階層不変条件により `Si.kt` が共連れで再コンパイルされ、entries は必ず最新の階層から再計算される。
逆方向（階層の再コンパイルに無関係なファイルが共連れされないこと）も実測済みで、
プラグイン適用時に dirty 税が発生しないことと併せて V7 で確認する。

この方針を実装規則へ落としたものが、次の 3 原則である。

### 5.1 IC 安全 3 原則

- **P1（帰属の原則）**: 継承者の集合に依存する生成内容（entries の実体 = EntriesHolder）は、
  **基底クラスのファイルに帰属する宣言としてのみ生成**する。階層不変条件により、集合が変化するあらゆるビルドで
  必ず再生成され、かつそのラウンドではすべての継承者がソースとして可視である。
- **P2（形状独立の原則）**: FIR に公開する宣言の**シグネチャ**は継承者の集合に依存させない。
  集合に依存するのは IR のボディと、生成 Enumish の inheritors 属性（§5.2）のみ。
  IDE（FIR のみ動く環境）での解決が階層列挙に依存しなくなる効果もある。
- **P3（非集約の原則）**: モジュール内の `@Enumize` 全件を列挙して 1 つの宣言（レジストリ・ガワ・トップレベル
  合成ファイル）に焼き込むことをしない。プラグインによるグローバル探索では、IC 下で当該ラウンドのソースしか
  見えないという問題（KT-55982）が公式に認識されており、2.3+ の保守的な機構（KT-75864）の下でも
  「述語にマッチしたファイルを常に再コンパイルする」という税を払うことになる。
  ネスト生成に留めればこの税自体を回避できる見込みである（V7 で実測確認）。

### 5.2 継承者の集合への依存の唯一の例外: inheritors 属性

生成 Enumish を sealed にするため、その継承者リスト（すべての kind の ClassId）を
`FirRegularClass.setSealedClassInheritors` の **lazy オーバーロード**でプラグイン自身が登録する
（コンパイラの収集器はソース宣言の sealed しか処理しないため）。これは「継承者の集合に依存する FIR 情報」だが、

- Si.kt 帰属の宣言に載る（P1 準拠 = 階層が変わるビルドで必ず再計算される）
- lazy 登録により、SUPER_TYPES 段階での階層列挙（フェーズ違反リスク）も回避する

未検証項目 **V1**（本設計の最難関）: (a) この属性がメタデータ / klib に `sealed_subclass_fq_name` として
直列化され**別モジュールからの kind-when の網羅性が成立する**こと、(b) 利用側モジュールの kind-when が
末端の追加によって再検査されること、(c) when の各枝形が網羅性の判定に算入されること — companion kind の
等値枝（`Foo.Companion ->` と短縮形 `Foo ->` の両形）・object kind の等値枝・`is` 枝（companion object が
sealed 継承者になるという公開前例のない組合せのため）、(d) IDE（Analysis API）での動作。

**縮退案**: 非 sealed で出荷し、kind-when には else を要求する。ただし「安全性は変わらない」わけではない:
非 sealed だと第三者が `SI.Enumish` を実装でき、entries の完全性と valueOf の解決が実行時に静かに破れる
（entries に載らない kind が存在しうる）。このため縮退の有無に関わらず、
プラグイン適用モジュール内での「kind 以外による生成 Enumish / 基底 Enumish の実装」を診断でエラーにする
（`ENUMIZE_MANUAL_ENUMISH_IMPL`。sealed 成立時も同一モジュール・同一パッケージからの手動継承は言語上可能なため、
プラグインが登録した inheritors と食い違う前に検出する）。プラグイン未適用モジュールからの実装は防げないため、
失敗モードとともに文書化する。

また、**else 不要の網羅が成立するのは、すべての kind が呼び出し側から可視の場合に限る**。
これは可視性の低い継承者を持つ sealed に対する言語本来の挙動と同じであり、判定は**呼び出し側の位置に依存する**。
したがって「private / internal な kind を含む階層では常に else が必要」ではない —
可視範囲の内側（例: private 基底と同一ファイル）から書く when は、通常どおり else なしで網羅する。
else が必要になるのは、可視範囲の**外側**から when を書く場合だけである（そもそも基底自体が見えないなら
`asEnumish()` を呼ぶこともできないため、これが問題になるのは internal 基底をモジュール内の
より狭い可視性の kind と混在させた場合などに限られる）。

### 5.3 編集ケース分析（親子ファイル分離時に片側だけ編集されたらどうなるか）

前提: 階層不変条件（§1 の環境限定つき）。「利用側」= 階層外・他モジュールを含む参照側。

| # | 編集 | dirty になるもの（実測 + 機構） | プラグイン上の帰結 |
|---|---|---|---|
| 1 | 末端側のファイルのみ編集（ABI を変えない変更を含む） | 階層の全ファイル（実測: private メンバーの追加やコメントのみの変更でも共連れ） | Si.kt が再コンパイルされ、EntriesHolder と inheritors 属性が最新の階層から再生成される |
| 2 | 末端の追加（新規ファイル） | 階層の全ファイル + 基底を参照する利用側のファイル | entries に新しい末端が反映される。利用側の kind-when は網羅性エラーで検出される（V1-b） |
| 3 | 末端の削除（ファイル削除） | 同上 | entries から消える。削除された kind を参照する利用側はコンパイルエラーになる |
| 4 | 基底のみ編集 | 階層の全ファイル | 末端側の生成物（label / asEnumish / companion）も再生成される |
| 5 | 内容を変えないファイルの改名・末端のファイル間移動 | 対象ファイルが dirty → 階層共連れ | **生成物は不変**（継承者一覧が FQN 順に正規化済みであり、ソースの配置に依存しないため。§6.1）。バイト一致テストで不変であることを確認する |
| 6 | **末端（または外側クラス）の改名** | 改名したファイルが dirty → 階層共連れ | ClassId が変わるため entries の FQN 順の並びが再配置される。加えて**末端自身の改名では label も変わる**ため valueOf の呼び出し側にも影響する（外側クラスの改名では label は不変であり、並びだけが変わる） |
| 7 | 手動 companion の追加 / 削除（既定名 `Companion`） | 末端側のファイルが dirty → 階層共連れ。**ABI は変化しない**（生成 companion も public な `Foo$Companion` であり、どちらの状態でもクラスは存在する） | 自動生成と流用が切り替わるだけで、利用側から見た形は変わらない |
| 7-b | 手動 companion の追加 / 削除（**名前つき** `companion object Factory`） | 末端側のファイルが dirty → 階層共連れ。`Foo$Companion` ⇔ `Foo$Factory` のクラス名の変化が ABI 差分として利用側へ伝播する | **label は変わらない**（label は末端宣言 `Foo` の単純名であり、kind を担う companion の宣言名には依存しない。§8 の label 規則）。したがって `valueOf` の呼び出し側は影響を受けない。影響が及ぶのは kind を修飾名で名指しする側（`Foo.Companion ->` → `Foo.Factory ->`。短縮形 `Foo ->` は不変）である。stale 出力（旧 companion class）の掃除は、「末端側のファイルの出力」として IC が追跡する |
| 7-c | 既存 companion の可視性の変更（public ⇔ internal） | 同上 | `asEnumish` の返り値型が `Foo.Companion` ⇔ `SI.Enumish` で切り替わり（設計01 §5.4）、ABI 差分として利用側へ伝播する。private / protected への変更は `ENUMIZE_KIND_NOT_ACCESSIBLE` になる |
| 8 | label 衝突の導入 / 解消（別ファイルに同名の末端を追加した場合など） | 階層共連れ | CHECKERS が `ENUMIZE_LABEL_CLASH` を報告 / 解除する |
| 9 | 中間 sealed の追加 / 除去 | 階層共連れ | 末端を再帰的に収集し直し、順序を再計算する |
| 10 | 階層外の無関係なファイルの編集 | 階層は dirty にならない想定（実測済みなのは逆方向 = 階層の再コンパイルに無関係なファイルが共連れされないこと） | 生成物は再生成されない（P3 により dirty 税も発生しない見込み。いずれも V7 で実測確認） |
| 11 | ライブラリ側で末端を追加（跨モジュール） | 利用側: sealed リストの ABI 差分 → 基底を参照するファイルが dirty（実測） | 利用側の kind-when / 値 when が再検査される |

このうち #6（改名による entries の並びの再配置）は enum に無い編集意味論（enum の宣言順は改名で不変）であり、
#5（配置の変更で生成物が不変であることの確認）と併せてテストマトリクス（§9）の重点ケースである。

## 6. entries の順序

**本プラグインは順序を規定しない。** entries の並びは、Kotlin コンパイラが sealed の継承者一覧に対して用いる
正規化順に**従う**だけである。プラグイン独自の順序（宣言順など）は定義しない — 宣言順は全順序として規定できず
（ファイル名という人工的なキーを要し、ファイルの改名や移動、Unicode 正規化の差で並びが揺れる）、
かつコンパイラ・リフレクション・KSP と並べ替えの基準が食い違うことになるためである。

### 6.1 従う順序（コンパイラ側の性質）

コンパイラは sealed の継承者一覧を **FQN 文字列（`ClassId.asFqNameString()` = `pkg.Outer.Inner` 形式）の
UTF-16 序数昇順（大文字小文字を区別・ロケール非依存）** に正規化して保持する。
`KClass.sealedSubclasses` や KSP が返す順序もこれである。以下はこの性質の記述であり、
本プラグインが決めた規則ではない。

**正規化はセッター側で行われる**（`FirRegularClass.setSealedClassInheritors`。
`compiler/fir/tree/.../declarations/SealedClassInheritors.kt`）:

```kotlin
fun FirRegularClass.setSealedClassInheritors(inheritors: List<ClassId>) {
    sealedInheritorsAttr = lazyOf(inheritors.sortedBy { it.asFqNameString() })
}
fun FirRegularClass.setSealedClassInheritors(inheritorComputer: () -> List<ClassId>) {
    sealedInheritorsAttr = lazy { inheritorComputer().sortedBy { it.asFqNameString() } }
}
```

収集側（`FirSealedClassInheritorsProcessor`）は `mutableSetOf()`（= `LinkedHashSet`）にファイル・宣言の
訪問順で貯めるが、属性へ格納する時点で必ずソートされる。したがって **`getSealedClassInheritors` は
直列化を待たずに常に FQN 順を返し、ソースの配置（ファイル順・宣言順）には依存しない**。
直列化（`FirElementSerializer`）はこの属性をそのまま書き出すため、メタデータの順序も同じである。

> Kotlin 2.4.0 実測: ネストされた末端 `S.Aaa` / `Box.Bbb`・トップレベルの末端 `Mmm` / `Zzz` / `aLower` の混在階層で
> `sealedSubclasses = [Box.Bbb, Mmm, S.Aaa, Zzz, aLower]`。単純名昇順（Aaa 先頭）・宣言順（Zzz 先頭）・
> 大文字小文字を無視した順（aLower 先頭）のいずれでもなく、**FQN 序数順**であることが判別できる。

この正規化順はコンパイラの**実装詳細であり公式な保証は無い**（KSP に宣言順を提供してほしいという要望も
not-planned でクローズされている）。本プラグインはこれを、Kotlin のマイナーバージョン毎のアーティファクト分割（§1）と
§9 の決定性テスト（clean / incremental のバイト一致 + サポート対象の Kotlin 全マイナーで順序の回帰を検出すること）
によって受容する。

### 6.2 プラグインは並べ替えない

**プラグインは entries の並びに一切介入しない。** ソートも安定化も行わず、コンパイラから受け取った
継承者リストの順序をそのまま使う。中間 sealed に到達したらその継承者リストへ再帰的に降り、
戻ってきたら次の要素へ進む — **この深さ優先の走査でできた並びがそのまま entries になる**。

```
SI の継承者リスト = [Bbb, Mid]      （コンパイラ提供）
Mid の継承者リスト = [Aaa]           （同上）
                 ↓ Mid の位置をその継承者で置き換える
entries          = [Bbb, Aaa]
```

したがって entries の並びは「**コンパイラが提供する順序を、中間 sealed の位置で入れ子に展開したもの**」である。

- **中間 sealed が無い階層**では、entries はコンパイラが提供する順序そのものであり、
  §6.1 の正規化順（FQN 序数順）と一致する
- **中間 sealed がある階層**では、全体としては FQN 序数順に**ならない**場合がある。
  中間 sealed の継承者が中間の内側にネストしていない構成がこれにあたる:

  ```kotlin
  sealed interface SI
  sealed interface Mid : SI     // pkg/Mid
  object Aaa : Mid              // pkg/Aaa  ← Mid の内側ではなくトップレベル
  object Bbb : SI               // pkg/Bbb

  // SI の継承者は FQN 順で [Bbb, Mid] → 展開して entries = [Bbb, Aaa]
  // 末端集合を FQN 順に並べたなら [Aaa, Bbb] になるが、そうはならない
  ```

  末端が中間 sealed の内側にネストしている通常の構成では、ネストした末端の FQN が中間の FQN を接頭辞に持つため
  結果的に FQN 序数順と一致する

- 生成 Enumish の inheritors 属性（§5.2）も同様に、収集した順のまま登録する。
  メタデータへ直列化する際の正規化はコンパイラ本体が行うため、プラグイン側で整える必要はない

### 6.3 帰結

- **決定性とソースの配置への非依存は保たれる**。各段の継承者リストは属性へ格納される時点で
  FQN 順に正規化されており（§6.1）、プラグインの走査は再帰の順序だけで決まるため、
  ファイル名・ファイル順・宣言位置を変えても entries の並びは変わらない。
  順序が変わるのは**末端（またはその外側クラス）の改名・追加・削除**、および階層の入れ子構造の変更のときである
  （回帰は §9 の決定性テストが clean / incremental のバイト不一致として検出する）
- 順序は `entries` の並びとしてのみ観測される。**序数（`ordinal` 相当）は API として公開しない**（§4.1・概要 §4）
  ため、順序の変動が利用側の永続化データを壊す経路は設計上存在しない
  （利用者が `entries.indexOf(...)` の値を自前で永続化してはならない旨は概要 §5 に明記している）。
  この「序数を公開しない」判断が、順序に介入しない方針の前提でもある

## 7. クロスモジュール・マルチプラットフォーム

- 階層は言語仕様上、単一モジュール・単一ソースセットに閉じる。したがって**すべての生成は定義モジュール内で完結**し、
  「モジュールを跨いだ生成」は存在しない。跨モジュールの考慮点は参照側に集約される:
  - 生成 API は通常の宣言としてメタデータ / klib に載るため、プラグイン未適用の利用側からも参照できる
  - 跨モジュールの kind-when の網羅性のみ、生成 Enumish の inheritors の直列化（V1-a）に依存する
- **metadata コンパイル**: common ソースセットの `@Enumize` は metadata コンパイルでもプラグインが動作し、
  生成宣言が共通メタデータに載ることが前提（`FirDeclarationsForMetadataProviderExtension` の要否は V5）。
  metadata コンパイルと各 platform コンパイルの間で生成結果が決定的に一致すること（§6 の順序）が前提条件である。
- **expect/actual**: expect sealed は actual 毎に階層が変わりうるため、`@Enumize` を expect へ付与することは
  v1 ではエラーとする（`ENUMIZE_ON_EXPECT`）。
- **旧バイナリとの実行時組み合わせ**: entries はホルダーを経由して実行時に解決されるので、実行時に存在する版の集合が返る。
  この性質を保つため **entries アクセサを inline にしない**ことを設計制約とする。
- 継承者が別のソースセットへ逸脱することはコンパイラ本体の診断対象だが、プラグインからも補足説明（`ENUMIZE_CROSS_SOURCE_SET`）を出す。

## 8. 診断カタログ

検査ロジック・報告位置・メッセージの詳細は [設計01](コンパイラプラグイン設計01.md) §7。ここでは一覧のみ。

| ID | 深刻度 | 条件（要約） |
|---|---|---|
| ENUMIZE_NOT_SEALED | error | `@Enumize` が sealed class / sealed interface 以外に付与されている（fun interface は sealed であっても対象。sealed fun interface が言語側で許容されるかは V9） |
| ENUMIZE_ON_EXPECT | error | `@Enumize` が expect 宣言に付与されている（v1 制限） |
| ENUMIZE_MULTIPLE_FAMILIES | error | 同一クラスが 2 つ以上の `@Enumize` 階層に属している（兄弟階層の交差 `object X : SI1, SI2` を含む非交差条件） |
| ENUMIZE_NESTED_IN_HIERARCHY | error | `@Enumize` 階層のメンバーに別の `@Enumize` が付与されている（MULTIPLE_FAMILIES の特殊ケース・個別メッセージ） |
| ENUMIZE_AMBIGUOUS_KIND | error | 階層内のある型が 2 つ以上の末端のサブタイプになる（非 final な末端を許容したことによる新条件。kind が一意に定まらない） |
| ENUMIZE_INNER_LEAF | error | 末端が inner class（companion を持てないという言語制約による） |
| ENUMIZE_KIND_NOT_ACCESSIBLE | error | kind が基底の本体スコープから参照できない（別ファイルの private なトップレベルの末端、private / protected な既存 companion） |
| ENUMIZE_COMPANION_LEAF_CONFLICT | error | 階層の末端 class の companion が同一階層の末端でもある（kind の二重対応） |
| ENUMIZE_LABEL_CLASH | error | label（既定 = 末端宣言の単純名。**companion 自身が末端である場合に限り**その宣言名）の重複 |
| ENUMIZE_MANUAL_MEMBER_CONFLICT | error | 生成対象メンバーを**その生成先クラス**が手動宣言・継承している（生成先の対応は設計01 §5.3） |
| ENUMIZE_MANUAL_SUPERTYPE_MISMATCH | error | 型引数の異なる手動継承（`: Enumized<別型>` 等） |
| ENUMIZE_MANUAL_ENUMISH_IMPL | error | kind 以外による生成 Enumish / 基底 Enumish の実装（末端 class 自身での実装を含む） |
| ENUMIZE_RESERVED_NAME_CLASH | error | 基底に既存のネスト宣言 `Enumish` がある |
| ENUMIZE_COMPANION_REQUIRED | error | 末端 class に companion が無く、自動生成の候補判定（設計01 §6）が働いていない |
| ENUMIZE_CROSS_SOURCE_SET | error | 階層の継承者が別のソースセットに存在する（本体診断への補足） |
| ENUMIZE_EXTENSION_SHADOWED | warning | 階層のメンバーが `label` という可視メンバーを宣言している（拡張シャドーイング） |
| ENUMIZE_ENUM_LEAF_UNSUPPORTED | error | （V4 不成立の縮退時のみ有効化）末端 enum class |

診断 ID は英語の識別子であり、本文の日本語用語とは独立に安定させる（例: `ENUMIZE_MULTIPLE_FAMILIES` の
FAMILIES は用語「階層」に追従して改名しない）。

**診断実装の設計制約（単調性）**: マルチラウンド IC では階層の部分集合ビューで CHECKERS が走るラウンドが存在しうる。
診断は部分集合ビューで**偽陽性を出してはならない**（検査対象は「見えているメンバーの性質」のみに依存させる。
「階層全体の完全性」に量化する検査を追加する場合はこの制約と両立させる）。現行のカタログは全て条件検査型であり単調である。

### 10.1 V2-b の縮退先: EntriesHolder の FIR 生成

V2-b が不成立の場合も **`EnumishEntriesHolder` の継承は維持する**（継承をやめて entries の保持・遅延初期化・
探索・メッセージ構築を IR で組み直す案は、runtime-api へ集約した責務を IR へ差し戻すことになるため採らない）。
代わりに `$EntriesHolder` を **IR-only ではなく FIR で生成**する。以下は公開 API のみで構成できることを
Kotlin 公式のコードで確認済みである。

- `createNestedClass(owner = SI.Enumish, name = "$EntriesHolder", ClassKind.OBJECT) { superType(...) }` で
  supertype つきのネスト object を生成する（`ClassBuildingContext` は任意の型を supertype に取れ、`visibility` も設定できる）。
  **`private` で生成する**ため、参照できるのは同じく `SI.Enumish` の内側にある生成 Companion だけである
  （設計01 §1 の「生成物は原則 `public`」に対する**唯一の例外**であり、同項にも明記している）
- コンストラクタは `createDefaultPrivateConstructor(generateDelegatedNoArgConstructorCall = true)` で生成する。
  これは `getSuperClassSymbolOrAny` を使ってスーパークラスへの委譲呼び出しを組み立てる公開ヘルパである
- kotlinx.serialization も `createNestedClass(... ClassKind.OBJECT) { superType(...) }` +
  `createDefaultPrivateConstructor` で `$serializer` を生成しており、**FIR 生成のネスト object に supertype と
  コンストラクタを持たせるのは確立した用法**である

**この縮退には runtime-api の変更が伴う**: 公開ヘルパが面倒を見る委譲呼び出しは **no-arg 限定**であるため、
`EnumishEntriesHolder` の FQN は**コンストラクタ引数ではなく `protected abstract val enumishFqName` にする**必要がある
（引数つきのままだと委譲呼び出しを DSL の外で手組みすることになり、FIR へ移す利点が減る）。
生成側は `enumishFqName`（const を返す getter）と `createEntries()` の 2 つを override し、
どちらのボディも IR で充填する — いずれも `label` の生成で既に使う機構である。

設計原則との整合: 生成する形状（クラス・supertype・2 つのシグネチャ）は**継承者の集合に依存しない**ため P2 を保ち、
生成先が `SI.Enumish` であるため帰属は Si.kt のままで P1 も保つ。多段ネスト生成という点では V2-a と同じ機構であり、
新しいリスクは増えない。失うのは「IR-only であることによる ABI からの隔離」だが、`private` であるため
跨モジュールの ABI には現れず、同一モジュール内でも形状が固定であるため IC 上の影響は無い。

## 11. IDE についての前提

IntelliJ の K2 モードはサードパーティ FIR プラグインをデフォルトでロードしない（KTIJ-29248、Backlog）。
当面のデフォルト体験は「CLI / Gradle ビルドは正しいが、エディタでは生成 API が未解決」である。

- P2（形状独立）により、エディタが生成宣言を解決できない場合でも赤くなる範囲は生成 API の参照箇所に限られる
- プラグインがロードされる環境では、**生成クラスの中にネストされたクラス**（`SI.Enumish.Companion`）の解決に
  KT-84625（`Analysis API. FIR` / `Analysis API. Providers and Caches`。Fixed）の修正が必要である。
  2.4.0-Beta2 で修正済みであり、**実用下限を 2.4 とする根拠はこの IDE / Analysis API 側の事情である**
  （CLI / Gradle の codegen はこの修正に依存しない。§1・設計01 §5.1）
- 緩和策として、コミュニティの Kotlin External FIR Support（KEFS）への対応（`<kotlin-version>-<lib-version>` 形式で
  バージョン別のアーティファクトを公開すること）と、JetBrains の compiler plugin devkit（KT-82617）を追跡する
