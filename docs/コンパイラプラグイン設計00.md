## 1. 前提と用語

- **K2 のみ**サポート（K1 は考慮しない）。  
  実用下限は **Kotlin 2.4** である（根拠は IDE / Analysis API 側の事情 = §11）。  
  コンパイラプラグイン API はリリース毎に破壊的変更が入ると公式に宣言されているため、Kotlin
  のマイナーバージョン毎にアーティファクトを分割する。
- **適用対象はソース宣言に限る（v1）**。  
  `@Enumize` 対象の基底も階層の継承者も、**当該モジュールのソースに書かれた宣言**であることを前提とする。  
  **他のコンパイラプラグインが生成した宣言に対する動作は v1 の対象外とし、挙動は未定義**とする。  
  内訳:
  - **FIR に存在しない sealed 基底**（IR でのみ生成された sealed 等）は認識しない。  
    本プラグインの述語判定・supertype 注入・診断はすべて FIR フェーズで動くため、FIR に無い宣言はそもそも観測できない
  - **他プラグインが FIR で生成したクラス**を `@Enumize` 対象や階層の継承者として扱うことは考慮しない。  
    プラグイン間の生成順序に保証が無く、コンパイラ本体の継承者収集もソース宣言の sealed しか対象にしないためである
  - ただしこれは**他プラグインの生成物**についての限定である。  
    本プラグイン自身が生成したクラスへさらに生成する多段ネスト（`SI.Enumish` → その `Companion`・
    メンバー）は設計の前提であり、対象内である
- **基底 Enumish**: runtime-api の `io.github.projectmapk.sealedClassEnumizer.Enumish`（非ジェネリック interface。`label` /
  `enumishCompanion` / `enumizedClass` を宣言し、`toString` は宣言しない — 概要 §2。`ordinal` 相当と `Comparable`
  も提供しない — 概要 §4）
- **生成 Enumish**: `@Enumize` 対象毎に生成されるネスト sealed interface（例: `SI.Enumish`）
- **EntriesHolder 基底**: runtime-api の `EnumishEntriesHolder<T>`（abstract class）。  
  生成される EntriesHolder の基底で、entries の遅延構築・label による探索・`valueOf` 失敗時のメッセージ構築を持つ。  
  **コンストラクタ引数を持たず**、基底の識別は `protected abstract val enumizedRootClass`（`@Enumize` 基底の class
  リテラルを返す）で行う（概要 §2）。  
  本書で無限定に「基底クラス」と書いた場合は `@Enumize` 対象の sealed 基底を指し、`EnumishEntriesHolder`
  を指すときは常に名前で書く。  
  プラグインが各階層に生成するホルダーは概念名「EntriesHolder」で呼び、
  実際の出力名は `$EntriesHolder` である（設計02 §4.1）
- **sealed 階層（以下単に「階層」）**: `@Enumize` 対象の sealed 基底から、sealed の継承者関係を**末端に到達するまで**
  辿って得られる閉じた集合。  
  sealed の継承者は言語仕様上、同一パッケージ・同一モジュール（MPP では同一ソースセット）に閉じるため、
  階層もこの範囲に収まる。  
  **末端が非 final の場合、そのサブタイプは階層に含まれない**（下記）
- **末端**: 階層のうち **sealed でない型**。  
  sealed の継承者追跡がここで止まるため「末端」と呼ぶ。  
  final な具象型（final class / data class / value class / enum class / object / data
  object）に加え、**open class / abstract class / interface / fun interface も末端になる**。  
  宣言の種類で限定するときは「末端 class」「末端 object」「末端
  interface」のように前置修飾で書く（条件節として述語化する「末端が class の場合」は可。
  「class の末端」のような後置形は用いない）
- **中間 sealed**: 階層内の sealed な継承者。entries には登場しない（末端のみ登場）
- **末端のサブタイプ**: 非 final な末端（open / abstract class・interface）を継承する型。  
  階層外（別モジュールを含む）に自由に作れるが、**階層にも entries にも含まれない**。  
  新しい kind を作らず、継承元の末端の kind に吸収される（§4.1）
- **kind**: 末端 1 つに対応する生成 Enumish のインスタンス（末端が object ならそれ自身、
  それ以外 — class / interface / enum class — ならその companion）
- **手動実装**: kind 以外のクラスが生成 Enumish または基底 Enumish を supertype に取ること。  
  基底 Enumish は非 sealed の public interface であり、その実装は任意のモジュールで無制約に行える。  
  生成 Enumish の直接実装は**階層内のもの（末端 class 自身による実装など）に限り許容**され（概要 §8）、
  階層外の直接実装は継承者一覧（§5.2）へ反映する経路が無いため `ENUMIZE_MANUAL_IMPL_OUTSIDE_HIERARCHY` でエラーにする。  
  許容される手動実装の値は kind ではないため entries / valueOf には現れない
- **階層不変条件**: 階層内の**既存 kind を宣言するファイル**が dirty になったら、
  基底ファイルを含む階層の全ファイルが同一の IC ラウンドで再コンパイルされる。  
  JVM + Gradle で実測確認済み。  
  集合が変化した際の一括再コンパイルは、コンパイラの実装コミットに明文化された設計意図である。  
  ただし**言語側の保証ではなく**、基底ファイルの生成物（`$EntriesHolder` の `createEntries`）が各 kind
  を参照することで生じた依存辺の効果であり（プラグイン非適用の同形では末端ファイルの編集で基底は再コンパイルされな
  い）、**新規ファイルで追加された末端**と**生成物から参照されない中間 sealed の単独編集**では基底ファイルがラウンドに入
  らない（実測）。  
  この基底不在ラウンドでも末端側の生成は成立し、集合の変化は後続ラウンドの基底再コンパイルで反映される（§5）。  
  **MPP（klib を含む）では KGP が既定で非 incremental にするため（§5.4 の KT-62686）、そもそも階層不変条件を要さない。JPS / Maven は別実装であり未検証（V8）**
  — 本書の IC 保証の記述はすべてこの限定の下にある

## 3. 処理パイプライン全体像

```
[FIR フェーズ列]                                    [プラグインの動作]
 RAW_FIR
 IMPORTS
 COMPILER_REQUIRED_ANNOTATIONS   … @Enumize の解決（predicate 登録による）
 COMPANION_GENERATION            … ソースクラスのネスト分類子の「名前」がすべて確定する:
                                     基底への SI.Enumish（述語判定のみ）
                                     object 以外の末端への companion（設計01 §6 の raw-ref 追跡判定）
 SUPER_TYPES                     … supertype 注入:
                                     SI                   += Enumized<SI.Enumish>
                                     末端 object          += SI.Enumish
                                     末端の既存 companion += SI.Enumish
                                    （プラグイン生成の companion は注入で訪問されないため、
                                     supertype は生成時に直接指定する = 設計01 §4・§5.1）
                                    生成 Enumish の実体構築もここで走りうる
                                    （その際に inheritors の lazy 登録を仕掛ける。§5.2）
 SEALED_CLASS_INHERITORS         … コンパイラ本体が「ソース宣言の」sealed の継承者を収集
                                    （生成 Enumish は宣言としては走査されないため上記の lazy 登録で補う。
                                     手動実装の反映は §5.2）
 TYPES / STATUS / ...
 (メンバースコープ解決)           … 生成クラスを owner とするネスト分類子生成（SI.Enumish.Companion）と
                                    メンバーシグネチャ生成（entries / valueOf / valueOfOrNull /
                                    enumishCompanion / enumizedClass / label / asEnumish。toString は含まない）
 BODY_RESOLVE
 CHECKERS                        … プラグイン診断（§8）
        │
        ▼ fir2ir
[IR]
 IrGenerationExtension           … EntriesHolder（IR-only）生成、kind の toString の IR-only 生成、
                                    FIR 生成メンバーのボディ充填
        │
        ▼ 各バックエンド lowering / シリアライズ（JVM class / klib / metadata）
```

FIR は「宣言の形状」（シグネチャ・supertype・診断）だけを担い、**ボディは一切作らない**。  
IR がすべてのボディと IR-only の実体（EntriesHolder）を作る。  
この分割は IC 安全性の根幹である（§5 の P2）。

## 4. 成果物対応表（何を・どの層で・どのファイルに帰属させて生成するか）

entries / valueOf の実体は IR-only の EntriesHolder へ委譲する（IC 帰属の一元化 = P1 と、実装詳細の ABI からの隔離）。

対象例: `@Enumize sealed interface SI`（ファイル Si.kt）、末端 class `Foo`（Foo.kt）、末端 object `Bar`（Bar.kt）。

| 成果物 | 宣言層 | ボディ層 | 帰属ファイル | 継承者の集合への依存 |
|---|---|---|---|---|
| `SI : Enumized<SI.Enumish>`（supertype 追加） | FIR (SupertypeGeneration) | — | Si.kt | なし |
| `SI.Enumish`（sealed interface : 基底 `Enumish`） | FIR (DeclarationGeneration, nested) | — | Si.kt | inheritors 属性のみ（§5.2） |
| `SI.Enumish.Companion : EnumishCompanion<SI.Enumish>` | FIR（多段ネスト生成） | — | Si.kt | なし |
| `Companion.entries` / `valueOf` / `valueOfOrNull`（override 宣言） | FIR（シグネチャのみ） | IR（ホルダー委譲） | Si.kt | ボディのみ間接 |
| `SI.Enumish.enumishCompanion`（override val・default 実装。返り値型を `SI.Enumish.Companion` へ共変絞り込み） | FIR（シグネチャ） | IR（`Companion` 返却） | Si.kt | なし |
| `SI.Enumish.enumizedClass`（override val・**抽象**。返り値型を `KClass<out SI>` へ共変絞り込み。実装は各 kind） | FIR（シグネチャのみ） | —（抽象宣言。ボディはどこにも生成しない） | Si.kt | なし |
| **EntriesHolder**（`SI.Enumish` 内ネスト object : `EnumishEntriesHolder<SI.Enumish>`。IR-only のため Kotlin ソースから不可視 = 設計02 §4.1） | **IR のみ** | `createEntries()` の実装（kind の列挙）と `enumizedRootClass` の実装（基底 SI の class リテラル） | Si.kt | **あり（ここに集約）** |
| 末端が object の場合: supertype `SI.Enumish` 追加 | FIR (SupertypeGeneration) | — | Bar.kt | なし |
| 末端が object 以外の場合（class / enum class / interface。open / abstract class・fun interface を含む = §4.1）: companion（既存流用 or 新規生成）へ supertype `SI.Enumish` 追加 | FIR | — | Foo.kt | なし |
| kind の `label` override | FIR（シグネチャ） | IR（単純名の const） | 末端側のファイル | なし |
| kind の `enumizedClass` override | FIR（シグネチャ） | IR（末端の class リテラル） | 末端側のファイル | なし |
| kind の `toString` override（生成の有無は概要 §4 の 2 原則 = §4.1。明示的な実装を持つ kind には生成しない） | **IR のみ**（宣言ごと生成 = 設計02 §5.3） | IR（label 返却） | 末端側のファイル | なし |
| 末端の `asEnumish()` override（末端 enum class への生成を含む） | FIR（シグネチャ） | IR | 末端側のファイル | なし |

この表の要点は、**継承者の集合に依存する生成物が「Si.kt 帰属」だけに閉じている**ことである（P1/P2 の実装）。  
末端側のファイルへの生成物（label / enumizedClass / toString / asEnumish / companion）は、いずれも「自分自身と基底、
および kind 自身の supertype 連鎖（toString の生成条件が参照する。§4.1）」にしか依存しない。

### 4.1 表の補足

- **中間 sealed には何も生成しない**（asEnumish は抽象のまま継承される）。
- **非 final な末端（open / abstract class・interface・fun interface）も末端として扱い、通常どおり生成する**。  
  末端 class と同じく companion が kind になり、`label` / `enumizedClass` / `toString` / `asEnumish`
  を生成する（interface の場合、`asEnumish` は default 実装として生成する）。  
  **これが entries の完全性を壊さない**のが要点である: 第三者が階層外で末端のサブタイプを作れるが、
  そのサブタイプは `asEnumish()` の実装を末端から継承するため、**新しい kind を作らず継承元の kind に吸収される**。  
  entries の要素は「階層内の末端」で決まり、階層外のサブタイプの有無に依存しない。  
  値単位の `when` の網羅性も、`is <末端>` の枝がサブタイプをすべて覆うため成立する。  
  したがって非 final な末端は「拡張点を開いたまま enum 的 API を得る」ための正当な構成である。  
  ただし**ある型が 2 つ以上の末端のサブタイプになると kind が一意に定まらない**ため、
  これは `ENUMIZE_AMBIGUOUS_KIND`（§8）で禁じる。
- **`ordinal` 相当と `Comparable` は提供しない**（概要 §4）。  
  sealed 階層の序数は宣言順に定まらず（コンパイラが提供する継承者順に従う = §6）、改名で変動するため永続化に使えず、
  「使ってはならない値」を API 表面に置く弊害の方が大きい。  
  `Comparable` は序数の存在が前提であるため併せて不提供である。  
  帰結として、順序に依存する生成物は EntriesHolder の `entries` の並びと生成 Enumish の inheritors 属性の並び（§5.2）の
  2 つだけであり（いずれも Si.kt 帰属）、**末端側のファイルには順序に由来する値を一切焼き込まない**（P1
  の維持が単純になる）。
- **entries の保持・遅延初期化・label による探索・失敗メッセージの構築は runtime-api の基底クラス `EnumishEntriesHolder<T>` に集約する**（概要 §2）。  
  生成する EntriesHolder が担うのは **supertype の指定（型引数）・`enumizedRootClass` の実装・`createEntries()` の実装（kind
  を §6 の順序で並べる）の 3 つだけ**であり（設計02 §4）、生成される valueOf / valueOfOrNull は `getByLabel(value)` /
  `getByLabelOrNull(value)` への 1 行委譲になる。  
  EntriesHolder は IR-only（ABI 保証外）であり、実装方式の変更を Kotlin ABI に露出させない継ぎ目として機能する。
- **`toString` は概要 §4 の 2 原則で扱う**（明示実装を持つ kind には生成しない / 持たない kind には `label` を返す
  `toString` を必ず生成する。生成先は kind 側 — interface には `Any` メンバーの default 実装を書けないという言語制約が
  あり、基底 Enumish / 生成 Enumish 側には置けない）。  
  `toString` は表示専用で entries / valueOf / asEnumish の整合性に影響しないため、手動宣言・override を診断（§8 の
  ENUMIZE_MEMBER_CONFLICT）の対象にもしない。  
  **生成は宣言・ボディとも IR-only で行い、FIR には何も置かない**（FIR 宣言が不要である理由・IR で判定する利点・
  判定条件の詳細は設計02 §5.3）。  
  生成条件が参照するのは kind 自身の宣言と supertype 連鎖のみであり、**継承者の集合には依存しない**。  
  FIR の宣言形状は toString を含まないため P2 の対象外であり、supertype 側の `toString` の増減は通常の ABI 変化として
  kind 側ファイルの再コンパイルを誘発するため、IC 上も安全である。
- **`enumishCompanion` は基底で `EnumishCompanion<Enumish>` と宣言し、生成 Enumish が具体型（`SI.Enumish.Companion`）へ default 実装つきで共変 override する**（型付けの帰結は概要 §2。共変の成立・束ねの成立とも実測済み）。
- **`enumizedClass` は kind に対応する末端の class リテラルを返す**（役割・共変 override の連鎖・非 final 末端の帰結は概要 §2）。  
  生成 Enumish では**抽象のまま**共変 override し（実装は持たない）、各 kind が `KClass<末端の型>` へ絞り込んで実装する
  （ボディは IR で充填）。  
  型パラメータ付きの末端・基底では class リテラルの型は star projection になる（`KClass<Foo<*>>`）。
- **`@JvmStatic` は v1 では付与しない**（Java からの呼び出し形は概要 §3）。  
  ソース Kotlin では **override メンバーへの `@JvmStatic` が禁止**されており、生成宣言（= override）にも同じ検査が及ぶ
  可能性が高い。  
  この不確実性を v1 に持ち込まないため付与せず、`SI.Enumish.getEntries()` 形の static アクセスは将来拡張とする
  （損失は Java からの呼び出し形だけであり、他ターゲットには影響しない）。

## 5. IC 設計

「基底と継承者のファイルが分かれていて片方だけが編集されても壊れない」ことは、本プラグインの一級要件である。  
本設計はこれを自前の依存追跡で解こうとせず、**コンパイラが sealed のために既に持っている性質に相乗りする**方針を採る。

**依拠する事実（階層不変条件・§1）**: Kotlin コンパイラ自身が (a) `when` の網羅性の検査と (b) sealed
サブクラス一覧のメタデータへの焼き込み、という 2 つの目的のために、
継承者の集合が変化したときは **sealed 階層を 1 単位として再コンパイルする**。  
成立範囲・実測・環境限定は §1 のとおりである。

この事実があるため、プラグインは「継承者の集合に依存する生成物を、
必ず一緒に再コンパイルされる場所に置く」だけでよい（編集ケースごとの帰結は §5.3）。

**共連れが成立しない編集がある**（新規ファイルでの末端追加・生成物から参照されない中間 sealed の単独編集。§1）。  
基底不在のラウンドでも末端側の生成が成立することは、帰属（P1）とは独立に満たす必要がある要件であり、IR
側のボディ充填を階層の走査ではなく生成宣言の origin で駆動することで満たす（設計02 §1）。

この方針を実装規則へ落としたものが、次の 3 原則である。

### 5.1 IC 安全 3 原則

- **P1（帰属の原則）**: 継承者の集合に依存する生成内容（entries の実体 =
  EntriesHolder）は、**基底クラスのファイルに帰属する宣言としてのみ生成**する。  
  基底ファイルが入るラウンドでは、すべての継承者がソースとして可視な状態で再生成される。  
  基底ファイルが入らないラウンド（§5 冒頭）では再生成されず、集合の変化は IC のラウンド反復による収束で反映される。  
  **1 巡目を完走できることが前提**であり、そこで失敗すると後続ラウンドに到達しない。  
  新規ファイルでの末端追加の実測（Kotlin のビルドレポートで 3 巡）は次のとおりで、
  最終的な成果物は同一ソースの clean ビルドとバイト一致する。
  - 1 巡目（新規末端 + 利用側。基底は入らない）が末端の `.class` を書く
  - その ABI が基底の継承者集合を変えるため、IC が基底クラスを変更シンボルとみなす
  - 2 巡目で基底ファイルが再コンパイルされ、EntriesHolder が最新の集合で再生成される
  - 生成 Enumish の変化が 3 巡目を呼び、その参照側が追随して収束する
- **P2（形状独立の原則）**: FIR に公開する宣言の**シグネチャ**は継承者の集合に依存させない。  
  集合に依存するのは IR のボディと、生成 Enumish の inheritors 属性（§5.2）のみ。  
  IDE（FIR のみ動く環境）での解決が階層列挙に依存しなくなる効果もある。
- **P3（非集約の原則）**: モジュール内の `@Enumize` 全件を列挙して 1 つの宣言（レジストリ・ガワ・
  トップレベル合成ファイル）に焼き込むことをしない。  
  プラグインによるグローバル探索では、IC 下で当該ラウンドのソースしか見えないという問題（KT-55982）が公式に認識されてお
  り、2.3+ の保守的な機構（KT-75864）の下でも「述語にマッチしたファイルを常に再コンパイルする」という税を払うことにな
  る。  
  ネスト生成に留めればこの税自体を回避できる。  
  JVM + Gradle で実測済みであり、階層外の無関係なファイルの編集・新規 `@Enumize` 階層の追加・独立した 2 階層の片側編集・
  下流モジュールでのサブタイプ追加のいずれでも、既存の階層は dirty にならない。

### 5.2 継承者の集合への依存の唯一の例外: inheritors 属性

生成 Enumish を sealed にするため、その継承者リストを `FirRegularClass.setSealedClassInheritors` の
**lazy オーバーロード**でプラグイン自身が登録する（コンパイラの収集器はソース宣言の sealed しか処理しないため）。  
これは「継承者の集合に依存する FIR 情報」だが、

- Si.kt 帰属の宣言に載る（P1 準拠 = 階層が変わるビルドで必ず再計算される）
- lazy 登録により、SUPER_TYPES 段階での階層列挙（フェーズ違反リスク）も回避する

**一覧に載せるべき内容**は「生成 Enumish のすべての直接実装」であり、次の 2 種からなる:

1. **すべての kind の ClassId** — 基底 SI の inheritors 属性から中間 sealed を再帰展開して算出できる（設計01 §5.2）
2. **手動実装（§1）のうち生成 Enumish を直接実装する階層内のもの**（末端 class 自身が `SI.Enumish` を実装する形）の
   ClassId — 階層走査の過程で検出でき、sealed の網羅 when にはその枝も必要になる（概要 §3・§8）。  
   **階層外の手動実装**（例: 同一パッケージの `object Rogue : SI.Enumish`）は述語にも階層走査にも掛からず、lazy
   計算単独では列挙できない。  
   収集器（`FirSealedClassInheritorsProcessor`）はソースクラスの supertype として生成 sealed を発見して収集はするが、
   属性の設定はソースツリー上の宣言に対してのみ行うため、**生成 sealed へ属性が設定されることはない**（実測。
   収集結果は破棄され、プラグインの lazy 登録が上書きされることもない）。  
   パッケージ限定のソース走査による列挙も、IC ラウンドでは当該ラウンドのソースしか見えず clean / incremental
   の生成物一致（§9）を壊すため採らない。  
   したがって階層外の直接実装は `ENUMIZE_MANUAL_IMPL_OUTSIDE_HIERARCHY`（§8）で**コンパイルエラー**とし、
   一覧は 1・2 で完全になる（エラーにしなければ、一覧に無い実装が JVM の `PermittedSubclasses` により実行時拒否 —
   `IncompatibleClassChangeError` — になる）

**検証状況**: 生成 Enumish は sealed であり、属性はメタデータへ `sealed_subclass_fq_name` として直列化され、
別コンパイル単位からの kind-when の網羅性が成立する。  
companion kind の等値枝（`Foo.Companion ->`）・companion 短縮形（`Foo ->`）・object kind の等値枝・`is`
枝は網羅性の判定に算入され、可視範囲の内側からの else 省略も成立する。  
短縮形が成立するため、これを利用手引きの正典とする（= 概要 §6）。  
階層内の手動実装は継承者一覧へ反映され、階層外は上記のとおりエラーにする。  
以上は JVM で確認済みであり、属性の klib への直列化も確認済みである（§7）。  
末端の追加は ABI 差分として未編集の利用側モジュールを再コンパイルさせ、else 無しの kind-when
が網羅性エラーとして再検査される。  
未検証範囲として残るのは IDE（Analysis API）での動作のみである（§10）。

また、**else 不要の網羅が成立するのは、すべての kind（と手動実装）が呼び出し側から可視の場合に限る**。  
可視性の低い継承者を持つ sealed に対する言語側の挙動と同じく、
判定は **呼び出し側の位置に依存する**（可視範囲の内側からの else 省略・外側での else 要求とも確認済み）。  
可視範囲の内側（例: private 基底と同一ファイル）から書く when は通常どおり else なしで網羅し、else が必要になるのは、
可視範囲の**外側**から when を書く場合だけである（internal 基底をモジュール内のより狭い可視性の kind
と混在させた場合のほか、基底より広い可視性の末端を持つ階層 — sealed interface では言語上成立する — では、
基底が見えない位置でも末端型の値から `asEnumish()` を呼べるため同様に生じる。エッジケースへの対応方針 §1）。

### 5.3 編集ケース分析（親子ファイル分離時に片側だけ編集されたらどうなるか）

前提: 階層不変条件（§1 の環境限定つき）。「利用側」= 階層外・他モジュールを含む参照側。

| # | 編集 | dirty になるもの（実測 + 機構） | プラグイン上の帰結 |
|---|---|---|---|
| 1 | 末端側のファイルのみ編集（ABI を変えない変更を含む） | 階層の全ファイル（実測: private メンバーの追加やコメントのみの変更でも共連れ） | Si.kt が再コンパイルされ、EntriesHolder と inheritors 属性が最新の階層から再生成される |
| 2 | 末端の追加（新規ファイル） | 1 巡目は追加ファイルと基底を参照する利用側のファイルのみで、**基底ファイルは入らない**。2 巡目以降で基底ファイル、次いでその生成物を参照するファイルが dirty になる（§5.1 P1 の収束） | entries に新しい末端が反映される（反映は基底が入る 2 巡目）。利用側の kind-when は網羅性エラーで検出される |
| 3 | 末端の削除（ファイル削除） | 同上（多ラウンドで収束する） | entries から消える。削除された kind を参照する利用側はコンパイルエラーになる |
| 4 | 基底のみ編集 | 階層の全ファイル | 末端側の生成物（label / enumizedClass / toString / asEnumish / companion）も再生成される |
| 5 | 内容を変えないファイルの改名・末端のファイル間移動 | 対象ファイルが dirty → 階層共連れ | **生成物は不変**（継承者一覧が FQN 順に正規化済みであり、ソースの配置に依存しないため。§6.1）。バイト一致テストで不変であることを確認する |
| 6 | **末端（または外側クラス）の改名** | 改名したファイルが dirty → 階層共連れ | ClassId が変わるため entries の FQN 順の並びが再配置される。加えて**末端自身の改名では label も変わる**ため valueOf の呼び出し側にも影響する（外側クラスの改名では label は不変であり、並びと `enumizedClass` の指す ClassId だけが変わる） |
| 7 | 手動 companion の追加 / 削除（既定名 `Companion`） | 末端側のファイルが dirty → 階層共連れ。**companion クラスの存在と名前は不変**（生成 companion も public な `Foo$Companion` であり、どちらの状態でもクラスは存在する。手動 companion に書いたメンバーは通常のメンバー追加として ABI に現れる） | 自動生成と流用が切り替わるだけで、利用側から見た形は変わらない |
| 7-b | 手動 companion の追加 / 削除（**名前つき** `companion object Factory`） | 末端側のファイルが dirty → 階層共連れ。`Foo$Companion` ⇔ `Foo$Factory` のクラス名の変化が ABI 差分として利用側へ伝播する | **label は変わらない**（label は末端宣言 `Foo` の単純名であり、kind を担う companion の宣言名には依存しない。§8 の label 規則）。したがって `valueOf` の呼び出し側は影響を受けない。影響が及ぶのは kind を修飾名で名指しする側（`Foo.Companion ->` → `Foo.Factory ->`。短縮形 `Foo ->` は不変）である。stale 出力（旧 companion class）の掃除は、「末端側のファイルの出力」として IC が追跡する |
| 7-c | 既存 companion の可視性の変更（public ⇔ internal） | 同上 | `asEnumish` の返り値型が `Foo.Companion` ⇔ `SI.Enumish` で切り替わり（設計01 §5.4）、ABI 差分として利用側へ伝播する。private / protected への変更でも返り値型は規則 2（`SI.Enumish`）のままで、kind は IR-only アクセサ経由で参照され build は成立する（設計02 §4.3・概要 §8）。基底より広い可視性の末端では、internal への変更が `ENUMIZE_KIND_TYPE_NOT_DENOTABLE` になる場合がある（設計01 §5.4 の規則 3） |
| 8 | label 衝突の導入 / 解消（別ファイルに同名の末端を追加した場合など） | 階層共連れ | CHECKERS が `ENUMIZE_LABEL_CLASH` を報告 / 解除する。報告は当該ラウンドでコンパイルされる当事者（新規ファイル追加のラウンドでは追加した末端）に出る（設計01 §7.1 の報告先規則） |
| 9 | 中間 sealed の追加 / 除去 | 階層共連れ | 末端を再帰的に収集し直し、順序を再計算する |
| 10 | 階層外の無関係なファイルの編集 | 階層は dirty にならない（実測。逆方向 = 階層の再コンパイルに無関係なファイルが共連れされないことも実測） | 生成物は再生成されない（P3 により dirty 税も発生しない。JVM + Gradle で実測済み） |
| 11 | ライブラリ側で末端を追加（跨モジュール） | 利用側: sealed リストの ABI 差分 → 基底を参照するファイルが dirty（実測） | 利用側の kind-when / 値 when が再検査される |
| 12 | **階層外の手動実装**（`object Rogue : SI.Enumish`。§1）**の追加 / 削除** | 追加したファイルのみが dirty | 追加は `ENUMIZE_MANUAL_IMPL_OUTSIDE_HIERARCHY` のコンパイルエラーとして当該ファイル単体で顕在化する（診断は宣言単体の条件検査であり、階層の共連れを要しない）。階層内の手動実装（末端 class 自身による実装）は階層のファイルに属するため、#1 の階層共連れで inheritors が再計算される |

このうち #6（改名による entries の並びの再配置）は enum に無い編集意味論（enum
の宣言順は改名で不変）であり、#5（配置の変更で生成物が不変であることの確認）と併せてテストマトリクス（§9）の重点ケースで
ある。

## 6. entries の順序

**本プラグインは順序を規定しない。** entries の並びは、Kotlin コンパイラが sealed
の継承者一覧に対して用いる正規化順に**従う**だけである。  
プラグイン独自の順序（宣言順など）は定義しない — 宣言順は全順序として規定できず（ファイル名という人工的なキーを要し、
ファイルの改名や移動、Unicode 正規化の差で並びが揺れる）、かつコンパイラ・
リフレクション・KSP と並べ替えの基準が食い違うことになるためである。

### 6.1 従う順序（コンパイラ側の性質）

コンパイラは sealed の継承者一覧を **FQN 文字列（`ClassId.asFqNameString()` = `pkg.Outer.Inner` 形式）の UTF-16 序数昇順（大文字小文字を区別・ロケール非依存）**
に正規化して保持する。  
`KClass.sealedSubclasses` や KSP が返す順序もこれである。

**正規化はセッター側で行われる**: `FirRegularClass.setSealedClassInheritors`（lazy オーバーロード含む）が属性へ格納する
時点で `sortedBy { it.asFqNameString() }` を適用する（Kotlin リポジトリ
`compiler/fir/tree/.../declarations/SealedClassInheritors.kt`）。  
収集側（`FirSealedClassInheritorsProcessor`）はファイル・宣言の訪問順で貯めるが、属性へ格納する時点で必ずソートされる。  
したがって **`getSealedClassInheritors` は直列化を待たずに常に FQN 順を返し、ソースの配置（ファイル順・宣言順）には依存しない**。  
直列化（`FirElementSerializer`）はこの属性をそのまま書き出すため、メタデータの順序も同じである。

> Kotlin 2.4.0 実測: ネストされた末端 `S.Aaa` / `Box.Bbb`・トップレベルの末端 `Mmm` / `Zzz` / `aLower` の混在階層で
> `sealedSubclasses = [Box.Bbb, Mmm, S.Aaa, Zzz, aLower]`。  
> 単純名昇順（Aaa 先頭）・宣言順（Zzz 先頭）・大文字小文字を無視した順（aLower
> 先頭）のいずれでもなく、**FQN 序数順**であることが判別できる。

この正規化順はコンパイラの**実装詳細であり公式な保証は無い**（KSP に宣言順を提供してほしいという要望も not-planned
でクローズされている）。  
本プラグインはこれを、Kotlin のマイナーバージョン毎のアーティファクト分割（§1）と §9 の決定性テスト（clean / incremental
のバイト一致 + サポート対象の Kotlin 全マイナーで順序の回帰を検出すること）によって受容する。

### 6.2 プラグインは並べ替えない

**プラグインは entries の並びに一切介入しない。** ソートも安定化も行わず、
コンパイラから受け取った継承者リストの順序をそのまま使う。  
中間 sealed に到達したらその継承者リストへ再帰的に降り、戻ってきたら次の要素へ進む —
**この深さ優先の走査でできた並びがそのまま entries になる**。

```
SI の継承者リスト = [Bbb, Mid]      （コンパイラ提供）
Mid の継承者リスト = [Aaa]           （同上）
                 ↓ Mid の位置をその継承者で置き換える
entries          = [Bbb, Aaa]
```

したがって entries の並びは「**コンパイラが提供する順序を、中間 sealed の位置で入れ子に展開したもの**」である。

- **中間 sealed が無い階層**では、entries はコンパイラが提供する順序そのものであり、§6.1 の正規化順（FQN
  序数順）と一致する。  
  末端がすべて基底にネストしている、またはすべてトップレベルにある構成なら、
  これは単純名（= 既定の label）の昇順とも一致する（概要 §5）
- **中間 sealed がある階層**では、全体としては FQN 序数順に**ならない**場合がある。  
  中間 sealed の継承者が中間の内側にネストしていない構成がこれにあたる:

  ```kotlin
  sealed interface SI
  sealed interface Mid : SI     // pkg/Mid
  object Aaa : Mid              // pkg/Aaa  ← Mid の内側ではなくトップレベル
  object Bbb : SI               // pkg/Bbb

  // SI の継承者は FQN 順で [Bbb, Mid] → 展開して entries = [Bbb, Aaa]
  // 末端集合を FQN 順に並べたなら [Aaa, Bbb] になるが、そうはならない
  ```

  末端が中間 sealed の内側にネストしている通常の構成では、ネストした末端の FQN が中間の FQN を接頭辞に持つため結果的に
  FQN 序数順と一致する

- 生成 Enumish の inheritors 属性（§5.2）も同様に、収集した順のまま登録する。  
  属性へ格納される時点でセッター側の正規化（§6.1）が働くため、プラグイン側で整える必要はない

### 6.3 帰結

- **決定性とソースの配置への非依存は保たれる**。  
  各段の継承者リストは属性へ格納される時点で FQN 順に正規化されており（§6.1）、
  プラグインの走査は再帰の順序だけで決まるため、ファイル名・ファイル順・宣言位置を変えても entries の並びは変わらない。  
  順序が変わるのは**末端（またはその外側クラス）の改名・追加・削除**、
  および階層の入れ子構造の変更のときである（回帰は §9 の決定性テストが clean / incremental
  のバイト不一致として検出する）
- 順序は `entries` の並びとしてのみ観測される。  
  **序数（`ordinal` 相当）は API として公開しない**（§4.1・概要 §4）ため、
  順序の変動が利用側の永続化データを壊す経路は設計上存在しない（利用者が `entries.indexOf(...)`
  の値を自前で永続化してはならない旨は概要 §5 に明記している）。  
  この「序数を公開しない」設計が、順序に介入しない方針の前提でもある

## 7. クロスモジュール・マルチプラットフォーム

- 階層は言語仕様上、単一モジュール・単一ソースセットに閉じる。  
  したがって**すべての生成は定義モジュール内で完結**し、「モジュールを跨いだ生成」は存在しない。  
  跨モジュールの考慮点は参照側に集約される:
  - 生成 API は通常の宣言としてメタデータ / klib に載るため、プラグイン未適用の利用側からも参照できる
  - 跨モジュールの kind-when の網羅性のみ、生成 Enumish の inheritors の直列化（JVM のメタデータ・klib
    のいずれも確認済み）に依存する
- **metadata コンパイル**: common ソースセットの `@Enumize` は metadata コンパイルでもプラグインが動作し、
  生成宣言が共通メタデータに載る（実測確認済み）。  
  直列化はネスト分類子スコープ経由で生成拡張へ問い合わせる経路であり、
  専用の provider 拡張は要さない — 代わりに**生成拡張の名前集合の問い合わせが生成後にも同じ答えを返すこと**（設計01
  §6.1 の実装要件）が前提になる。  
  metadata コンパイルと各 platform コンパイルの間で生成結果が決定的に一致すること（§6 の順序）が前提条件である。
- **expect/actual**: `@Enumize` の expect / actual 宣言への付与は v1 ではいずれもエラーとする（概要 §7・§8）。  
  expect は actual 毎に階層が変わりうるため（`ENUMIZE_ON_EXPECT`）、actual は生成物の注入（supertype `Enumized<T>`・
  ネスト宣言 `SI.Enumish`）が expect-actual マッチングと両立するか未検証のため（`ENUMIZE_ON_ACTUAL`）である。
- **旧バイナリとの実行時組み合わせ**: entries はホルダーを経由して実行時に解決されるので、
  実行時に存在する版の集合が返る。  
  この性質を保つため **entries アクセサを inline にしない**ことを設計制約とする。
- 継承者が別のソースセットへ逸脱する構成は**コンパイラ本体の診断に委ねる**（プラグインは補足診断を持たない）。  
  別ソースセットの継承者は基底の sealed 継承者一覧に載らないためプラグインからは観測できず、
  本体の言語エラーが sealed の同一モジュール制約を明示するので補足の必要性も薄い（設計01 §7.2）。

## 8. 診断カタログ

診断 ID の一覧・検査ロジック・報告位置・メッセージは [設計01](コンパイラプラグイン設計01.md) §7.2
を正とする（実装は `EnumizeErrors`）。  
本書が定めるのは次の設計方針のみである。

- エラーにするのは、enum 的意味論（entries の完全性・label の一意性・kind の一意対応）を壊す構成と、
  生成への干渉が生じる構成に限る。  
  **手動実装（§1）のうち階層内のものと基底 Enumish の実装を対象とする診断は存在しない**（概要 §8 の許容）
- 診断 ID は英語の識別子であり、本文の日本語用語となるべく合わせる
- **診断実装の設計制約（単調性）**: マルチラウンド IC では階層の部分集合ビューで CHECKERS が走るラウンドが存在しうる。  
  診断は部分集合ビューで**偽陽性を出してはならない**（検査対象は「見えているメンバーの性質」のみに依存させる。
  「階層全体の完全性」に量化する検査を追加する場合はこの制約と両立させる）。  
  現行のカタログは全て条件検査型であり単調である

## 11. IDE についての前提

IntelliJ の K2 モードはサードパーティ FIR プラグインをデフォルトでロードしない（KTIJ-29248、Backlog）。  
当面のデフォルト体験は「CLI / Gradle ビルドは正しいが、エディタでは生成 API が未解決」である。

- P2（形状独立）により、エディタが生成宣言を解決できない場合でも赤くなる範囲は生成 API の参照箇所に限られる
- プラグインがロードされる環境では、**生成クラスの中にネストされたクラス**（`SI.Enumish.Companion`）の解決に
  KT-84625（`Analysis API. FIR` / `Analysis API. Providers and Caches`。Fixed）の修正が必要である。  
  2.4.0-Beta2 で修正済みであり、**実用下限を 2.4 とする根拠はこの IDE / Analysis API 側の事情である**（CLI / Gradle の
  codegen はこの修正に依存しない。§1・設計01 §5.1）
- 緩和策として、コミュニティの Kotlin External FIR Support（KEFS）への対応（`<kotlin-version>-<lib-version>`
  形式でバージョン別のアーティファクトを公開すること）と、JetBrains の compiler plugin devkit（KT-82617）を追跡する
