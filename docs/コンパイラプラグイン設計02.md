# コンパイラプラグイン設計 02: IR 部分の詳細

本書は IR（バックエンド）側の詳細設計を定める。全体感・用語（無限定の「基底クラス」= `@Enumize` 対象の  
sealed 基底、という表記規約を含む）・成果物対応表・IC 原則（P1/P2/P3）は  
[設計00](コンパイラプラグイン設計00.md)、FIR 側で生成される宣言の形状は  
[コンパイラプラグイン設計01.md](コンパイラプラグイン設計01.md) を前提とする。  
利用者視点の仕様は [概要.md](概要.md) を正とする。

IR 側の責務は次の 3 つである:

1. **EntriesHolder**（継承者の集合に依存する実体）の IR-only での生成 — 基底ファイル帰属（P1）
2. FIR が形状だけ生成した全メンバーの**ボディの充填**
3. kind の **`toString` override の IR-only 生成**（生成可否の判定・宣言・ボディのすべて。§5.3）

## 1. エントリポイントと処理の流れ

`IrGenerationExtension.generate(moduleFragment, pluginContext)` で以下を行う:

```
1. moduleFragment を走査し、対象クラスを 2 つに分けて確定させる
   - 生成宣言の持ち主（origin = EnumizeKey の宣言を直下に持つクラス）
   - @Enumize 付き基底クラス
2. 各持ち主について（末端側。基底の同席に依らない）:
   a. 末端側のファイル帰属の生成メンバー（asEnumish / label / enumizedClass）のボディを充填する（§5.2）
   b. 生成 object のコンストラクタを補完し、kind の toString を宣言ごと生成する（§5.3）
3. 各 @Enumize 基底について（基底側。基底がラウンドに同席するときだけ走る）:
   a. 階層の末端を列挙し（§2）、順序を決定する（§3）
   b. 生成 Enumish の中に EntriesHolder を IR-only で生成する（§4）
   c. 基底ファイル帰属の生成メンバー（entries / valueOf / valueOfOrNull / enumishCompanion）の
      ボディを充填する（§5.1）
```

- ボディ充填の対象は **origin = `EnumizeKey`** で発見する（`IrDeclarationOrigin.GeneratedByPlugin`）。  
  名前照合による発見はしない（ユーザーの宣言との誤対応を防ぐ）
- **末端側（2）は階層の走査を伴わない**。基底が IC ラウンドへ入らない編集は実在するため（設計00 §5）、  
  末端側の充填を基底の同席に依存させてはならない。kind に対応する末端は、生成 `enumizedClass` の  
  宣言型 `KClass<末端>` から読む（FIR が確定させた対応をそのまま使う）
- 生成 Enumish とその companion は基底ファイル帰属の生成物であり、2 の対象から外す  
  （Enumish の `enumizedClass` は abstract のまま残す）
- 走査と生成を分ける（1 で対象を確定させてから 2・3 を走らせる）。§4.3 のアクセサ生成と §5.3 の  
  toString 生成はクラスの宣言リストを変更するため、走査中に混ぜられない
- **充填漏れは不変条件違反として検出する**。2・3 の後に生成宣言（abstract を除く）のボディを走査し、  
  空のものがあればどの宣言かを名指しして失敗する。取りこぼしはバックエンドの  
  `Function has no body` として離れた場所で表面化するため、原因の宣言をここで特定する
- 2 は「末端が定義モジュール内にある」前提で成立する。階層は言語仕様上、単一モジュールに閉じるため、  
  **他モジュールの宣言へボディを充填する状況は存在しない**

## 2. 階層の末端の列挙

- 第一候補: **FIR の sealed inheritors 属性**。`IrClass.metadata`（`FirMetadataSource`）経由で基底の  
  `FirRegularClass` を取り、`getSealedClassInheritors(session)` を読む。これはコンパイラが `when` の網羅性検査と  
  メタデータの直列化（`sealed_subclass_fq_name`）に使うものと同一のデータであり、**真実の単一ソース**である  
  （仮に IC 下でこの集合が壊れるとすれば、それは言語機能側のバグであり、プラグイン固有の破損ではない）
- 中間 sealed は再帰的に展開し、**末端のみ**を集める（中間 sealed 自身は entries に載せない）
- 各末端から kind を解決する: object なら末端自身の IrClass、それ以外（class / enum class / interface。  
  open / abstract を含む）ならその companion の IrClass
- ここで列挙するのは**基底 SI の階層 = kind の集合**である。手動実装（設計00 §1。生成 Enumish の直接実装）は  
  kind ではないため entries に載せない — 手動実装が関与するのは FIR 側の inheritors 属性（設計01 §5.2）だけである
- このコードは基底ファイルがラウンドに入るときに走り、そのラウンドでは**すべての末端がソースとして可視**で  
  各末端の IrClass（と ClassId）が取得できる。基底ファイルが入らないラウンドではこの列挙自体が走らないため、  
  末端側のボディ充填はこの列挙に依存させない（§1・設計00 §5）

## 3. 順序の扱い（設計00 §6.2 の実装）

**IR 側は並べ替えを一切行わない。** 末端の列挙（§2）でコンパイラから受け取った継承者リストを先頭から走査し、  
中間 sealed に到達したらその継承者リストへ再帰的に降りる。この走査で現れた順序をそのまま  
`createEntries()` の `listOf(...)` の並びにする。

実装上の規則（決定性・relocatability）:

- ソート・安定化のための比較関数を持たないため、ロケールに依存する比較（Collator 等）が紛れ込む余地もない
- 走査に使うのは継承者リストとその再帰だけである。`IrFile` のパス・ファイル名・宣言オフセット・  
  タイムスタンプ・乱数・環境変数は**一切参照しない**（これらに由来する非決定性を持ち込まないため）
- 走査順を保つコレクション（`List`）だけを使い、`HashSet` / `HashMap` を経由させない  
  （訪問済みガード等で集合が必要な場合も `LinkedHashSet` を用いて走査順を壊さない）

この順序は `entries` の並びとしてのみ観測される（序数を公開する API は無い。設計00 §4.1）。  
コンパイラが渡す各段の継承者リストは属性へ格納される時点で FQN 順に正規化済みであるため（設計00 §6.1）、  
並べ替えをしなくても走査結果はソースの配置に依存しない。

## 4. EntriesHolder の生成（IR-only）

### 4.1 形状

概念形（Kotlin ソース相当。概念名 `EntriesHolder`、実際の出力名は `$EntriesHolder`）:

```kotlin
// SI.Enumish の中にネストされる object。IR のみで生成し FIR には存在しない。
// entries の保持・遅延初期化・label 探索・失敗メッセージの構築は runtime-api の EnumishEntriesHolder が持つ（概要 §2）
object $EntriesHolder : EnumishEntriesHolder<SI.Enumish>() {
    override val enumizedRootClass: KClass<SI> get() = SI::class
    override fun createEntries(): List<SI.Enumish> = listOf(kind_0, kind_1, ...)  // §3 の順序
}
```

生成するのは **supertype の指定（型引数）・`enumizedRootClass` の実装（基底の class リテラルを返す）・  
`createEntries()` の実装の 3 つだけ**である（概要 §2）。IR 側で `Lazy` フィールドやラムダ  
（`IrFunctionExpression`）・文字列結合（`IrStringConcatenation`）を組み立てることはない。

- **配置**: 生成 Enumish のネスト object として生成し、**IR 上の帰属を基底ファイルにする**（P1 の実装）。  
  トップレベルや合成 IrFile には置かない（klib では `IrFile` を自作するとシリアライザの整合性検査に当たる  
  という報告があり、実質的に不可能である。JVM でも、トップレベルへの生成に対する IC の第一級サポートは  
  Open である（KT-66735））
- **可視性**: IR-only 宣言は `@Metadata` に載らないため Kotlin ソースからは不可視。JVM では Java から見えるため、  
  `$` 入りの出力名（`$EntriesHolder`）で偶発的な利用を抑止し、ABI 保証外であることを文書化する
- **klib**: IR-only 宣言は klib に IR ごと直列化され、同一モジュール内でのリンクは成立する。  
  EntriesHolder は**常に同一ファイル内（生成 Companion のメンバーボディ）からのみ参照される**ため、  
  跨モジュールでの IR 署名の参照のような不安定な機構には依存しない
- **JS/Wasm の DCE**: EntriesHolder は生成 Companion のメンバーボディから通常の経路で参照されるため、  
  entries / valueOf が到達可能な限り DCE で消えない（アノテーション経由の参照のような特殊な経路を使わない）

### 4.2 生成する要素

| 要素 | 内容 |
|---|---|
| supertype | `IrPluginContext.referenceClass(ClassId)` で `EnumishEntriesHolder` の `IrClassSymbol` を引き、生成 Enumish を型引数に与えた `IrSimpleType`（`typeWith`）として構成する（ClassId からの静的参照であり、名前解決を経ない） |
| コンストラクタ呼び出し | **no-arg** の super 委譲（`EnumishEntriesHolder` はコンストラクタ引数を持たない — 概要 §2） |
| `enumizedRootClass` の override | 基底 SI の class リテラル（`IrClassReference`）を返す getter。型パラメータ付きの基底では star projection の型になる（`KClass<S<*>>` 相当） |
| `createEntries()` の override | kind を §3 の順序で並べた `List` を返す。kind の参照は `IrGetObjectValue` |

- 遅延初期化は `EnumishEntriesHolder` の `by lazy`（既定の `LazyThreadSafetyMode.SYNCHRONIZED`）が担う。  
  全プラットフォームで安全である（JS / Wasm はシングルスレッドであり、モード自体が無視される。  
  Native は新 MM を前提とするため問題ない）
- 遅延初期化の意味論の差分（enum はクラスロード時に初期化されるのに対し、本設計は初回アクセス時に初期化される）と、  
  **kind の初期化子から entries / valueOf に触れてはならない**という制約（lazy への同一スレッドでの再入 →  
  プラットフォーム依存の未定義動作。JVM 実測では初期化子の二重実行）は、利用者向けの文書化事項である（概要 §6）
- label の探索（`getByLabel` / `getByLabelOrNull`）は entries を先頭から線形に走査し、label が  
  **完全一致する最初の要素**を返す（概要 §2）。label の一意性は ENUMIZE_LABEL_CLASH（設計01 §7.2）が  
  保証するため、最初の一致を返す実装でも結果は一意に定まる
- EntriesHolder は IR-only（ABI 保証外・§4.1）であり、実装方式の変更を Kotlin ABI に露出させない継ぎ目として機能する

> IR-only 宣言に supertype・no-arg の super コンストラクタ呼び出し・abstract メンバーの override を持たせる
> 方式は JVM の codegen と実行を通る（IR-only の宣言で行う公開前例は無い）。**klib の直列化を通ることの確認は
> 残る**（設計00 §10）。klib で不成立の場合は
> **継承を維持したまま `$EntriesHolder` を FIR 生成へ切り替える**（設計00 §10.1。`EnumishEntriesHolder` の
> コンストラクタは no-arg のため runtime-api の変更は不要であり、FIR がシグネチャを宣言し、
> 本節と同じ IR 構築でボディを充填する）。

### 4.3 参照不能 kind の IR-only アクセサ

**方針**: 「private な内容であっても entries は全種取得可能」（概要 §8）とする。`createEntries()` は各 kind を  
`IrGetObjectValue` で直接参照するが、基底本体スコープから名前参照できない kind  
（private / protected な既存 companion・別ファイルの private トップレベル末端・private 外側クラスにネストした末端）は  
JVM 以外のバックエンド（klib）で直接参照が可視性検査に掛かりうる。これらに対しては、アクセス権を持つ位置に  
**IR-only の internal アクセサ**を生成し、`createEntries()` はアクセサ呼び出しで kind を得る。**FIR には宣言を作らない**  
ため（メタデータ非搭載＝ABI 非追加）Kotlin ソースからは不可視であり、外部からの参照はできない  
（他案との比較はエッジケースへの対応方針 §1.4）。

**参照可能性の判定（`base` 本体から kind を名前参照できるか）**: kind の外側クラス連鎖を内側から外へ辿り、  
各クラスの可視性を見る。`public` / `internal` は同一モジュールから参照可。`private` / `protected` のクラスは、  
基底がその宣言スコープの内側（ネストなら外側クラスの subtree 内、file-private なトップレベルなら同一ファイル内）に  
あれば可、無ければ**壁**。壁が 1 つも無ければ直接参照する（public / internal な kind・基底内ネストの  
private 末端）。

**アクセサの配置**: 連鎖中の最も外側の壁 W の container（W.parent）へ IR-only アクセサを置く。W はそこから見て  
直接メンバーであり、壁より内側は壁が無いため kind まで到達できる。

| W.parent | 生成物 | 例 |
|---|---|---|
| クラス | 末端クラス内にネストした `object`（`fun get(): SI.Enumish`）。ネスト object は外側クラスの private / protected companion を intra-scope で参照する | private / protected companion（W = companion, container = 末端クラス） |
| ファイル | 末端ファイルのトップレベル `internal fun`（返り値 = kind）。file-private な壁は同一ファイル内から参照できる | private トップレベル末端 / private 外側クラス（W = 末端 / 外側クラス, container = ファイル） |

`createEntries()` は kind ごとに「直接 `IrGetObjectValue`」または「アクセサ呼び出し」を選び、§3 の順序で `listOf(...)` に並べる。

**MPP / IC 安全性**: どの配置でも「基底ファイルの `createEntries` → 末端ファイルのアクセサ」参照になり、直接参照時の  
「`createEntries` → 末端の kind object」と同じ base→末端方向で、基底ファイルが入るラウンドで再生成される  
（基底不在ラウンドでは基底側の生成そのものが走らない = §1）。  
アクセサ→kind の参照は常にアクセサと同一スコープ内（intra-scope）で klib の可視性検査を通る。名前はアクセサ object を  
`$EnumizeKindAccessor`、トップレベル関数を `$enumizeKindAccessor$<kind の相対名>` とし、kind の安定 FQN から決めるため  
決定的である（多重 private 壁のネストは実利用に無く対象外＝単一壁のみ対応）。全 klib ターゲット（jvm / js / native /  
wasmJs / wasmWasi）と clean / incremental / from-cache での成立を結合テスト（mpp-producer・gradle-integration）が確認する。

## 5. ボディ充填（メンバーごとの生成内容）

§5.1・§5.2 は「FIR が形状を宣言済み・origin = `EnumizeKey`」のメンバーに対する充填である。  
Kotlin の等価コードで示す（IR の構築は `DeclarationIrBuilder` による機械的な組み立てである）。  
**kind の `toString` を除き、生成の有無の判定は FIR 側にある**（設計01 §5.3）— IR は FIR が宣言した  
メンバーを埋めるだけであり、充填対象を独自に増減させない。

### 5.1 基底ファイル帰属（Si.kt）

| メンバー | ボディ（Kotlin 等価） |
|---|---|
| `Companion.entries` (getter) | `return $EntriesHolder.entries` |
| `Companion.valueOf(value)` | `return $EntriesHolder.getByLabel(value)` |
| `Companion.valueOfOrNull(value)` | `return $EntriesHolder.getByLabelOrNull(value)` |
| `Enumish.enumishCompanion` (getter) | `return Companion`（`IrGetObjectValue`） |

- 3 つとも `$EntriesHolder`（`IrGetObjectValue`）へのメンバー呼び出し 1 つで済む
- `valueOf` の失敗メッセージは `No enumish entry with label '<label>' in <基底の simpleName>` 形式である（概要 §2）。  
  組み立ても `enumizedRootClass.simpleName` の取得も `EnumishEntriesHolder` 側にあるため、メッセージは  
  全プラットフォームで同一文言になる（enum の `No enum constant` は Native で文言が異なるが、本 API は割れない）
- `Enumish.enumizedClass` は**抽象宣言のため充填対象が存在しない**（実装は各 kind = §5.2。設計01 §5.3）
- `enumishCompanion` は interface のメンバーの実装である（JVM では default メソッド系の lowering を  
  コンパイラ本体が処理する）。**階層の順序に依存するロジック（entries の構築）が基底ファイルに帰属する  
  ボディに閉じている**ことが、この表の要点である（P1。末端側のファイルには順序に由来する値を一切焼き込まない）

### 5.2 末端側のファイル帰属

| メンバー | ボディ（Kotlin 等価） |
|---|---|
| kind の `label` (getter) | `return "<末端宣言の単純名>"`（`IrConst`。**companion 自身が末端である場合に限り**その宣言名。末端 class の kind を担うだけの companion の宣言名は label に影響しない） |
| kind の `enumizedClass` (getter) | `return <末端の型>::class`（`IrClassReference`）。非 final な末端でも**分類の代表である末端自身**の class リテラルを返す（値の実行時クラスとは一致しない場合がある — 概要 §2）。型パラメータ付きの末端では star projection の型になる（`KClass<Foo<*>>` 相当） |
| 末端 object の `asEnumish()` | `return this` |
| 末端 class / 末端 enum class / 末端 interface の `asEnumish()` | `return Companion`（`IrGetObjectValue`。返り値型は設計01 §5.4 の規則で FIR 側が決定済み）。open / abstract class と interface でもボディは同一で、interface の場合は default 実装のボディとして充填する。末端 enum class も同一である |

いずれも「自分自身と基底」にしか依存しない（P1 の帰結 — 継承者の集合に依存する内容は基底ファイル側に  
閉じているため、末端側のファイルの生成物は兄弟の増減では変化しない）。

### 5.3 kind の toString（IR-only・宣言ごと生成）

kind の `toString` override は **FIR に宣言を持たず、生成可否の判定・宣言・ボディのすべてを IR で行う**。

- **FIR 宣言が不要である理由**: `toString` の解決スロットは `Any` が全型に提供しており、呼び出し側の解決は  
  override の存在に依存しない（実行時の仮想ディスパッチで届く）。kind（object / companion）はサブクラス化  
  できないため「override の存在を見て再 override する」利用者も無く、FIR 宣言の効果（解決可能性・  
  メタデータへの掲載）に消費者が存在しない
- **判定を IR で行う利点**: supertype が完全解決済みであるため、下記の生成条件が単純に計算できる。  
  IDE（Analysis API）は IR 拡張を実行せず、メンバーの存在も解決に観測されないため、  
  CLI / IDE の判定不一致という問題が構造的に生じない

**生成条件**（概要 §4 の 2 原則の実装。対象は kind = 末端 object と kind となる companion）:

- 明示的な `toString` 実装を持つ kind には生成しない:
  1. kind 自身が `toString` を宣言している（IrClass の宣言から判定する。fake override は数えない。  
     生成しないだけで診断はしない — ENUMIZE_MANUAL_MEMBER_CONFLICT の対象外 = 設計01 §7.2）
  2. 継承経路上で**最も派生側**の `toString` 宣言が `Any` 以外の具象実装である（superclass 連鎖を派生側から  
     辿って最初に見つかる宣言で判定する。interface は `toString` の本体を持てないため superclass 連鎖だけを  
     見ればよく、基底 Enumish / 生成 Enumish は `toString` を宣言しないため探索に干渉しない）。  
     **final な継承 `toString` は必ずこの条件に該当する**ため、生成が final override 衝突（言語エラー）を  
     起こす構成は存在しない
  3. 末端 data object（言語が単純名を返す `toString` を合成する）
- 上記に該当しない kind には `toString` を必ず生成する（`Any` の既定表示を許容しない）。  
  ボディは `return label`（label の getter 呼び出しにする。将来 label のカスタマイズを導入したときに  
  自動的に整合するよう、const の直書きにはしない）

実装・境界の注意:

- **fake override の置換**: Fir2Ir は各 IrClass に `toString` の fake override を作る。生成時はこれを  
  実 override（`overriddenSymbols` を継承チェーンへ接続した `IrSimpleFunction`）で差し替え、  
  fake と実の二重登録を残さない
- **抽象再宣言の構成では生成に至らない**: kind の supertype が `toString` を抽象として再宣言している場合、  
  FIR に実装が無い時点でコンパイラ本体の「抽象メンバー未実装」エラーになり、IR は実行されない。  
  この構成では kind 側の手動実装が必要である（概要 §4）。したがって IR が条件 2 を判定する時点で、  
  継承 `toString` の実体は常に「`Any` 直下」か「`Any` 以外の具象実装」のどちらかである
- 生成条件が参照するのは kind 自身の宣言と superclass 連鎖のみで、**継承者の集合には依存しない**。  
  superclass の `toString` の増減は通常の ABI 変化として kind 側ファイルの再コンパイルを誘発するため、  
  clean / incremental の生成物の一致（§6）も保たれる
- **JVM での成立**: FIR に宣言を持たないメンバー override の  
  IR 追加・fake override の置換・スキップ判定（手動宣言・data object 合成）が JVM の codegen と  
  仮想ディスパッチを通過する。**klib への直列化と JS / Native / Wasm での仮想ディスパッチの確認は残る**（設計00 §10）。  
  前例: kotlinx.serialization は `write$Self` と合成コンストラクタをソースクラスへ IR-only で追加している  
  （klib ターゲット含め成立）。またデータクラスの `equals` / `hashCode` / `toString` も FIR には宣言されず  
  fir2ir 段で生成される（解決に FIR 宣言を要するのは `componentN` / `copy` だけ）— `Any` 由来のメンバーは  
  後段生成で足りるという同じ切り分けである

## 6. 決定性・relocatability の保証

生成物のバイト単位での一致（clean / incremental / from-cache / relocated）を守るための実装規則:

1. 並べ替えを一切行わず、コンパイラが渡す継承者リストの走査順をそのまま使う  
   （§3。パス・ファイル名・宣言オフセット・時刻・乱数・環境に依存する値は参照しない）
2. 生成する名前は `$EntriesHolder`、`createEntries()` / `enumizedRootClass` の override、kind の `toString` の  
   override のみで、いずれも固定文字列である  
   （連番やハッシュによるマングリングは不要 — ネストして生成するため名前空間が基底ごとに分かれている）
3. IR の構築順は末端の決定順序（§3）に一致させ、コレクションの走査順に由来する非決定性（HashMap 等）を挟まない
4. 生成コードに埋め込む文字列は kind の label（§5.2）**のみ**である。このほかに class リテラル参照  
   （`enumizedRootClass` の基底・`enumizedClass` の末端）を埋め込むが、これらは ClassId への静的参照であり、  
   文字列・ソースの配置・環境に依存しない。いずれも宣言名から決定的に導出される

これらの規則の回帰は、設計00 §9 の決定性テスト（clean / incremental / from-cache / relocated のバイト一致）が検出する。

## 7. プラットフォーム別の注意

| ターゲット | 論点 | 方針 |
|---|---|---|
| JVM | interface の default 実装（`enumishCompanion` / 末端 interface の `asEnumish`）の lowering。`enumishCompanion` / `enumizedClass` の共変 override には bridge メソッドが生成される（`@JvmStatic` は v1 では付与しない = 設計00 §4.1） | コンパイラ本体の lowering に委ねる（プラグイン側の追加処理はない）。codegen テストで検証する |
| JVM | `$EntriesHolder` が Java から見える | `$` を入れた命名と、ABI 保証外であることの文書化（§4.1） |
| JVM (17+) | 基底 sealed の `PermittedSubclasses` 属性 | コンパイラ本体の既存機能である（プラグインは関与しない）。Java 21 の switch との連携は概要 §3 に記載する |
| klib (JS/Native/Wasm) | IR-only 宣言の直列化・同一モジュール内での参照 | §4.1。跨モジュールでの IR 参照はしない |
| JS/Wasm | DCE | §4.1（通常の参照のみであるため追加の対応は不要） |
| Native | lazy と新 MM | 問題なし（§4.2） |
| 全ターゲット共通 | class リテラル（`enumizedClass` / `enumizedRootClass`）と `KClass.simpleName`（失敗メッセージ） | いずれも stdlib の機能であり kotlin-reflect を要しない。`qualifiedName` は JS 等で利用できないため使わない（概要 §2） |
| 全ターゲット共通 | metadata コンパイル（common ソースセット） | FIR が生成した宣言（生成 Enumish・その Companion・末端の自動 companion・各メンバー）が共通メタデータに載る（実測確認済み。設計00 §7）。EntriesHolder は IR-only であるため metadata klib には現れない（実体は各 platform のコンパイルで生成される。共通コードからの参照は companion / 生成 Enumish の生成メンバーを経由するため問題にならない） |

## 8. no-reflection 保証の確認

生成コード・runtime-api が実行時に使う API の全リスト:

| 使用 API | 分類 |
|---|---|
| `EnumishEntriesHolder`（runtime-api の EntriesHolder 基底）内の `lazy` / `Lazy.value`・`List` の構築と走査 | stdlib + runtime-api（非 reflection） |
| 文字列の比較・文字列の結合・`KClass.simpleName`（`EnumishEntriesHolder` 内での label の照合と失敗メッセージの構築） | stdlib（非 reflection。`simpleName` は kotlin-reflect を要しない） |
| `IrGetObjectValue` によるシングルトン参照（EntriesHolder・kind・生成 Companion） | 静的リンク（非 reflection） |
| `IrClassReference` による class リテラル（kind の `enumizedClass`・EntriesHolder の `enumizedRootClass`） | 静的リンク（非 reflection。`KClass` インスタンスの保持と `simpleName` の参照のみで、members / `qualifiedName` 等には触れない） |

`kotlin-reflect`・`java.lang.reflect`・`Class.forName`・`KClass.sealedSubclasses`・associated object は  
生成コード・runtime-api のどこからも使用しない。**`KClass` を受け取る API も持たない**  
（reified ヘルパを提供しないため。概要 §3）。`KClass` を**返す** API（`enumizedClass` /  
`enumizedRootClass`）は class リテラルの保持と `simpleName` の参照だけを行う（概要 §2）。  
したがって no-reflection は例外条項なしに成立する。
