# コンパイラプラグイン設計 02: IR 部分の詳細

本書は IR（バックエンド）側の詳細設計を定める。全体感・用語・成果物対応表・IC 原則（P1/P2/P3）は
[設計00](コンパイラプラグイン設計00.md)（無限定の「基底クラス」= `@Enumize` 対象の sealed 基底、という表記規約を含む）、FIR 側で生成される宣言の形状は
[コンパイラプラグイン設計01.md](コンパイラプラグイン設計01.md) を前提とする。

IR 側の責務は次の 2 つである:

1. **EntriesHolder**（継承者の集合に依存する実体）の IR-only での生成 — 基底ファイル帰属（P1）
2. FIR が形状だけ生成した全メンバーの**ボディの充填**

## 1. エントリポイントと処理の流れ

`IrGenerationExtension.generate(moduleFragment, pluginContext)` で以下を行う:

```
1. moduleFragment を走査し、origin が EnumizeKey の宣言（= FIR 生成物の IR 対応物）と
   @Enumize 付き基底クラスを収集する
2. 各 @Enumize 基底について:
   a. 階層の末端を列挙し（§2）、順序を決定する（§3）
   b. 生成 Enumish の中に EntriesHolder を IR-only で生成する（§4）
   c. 基底ファイル帰属の生成メンバー（entries/valueOf/valueOfOrNull/enumishCompanion）の
      ボディを充填する（§5）
   d. 末端側のファイル帰属の生成メンバー（label/toString/asEnumish）のボディを充填する（§5）
```

- ボディ充填の対象は **origin = `EnumizeKey`** で発見する（`IrDeclarationOrigin.GeneratedByPlugin`）。
  名前照合による発見はしない（ユーザーの宣言との誤対応を防ぐ）
- 2-d は「末端が定義モジュール内にある」前提で成立する。階層は言語仕様上、単一モジュールに閉じるため、
  **他モジュールの宣言へボディを充填する状況は存在しない**

## 2. 階層の末端の列挙

- 第一候補: **FIR の sealed inheritors 属性**。`IrClass.metadata`（`FirMetadataSource`）経由で基底の
  `FirRegularClass` を取り、`getSealedClassInheritors(session)` を読む。これはコンパイラが `when` の網羅性検査と
  メタデータの直列化（`sealed_subclass_fq_name`）に使うものと同一のデータであり、**真実の単一ソース**である
  （仮に IC 下でこの集合が壊れるとすれば、それは言語機能側のバグであり、プラグイン固有の破損ではない）
- 中間 sealed は再帰的に展開し、**末端のみ**を集める（中間 sealed 自身は entries に載せない）
- 各末端から kind を解決する: object なら末端自身の IrClass、それ以外（class / enum class / interface。open / abstract を含む）ならその companion の IrClass
- 階層不変条件により、このコード（基底ファイルの再コンパイル時に走る）が実行されるラウンドでは
  **すべての末端がソースとして可視**であり、各末端の IrClass（と ClassId）が取得できる

## 3. 順序の扱い（設計00 §6.2 の実装）

**IR 側は並べ替えを一切行わない。** 末端の列挙（§2）でコンパイラから受け取った継承者リストを先頭から走査し、
中間 sealed に到達したらその継承者リストへ再帰的に降りる。この走査で現れた順序をそのまま
`createEntries()` の `listOf(...)` の並びにする。

実装上の規則（決定性・relocatability）:

- **ソート・安定化・並べ替えを一切行わない**（設計00 §6.2）。比較関数を持たないため、
  ロケールに依存する比較（Collator 等）が紛れ込む余地もない
- 走査に使うのは継承者リストとその再帰だけである。`IrFile` のパス・ファイル名・宣言オフセット・
  タイムスタンプ・乱数・環境変数は**一切参照しない**（これらに由来する非決定性を持ち込まないため）
- 走査順を保つコレクション（`List`）だけを使い、`HashSet` / `HashMap` を経由させない
  （訪問済みガード等で集合が必要な場合も `LinkedHashSet` を用いて走査順を壊さない）

この順序は `entries` の並びとしてのみ観測される（序数を公開する API は無い。設計00 §4.1）。
clean / incremental / from-cache / relocated の各ビルドにおけるバイト単位の一致は、テストで検証される（設計00 §9）。
コンパイラが渡す各段の継承者リストは属性へ格納される時点で FQN 順に正規化済みであるため（設計00 §6.1）、
並べ替えをしなくても走査結果はソースの配置に依存しない。

## 4. EntriesHolder の生成（IR-only）

### 4.1 形状

概念形（Kotlin ソース相当。概念名 `EntriesHolder`、実際の出力名は `$EntriesHolder`）:

```kotlin
// SI.Enumish の中にネストされる object。IR のみで生成し FIR には存在しない。
// entries の保持・遅延初期化・label 探索は runtime-api の EnumishEntriesHolder が持つ（概要 §2）
object $EntriesHolder : EnumishEntriesHolder<SI.Enumish>("com.example.SI.Enumish") {
    override fun createEntries(): List<SI.Enumish> = listOf(kind_0, kind_1, ...)  // §3 の順序
}
```

生成するのは **supertype 指定（型引数）・FQN のコンストラクタ引数・`createEntries()` の実装の 3 つだけ**である。
lazy・探索・例外メッセージの構築はすべて `EnumishEntriesHolder` 側にあるため、IR 側で `Lazy` フィールドや
ラムダ（`IrFunctionExpression`）、文字列結合（`IrStringConcatenation`）を組み立てる必要がない。

- **配置**: 生成 Enumish のネスト object として生成し、**IR 上の帰属を基底ファイルにする**（P1 の実装）。
  トップレベルや合成 IrFile には置かない（klib では `IrFile` を自作するとシリアライザの整合性検査に当たる
  という報告があり、実質的に不可能である。JVM でも、トップレベルへの生成に対する IC の第一級サポートは
  Open である（KT-66735））
- **可視性**: IR-only 宣言は `@Metadata` に載らないため Kotlin ソースからは不可視。JVM では Java から見えるため、
  `$` 入りの出力名（`$EntriesHolder`）で偶発的な利用を抑止し、ABI 保証外であることを文書化する
- **klib**: IR-only 宣言は klib に IR ごと直列化され、同一モジュール内でのリンクは成立する。
  EntriesHolder は**常に同一ファイル内（生成 Companion のメンバーボディ）からのみ参照される**ため、
  跨モジュールでの IR 署名の参照のような不安定な機構には依存しない
- **JS/Wasm の DCE**: EntriesHolder は生成 Companion のメンバーボディから通常の経路で参照されるため、
  entries / valueOf が到達可能な限り DCE で消えない（アノテーション経由の参照のような特殊な経路を使わない）

### 4.2 生成する要素

| 要素 | 内容 |
|---|---|
| supertype | `EnumishEntriesHolder<SI.Enumish>` を `ClassId.constructClassLikeType` で構成し、生成 Enumish を型引数に与える |
| コンストラクタ呼び出し | 生成 Enumish の FQN を `IrConst` で渡す（例外メッセージ用。生成時に確定する定数） |
| `createEntries()` の override | kind を §3 の順序で並べた `List` を返す。kind の参照は `IrGetObjectValue` |

- 遅延初期化は `EnumishEntriesHolder` の `by lazy`（既定の `LazyThreadSafetyMode.SYNCHRONIZED`）が担う。
  全プラットフォームで安全である（JS / Wasm はシングルスレッドであり、モード自体が無視される。
  Native は新 MM を前提とするため問題ない）
- 遅延初期化の意味論の差分（enum はクラスロード時に初期化されるのに対し、本設計は初回アクセス時に初期化される）と、
  **kind の初期化子から entries / valueOf に触れてはならない**という制約（lazy への同一スレッドでの再入 →
  StackOverflow）は、利用者向けの文書化事項である（概要 §6）
- label の一意性は ENUMIZE_LABEL_CLASH（設計01 §7.2）が保証するため、`EnumishEntriesHolder` の先頭一致による探索で一意に定まる
- EntriesHolder は IR-only（ABI 保証外・§4.1）であり、実装方式の変更を Kotlin ABI に露出させない継ぎ目として機能する

> IR-only 宣言に supertype とコンストラクタ呼び出しを持たせる方式は、`entries` を直接保持していた旧形より
> IR 構築の手数が減る一方で、生成クラスの super 呼び出しという新しい要素を含む。成立の確認は V2-b に含める。
> 不成立の場合は**継承を維持したまま `$EntriesHolder` を FIR 生成へ切り替える**（設計00 §10.1）。
> その場合 FQN は `EnumishEntriesHolder` の `abstract val` へ移り、本節の「コンストラクタ引数」は不要になる。

## 5. ボディ充填（メンバーごとの生成内容）

すべて「FIR が形状を宣言済み・origin = `EnumizeKey`」のメンバーに対する充填である。
Kotlin の等価コードで示す（IR の構築は `DeclarationIrBuilder` による機械的な組み立てである）。

### 5.1 基底ファイル帰属（Si.kt）

| メンバー | ボディ（Kotlin 等価） |
|---|---|
| `Companion.entries` (getter) | `return $EntriesHolder.entries` |
| `Companion.valueOf(value)` | `return $EntriesHolder.getByLabel(value)` |
| `Companion.valueOfOrNull(value)` | `return $EntriesHolder.getByLabelOrNull(value)` |
| `Enumish.enumishCompanion` (getter) | `return Companion`（`IrGetObjectValue`） |

- 3 つとも `$EntriesHolder`（`IrGetObjectValue`）へのメンバー呼び出し 1 つで済む
- valueOf のメッセージは**全プラットフォームで JVM enum 形式に統一**する:
  `"No enumish constant <生成 Enumish の FQN>.<value>"`。組み立ては基底クラス `EnumishEntriesHolder`（概要 §2）が行い、
  FQN は EntriesHolder のコンストラクタ引数として生成時に渡す（§4.2）。
  enum 自体は Native で文言が異なるが、本プラグインは統一する（enum より一貫している）
- `enumishCompanion` は interface のメンバーの実装である（JVM では default メソッド系の lowering を
  コンパイラ本体が処理する）。**階層の順序に依存するロジック（entries の構築）が基底ファイルに帰属する
  ボディに閉じている**ことが、この表の要点である（P1。末端側のファイルには順序に由来する値を一切焼き込まない）

### 5.2 末端側のファイル帰属

| メンバー | ボディ（Kotlin 等価） |
|---|---|
| kind の `label` (getter) | `return "<末端宣言の単純名>"`（`IrConst`。**companion 自身が末端である場合に限り**その宣言名。末端 class の kind を担うだけの companion の宣言名は label に影響しない） |
| kind の `toString()` | `return label`（label の getter 呼び出しにする。将来 label のカスタマイズを導入したときに自動的に整合するよう、const の直書きにはしない。**末端 data object と末端 enum class には生成しない** — 設計01 §5.3。利用側の override も許容する — 設計00 §4.1） |
| 末端 object の `asEnumish()` | `return this` |
| 末端 class / 末端 enum class / 末端 interface の `asEnumish()` | `return Companion`（`IrGetObjectValue`。返り値型は設計01 §5.4 の規則で FIR 側が決定済み）。open / abstract class と interface でもボディは同一で、interface の場合は default 実装のボディとして充填する |

いずれも「自分自身と基底」にしか依存しない（P1 の帰結 — 継承者の集合に依存する内容は基底ファイル側に
閉じているため、末端側のファイルの生成物は兄弟の増減では変化しない）。

## 6. 決定性・relocatability の保証

生成物のバイト単位での一致（clean / incremental / from-cache / relocated）を守るための実装規則:

1. 並べ替えを一切行わず、コンパイラが渡す継承者リストの走査順をそのまま使う（§3。ファイル名・宣言オフセット・パス・時刻・乱数・環境に依存する値は参照しない）
2. 生成する名前は `$EntriesHolder` と `createEntries()` の override のみで、いずれも固定文字列である
   （連番やハッシュによるマングリングは不要 — ネストして生成するため名前空間が基底ごとに分かれている）
3. IR の構築順は末端の決定順序（§3）に一致させ、コレクションの走査順に由来する非決定性（HashMap 等）を挟まない
4. 生成コードに埋め込む文字列は (a) EntriesHolder のコンストラクタへ渡す生成 Enumish の FQN（§4.2）と
   (b) kind の label（末端宣言の単純名。companion 自身が末端である場合に限りその宣言名。§5.2）の 2 種類のみである。
   いずれも宣言名から決定的に導出され、ソースの配置や環境に依存しない

## 7. プラットフォーム別の注意

| ターゲット | 論点 | 方針 |
|---|---|---|
| JVM | interface の default 実装（`enumishCompanion`）の lowering。`enumishCompanion` の共変 override には bridge メソッドが生成される（`@JvmStatic` は v1 では付与しない = 設計00 §4.1） | コンパイラ本体の lowering に委ねる（プラグイン側の追加処理はない）。codegen テストで検証する |
| JVM | `$EntriesHolder` が Java から見える | `$` を入れた命名と、ABI 保証外であることの文書化（§4.1） |
| JVM (17+) | 基底 sealed の `PermittedSubclasses` 属性 | コンパイラ本体の既存機能である（プラグインは関与しない）。Java 21 の switch との連携は概要 §3 に記載する |
| klib (JS/Native/Wasm) | IR-only 宣言の直列化・同一モジュール内での参照 | §4.1。跨モジュールでの IR 参照はしない |
| JS/Wasm | DCE | §4.1（通常の参照のみであるため追加の対応は不要） |
| Native | lazy と新 MM | 問題なし（§4.2） |
| 全ターゲット共通 | metadata コンパイル（common ソースセット） | FIR が生成した宣言が共通メタデータに載ることが前提である（V5）。EntriesHolder は IR-only であるため metadata klib には現れない（実体は各 platform のコンパイルで生成される。共通コードからの参照は companion / 生成 Enumish の生成メンバーを経由するため問題にならない） |

## 8. no-reflection 保証の確認

生成コード・runtime-api が実行時に使う API の全リスト:

| 使用 API | 分類 |
|---|---|
| `EnumishEntriesHolder`（runtime-api の EntriesHolder 基底）内の `lazy` / `Lazy.value`・`List` の構築と走査 | stdlib + runtime-api（非 reflection） |
| 文字列の比較・文字列の結合（`EnumishEntriesHolder` 内での label の照合と例外メッセージの構築） | stdlib（非 reflection） |
| `IrGetObjectValue` によるシングルトン参照（EntriesHolder・kind・生成 Companion） | 静的リンク（非 reflection） |

`kotlin-reflect`・`java.lang.reflect`・`Class.forName`・`KClass.sealedSubclasses`・associated object は
生成コード・runtime-api のどこからも使用しない。**`KClass` を受け取る API も持たない**
（reified ヘルパを提供しないため。概要 §3 の経緯）。したがって no-reflection は例外条項なしに成立する。
